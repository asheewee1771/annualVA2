# 68: One rule for "a live report file"

**Spec:** [Annual VA spec](../spec.md), stories 23 and 39 (follow-up raised by the ticket 60 review).
**Release:** 1
**What to build:** Ticket 60 added a soft delete of a report file (`report_file.deleted_at`). Every read that must ignore a deleted file now repeats its own `deleted_at IS NULL` condition: about 15 statements in `ReportFileStore`, `ScanReportStore.HAS_CONTENT`, `ReportFiles.file()` and `ScanPoller.keepFindings`, plus the V47 constraints (the list is in ticket 60's Comments). A future read can forget it and count, serve or settle a deleted file. Give "a live report file" one definition that every such read uses, so a new read cannot miss it, with no change in behaviour.
**Blocked by:** 60 (Delete a report file or a Manually Entered Finding while the VA Submission is editable)
**Status:** ready-for-agent
**Effort (orchestrator estimate):** not estimated; raised by the ticket 60 review of 2026-11-22. Small to medium: a refactor with no behaviour change.

- [ ] One definition of "a live report file" (for example a view, a single predicate constant, or a status the reads already filter on) is used by every read that must ignore deleted files; the reads that must see deleted files (`ReportFileStore.FIND`, `FindingStore.REPLACED_FILE`, the disposal reads) say so explicitly. The definition also covers "no live rescan supersedes it" (not rejected, not deleted, not superseded), which ticket 60 writes in `ReportFileStore.COUNT_LIVE` and the `ReportFileStore.DELETE` guard; the screen's `hasLiveRescan` in `ScanReportCard.tsx` infers it from a deleted rescan being absent from the list, and should read it from the API instead.
- [ ] A test fails when a new read of `report_file` bypasses the definition without saying why (an ArchUnit or source-scan test, or an equivalent guard).
- [ ] No behaviour changes but one: the existing Seam 1 tests of uploads, rescans, deletes, the 20-file cap, readiness, the mode rule, settlement and disposal pass unchanged in what they assert. The one deliberate change (decided by the user on 2026-11-26, "Keep it"): a file deleted between the scan job's read of its queue and its read of the file is no longer sent to the scanner (`DeletedWhileQueuedTest`; ADR 0061 item 8).
- [ ] ADR 0061 records the definition. The back-end gate passes; the front-end gate applies only if the front end changes.

## Comments

**2026-11-22, raised and approved:** the ticket 60 thermo-nuclear review (T1) found the deleted filter spread over about 15 statements; no single small, safe fix fitted inside ticket 60. The user chose a follow-up ticket, to be built after the current tickets land, so it is `ready-for-agent`.

**2026-11-23, built (implementer):** the definition is a view, `report_file_live` (V48: `SELECT * FROM report_file WHERE deleted_at IS NULL`), recorded as ADR 0061 item 8. Every statement that reads or writes an existing report file goes through it (PostgreSQL updates and locks the table's rows through a simple view, re-checking its condition as before): `ReportFileStore` `OF_SUBMISSION`, the new `FIND_LIVE` (which replaces the Java `deletedAt` checks of `ReportFiles.file()`, the deletion's read-back and `ScanPoller.keepFindings`), `COUNT_TOWARDS_LIMIT` (was `COUNT_LIVE`), `SUPERSEDE`, `CONFIRM`, `IN_FLIGHT`, `COUNT_IN_FLIGHT`, `WAITING`, `ATTEMPT_STARTED`, `ATTEMPT_FAILED`, `SETTLE`, `DELETE`, `LOCK_REPLACEABLE`, `FORGET_REPLACED`; `ScanReportStore.HAS_CONTENT`; `FindingStore.IS_READY_EVIDENCE` and `SOURCES`. The statements that see deleted files name the table and are listed with their reasons in `LiveReportFileReadsTest`: `ReportFileStore.FIND`, `INSERT`, `LEFTOVERS`, `DEFER_RELEASE`, `CLEAR_QUARANTINE_KEY`, `FindingStore.REPLACED_FILE` and the `DisposalStore` statements. "No live rescan supersedes it" is one SQL fragment on the view (`NO_LIVE_RESCAN_SUPERSEDES`, `superseded_by IS NULL OR NOT EXISTS (… report_file_live …)`, kept under an `OR` so the deletion's re-check after waiting for a supersede runs it again; review correction M1, pinned by `SupersededByLiveRescanTest`), used by the deletion's guard and returned by the API as `supersededByLiveRescan`, which `ScanReportCard.tsx` now reads instead of `hasLiveRescan`. The V47 constraints and index keep their own `deleted_at` (a constraint or an index cannot use a view). `EvidenceDownloadTest`'s list of a file's fields gains `supersededByLiveRescan`; no other existing assertion changed.

**2026-11-25, final-gate correction pass (implementer):** the compliance report's blocker and Mediums are fixed; ADR 0061 item 8 now describes the result.
- **Thermo-nuclear H1 and M1, code review P1, S2 and S3:** `LiveReportFileReadsTest` no longer lexes the sources. It reads every store's static SQL by reflection, as sent, through a helper shared with `ModuleConventionsArchTest`'s `va_system` rule (`StaticSql`). Statements built from `FindingStore.REPLACED_FILE` (`FINDING_TABLES`, `PAGE`, `PROPOSALS`, `BATCHES`, `ReworkQueueStore.PAGE`) are now listed with their reason, and `DisposalStore` is exempt as a whole.
- **Thermo-nuclear M2, Spring Boot L4:** the live read is now `ReportFileStore.find`; the table read is left only where it is needed (`HOLDS_CLEAN_COPY`, for a scan pass that lost a race). The scan job's `begin` and `advance` now read live, so a file deleted between the queue read and the file read is no longer sent to the scanner. That is a small behaviour change in that race only, recorded in ADR 0061 item 8.
- **Thermo-nuclear M3:** the deletion locks, then checks (`LOCK_DELETABLE`, then `DELETE` guarded by `NOT SUPERSEDED_BY_LIVE_RESCAN`), so the guard no longer depends on a plan shape. The earlier `NO_LIVE_RESCAN_SUPERSEDES` and its explanation are gone.
- **Thermo-nuclear M4:** the glossary gains "Live report file" and "active rescan", the prose for the index's sense says "active", and V48 notes the index's older sense of "live".
- **Code review S1:** `SupersededByLiveRescanTest` no longer calls the store. The race runs through the API and the real scan job, which a trigger added by the test holds just after its supersede, using an advisory lock.
- **Lows fixed:** the view's column list is now guarded (`LiveReportFileViewTest`), the V48 comment covers dropping and retyping a column, the ADR status line is reworded, `WITH_SYSTEM` is renamed `JOIN_SUBMISSION`, the reasons for `DEFER_RELEASE` and `CLEAR_QUARANTINE_KEY` are written at the statement, and the race test releases its lock in `finally` and runs on its own threads. The other Lows are left; the final report gives each reason.
- **Round two, thermo-nuclear N1 (code review S13, Spring Boot R2-L4):** the deletion is one store method again. `ReportFileStore.delete(EditTarget, fileId, by, now)` holds the row, then marks it, and returns `NOT_FOUND`, `NOT_DELETABLE` or `DELETED`. `DELETE` filters on `submission_id` again, and `writesToPreparedContentTakeTheEditLock` now lists `delete`. Round-two fixes to Lows: N2 (ADR 0061 items 1 and 2 now describe the lock-then-check) and R2-L3 (`LOCK_DELETABLE` takes `FOR NO KEY UPDATE`, the lock the single `UPDATE` took before).
- **Code review P3:** the 20-file count keeps `superseded_by IS NULL`, as before. A superseded file stays out of the cap even after its rescan is deleted; using "no live rescan supersedes it" there would change behaviour.
