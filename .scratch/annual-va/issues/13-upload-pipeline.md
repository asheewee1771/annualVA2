# 13: Scan Report upload pipeline: quarantine, scan, check, store

**Spec:** [Annual VA spec](../spec.md), stories 20 (pipeline), 24, 27, 78.
**Release:** 1
**What to build:** An SMO uploads one or more files for a Scan Report type. Each file is quarantined, malware-scanned, type-checked and schema-checked before anything reads it; a bad file is rejected with a plain message, a scan that keeps timing out is rejected after two retries, and nobody can view a file until it is clean.
**Blocked by:** 12 (Start a VA Submission)
**Status:** ready-for-agent
**Effort (orchestrator estimate):** about 18.5 developer days across stories 20 (11.5*), 24 (2.0), 27 (2.0), 78 (3.0); `*` marks the critical path. See `reports/dev-report.md`.

- [x] `POST /api/submissions/{id}/files` (SMO, Draft or Returned for Rework, multipart with report type and kind) quarantines the bytes with a SHA-256 and returns 202 with a file id in state QUARANTINED; the stages then run in the fixed order quarantine, malware scan, type allowlist, schema check, and a test proves that order (parse, pre-fill and age are appended by the parser and metadata tickets, which extend the test).
- [x] Scanning goes through the malware scanner boundary (submit, check, fetch clean); at most 10 files are in flight at once, an attempt times out after the configured period and is re-submitted, and after three attempts the file is REJECTED_SCAN_TIMEOUT with the message that the upload was rejected and should be uploaded again. A blocked verdict gives REJECTED_MALWARE and the quarantined bytes are discarded (malware is never retained; recorded as a decision beside the retention rules).
- [x] Type allowlist by declared report type with root-element or JSON-shape sniffing and the per-type size limits (ADR); a disallowed or oversized file is rejected before parsing; the schema check rejects unreadable files; machine-readable kinds hand over to the parsers that arrive in the next four tickets.
- [x] `GET /api/submissions/{id}/files/{fileId}` reports the pipeline status and reject code; `GET .../files/{fileId}/content` serves bytes as an attachment only when the file is clean and the caller may see the System, otherwise 404; every view and download is audited, and a direct download by someone who is not allowed to see the System is refused with 404 (Testing Decisions).
- [x] Errors never echo file content; log lines carry only file ids, statuses and attempt counts (never presigned URLs or file names).
- [x] The Seam 1 harness gains a fake scanner (clean-unchanged, sanitised, blocked, never-finishes) and an in-memory file store; the Scan Report cards on the prepare screen show per-file status and the rejection message.
- [x] The System Register workbook upload (`POST /api/system-register/uploads`, ticket 08) goes through the same quarantine and malware scan before `RegisterSheetReader` reads it (spec story 24, IM8 as-12). Decide whether this scan is synchronous for the small Register file or the upload gains a pending state (today it answers 201), and update ADR 0017 and the Register tests accordingly.
- [x] Every behaviour above is proven by Seam 1 tests through the HTTP API on a real PostgreSQL, with only the boundary adapters faked; the back-end and front-end gates pass.

## Comments

### Note from ticket 08 (2026-10-06): the Register workbook must be scanned too

Spec story 24 ("every upload is malware-scanned ... before it's read") and IM8 as-12 ("Uploads are malware-scanned before they are read") cover the System Register upload as well as Scan Reports. Ticket 08 parses the Register `.xlsx` with Apache POI **without** a malware scan, because the `MalwareScanner` boundary does not exist yet (this ticket builds it). It is a tracked deferral (docs/agents/reviewer-decisions.md, "IM8 controls owned by a later ticket"), owned by this ticket: when the quarantine and scan stages exist, route `POST /api/system-register/uploads` through them before `RegisterSheetReader` reads the bytes. Open design point for whoever builds it: the scan is asynchronous in the pipeline (202 and polling), whereas the Register upload answers `201` with the preview today; either scan synchronously for this small file or give the upload a pending state, and update ADR 0017. Mitigations in place until then: bytes-sniffed type, 2 MB cap, 200-part and 20 MB unpack caps, no macros, formulas never evaluated, DOCTYPE refused, the file is never stored or served, and only the two VA POCs (MFA sign-in) can upload.

### Verification (2026-10-13)

**Implemented** (commits `4b1d087`, `614a8f4`, `0dd3126`, `2601f82`, `43c9451`): `POST /api/submissions/{id}/files` (SMO only, VA Submission in Draft or Returned for Rework) quarantines each file under a random key, answers 202 with status QUARANTINED, and moves it through malware scan, type check by the file's bytes (never its name or declared type), size check and schema check before anything reads it; a file that passes waits at SCHEMA_OK for the parsers (tickets 14 to 17). Reject codes are MALWARE, SCAN_TIMEOUT, TYPE, TOO_LARGE, UNREADABLE, SCHEMA, HASH_MISMATCH and SANITIZED; a rejected file keeps no bytes, and the message is a plain sentence that never echoes file content. New `FileStore` and `MalwareScanner` boundary ports with a `scan` module (quarantine, the unchanged-must-match-the-upload-hash rule, at most 10 files in flight, three attempts then REJECTED_SCAN_TIMEOUT, pacing of a failed submit by the attempt timeout), a `parser` module with `SecureXml` as the only place an XML reader is made (DTDs and external entities off, enforced by an ArchUnit rule), and an `ingestion` module with the controller, `ReportFiles`, `ScanPoller` and `ScanPollerJob` (scheduled only when `annualva.scheduling.enabled`). The poller does scanner and store work with no transaction open, writes the whole outcome in one short guarded transaction, and deletes blobs only after commit in a sweep; a pass that loses a race re-reads the row before dropping its own copy. Status, list and download endpoints answer 404 identically for a missing file and one the caller may not see; a download is served only at SCHEMA_OK or later, as an attachment with a generic type, and is audited for every role before any bytes are read. The Register workbook upload goes through the same quarantine and scan (synchronous, bounded wait; still 201 when clean; 422 `file-rejected-malware`, 422 `file-modified-by-scan`, 503 `scan-timeout`, 503 `scan-mismatch`). Until ticket 51 the production beans are `adapters.pending.Unwired*`, which fail closed (an upload answers 503, nothing is called clean, no setting skips the scan). V9 adds `report_file` and `report_file_stage`; new audit actions FILE_UPLOADED, FILE_REJECTED, FILE_VIEWED and FILE_DOWNLOADED. The prepare screen has per-type Scan Report cards that upload, show per-file status and the rejection message, poll while a file is in progress (paused while the tab is hidden, "taking longer than usual" after two minutes), check type, size and empty files before sending and retry only unsent files. ADR 0021 records the pipeline; ADR 0017 and the README run book are updated.

**Decisions made (docs/agents/reviewer-decisions.md)**
- The per-type size limits and the 20-file cap are accepted as built (25 MB Dependency-Check and XCCDF; 50 MB ARF, Nessus and Burp; 50 MB request ceiling).
- A file's status or list read is audited when the caller is not the owning SMO/Tech Lead (extending the single-submission read rule); the owner's 3-second polling is not audited; downloads are audited for every role.
- A Sanitized scan verdict is a rejection, with no altered copy kept, for Scan Reports and the Register workbook. This supersedes the plan's "Sanitized accepted with clean hash" and ADR 0021 decision 5 as first written; ticket 51's adapter must map the scanner's Sanitized to it.

**Not verified, and open**
- The prepare screen was not viewed in a browser (the mock-m-sso stack is not on this machine), so the hidden-tab pause, the slow message and the partial-upload retry are untested there. There is no real scanner or object store (ticket 51); `ScanPollerJob` is never run in tests, and two-instance concurrency is only simulated in sequence.
- The IM8 reviewer rated two as-12 residuals Medium: (M-1) the front-end `accept` is extension-only, and (M-2) the type check runs after the scan, which the ticket and ADR 0021 fix. It noted that applying the IM8 table literally would make them High and the gate FAIL. M-1 is a one-line fix; M-2 should be recorded as a reviewer decision. Neither has been decided.
- Stale docs to fix before ticket 51 starts: ticket 51's checkbox on line 10 still says Sanitized is recorded with the clean hash, and `docs/implementation-plan.md` line 156 still says `scheduler_lock` and `SKIP LOCKED`.
- `ScanPoller.accept` deletes the clean copy on any exception from the outcome write, so a lost commit acknowledgement could leave SCHEMA_OK with no bytes (same pattern, safe direction, in `ReportFiles.upload`).
- Boundary failures are swallowed with no log line, so a scanner or store outage is invisible.
- The ports pass whole files as `byte[]` (up to 50 MB, no cap on the sum): decide the streaming shape before ticket 51, or record the heap budget in ADR 0021.
- No regression test for "no pooled connection is held during a store or scanner call".
- The upload checks (state, 20-file cap, insert) are not atomic; ticket 25 must re-check the state inside its own transaction.
- The verdict state machine and reject vocabulary are duplicated between `MalwareScan` and `ScanPoller`; `ScanPoller` is 317 lines; the VA Submission state is string-typed until ticket 30.
- The "taking longer than usual" clock is per screen, not per file, and keeps counting while the tab is hidden.
- A pre-existing defect, not this ticket's: a session created by a step-up is not evicted by that person's next sign-in, so a later step-up can answer 401. It is masked in the test harness by a stopgap in `TestEndpoints.resetRegister`, recorded on ticket 09, and a separate task for the real fix has been raised.
- Medium and Low findings remain open in the compliance report. A dev database that applied an earlier draft of V9 needs a reset (V9 was edited before its first commit).
