# Annual VA

Internal web application that runs the organisation's annual vulnerability assessment (VA): the VA Cycle and its Quarters, the System Register, VA Submissions with their Scan Reports and Findings, Cyber Manager review, VA POC endorsement, Exemptions, notifications, exports, audit log and retention.

- Spring Boot 4.0 / Java 21 back end in `backend/` (PostgreSQL 17, JdbcClient + Flyway)
- Vite + React 19 + TypeScript front end in `frontend/`
- Spec: `.scratch/annual-va/spec.md`. Glossary: `CONTEXT.md`. Decisions: `docs/adr/`, `docs/agents/reviewer-decisions.md`. Agent entry point: `AGENTS.md`.

**Every credential, key and password in this repository is a mock value for local development. None is suitable for any deployed environment.**

## Quick start

1. `docker compose up -d` (or, without `../mock-m-sso`, `docker compose up -d postgres localstack`).
2. First time only: `bash scripts/gen-dev-keys.sh` creates `backend/src/main/resources/dev-keystore.p12` and prints the base64 signing keys to paste into `application-dev-mcc.yml`.
3. Back end: `cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev-mcc` then `https://localhost:8443/actuator/health`.
4. Front end: `cd frontend && npm install && npm run dev` then open `https://localhost:5173` and accept the self-signed certificate.

## Simulating the mocks

- **Malware verdicts (mock-SFS):** the verdict follows a keyword in the file's display name: `quarantined` is blocked, `sanitized` is rejected (the app does not accept a modified file), `unchanged` or anything else is allowed unchanged. Upload `report_sanitized.xml` to see the "modified during scanning" rejection. Upload `report_quarantined.xml` to see a malware rejection. `SFS_SCAN_DELAY_MS` in `compose.yml` sets the scan delay.
- **Email (mock-MCNS):** nothing is stored; read sent messages from the container log: `docker compose logs -f mock-mcns | grep "Event=email"`. A message carries only the System, state, action, due date and a link.

## Sign-in and the anonymous-session cap

Starting a sign-in (`/oauth2/authorization/**`) or bootstrapping CSRF (`/api/csrf`) without a session writes a row to the session store, so the app caps how many such sessions one client may start per minute (`annualva.sign-in.anonymous-sessions-per-minute`, default 60; requests that carry a session are not counted). Two limits to know about:

- The cap is per client address as the app sees it. Behind a single gateway or load-balancer address every user shares one counter, so it acts as a global backstop; whether to throttle per client (real client address from the edge, or at the WAF) is a hosting decision (ticket 55).
- It is only a partial IM8 as-4 mitigation. Brute-force protection of the sign-in credentials belongs to the identity provider (MCC SSO), not to this app.

Calls from the app to MCC SSO (token endpoint, JWKS) time out after `annualva.mcc.connect-timeout` (3 s) and `annualva.mcc.read-timeout` (10 s); a timeout is a refused sign-in with reason `provider-error`.

## Step-up before sensitive actions

A sensitive command calls `StepUp.require("<intent>")` first (intent: a lower-case code such as `register-apply`). It is refused with `403 step-up-required` and a `stepUpPath` unless the session's `auth_time` is within `annualva.step-up.freshness-window` (5 minutes). The SPA sends the browser to `GET /auth/step-up?intent=...&returnTo=/route`, which starts a new authorization request with `prompt=login` and `max_age=0`. The callback refuses a token whose `auth_time` is absent or older than the step-up's start (less `annualva.step-up.clock-skew`, 30 s), that lacks MFA evidence, or that belongs to another person; otherwise it only refreshes `auth_time` (never the 8-hour limit) and redirects to `returnTo?stepup=done` (or `?stepup=refused&reason=<code>`). The action is never replayed. Each step is an audit entry (`step-up-started`, `step-up`, `step-up-refused`, and `request-refused` with reason `step-up-required` when the command is refused) carrying the user id and the intent; see "Audit log".

If SIT shows MCC SSO ignores `prompt=login`, set `annualva.step-up.mode: full-sign-in` (environment variable `ANNUALVA_STEPUP_MODE`): step-up then ends the app session and sends the person through a normal sign-in (ADR 0004). That only helps if the single sign-on session is also gone or re-authenticates; confirm with the SSO onboarding ticket.

## SIT onboarding checks (ticket 56)

The `sit` profile (`application-sit.yml`, values in `backend/.env.sit.example`) is ready; what MCC SSO in SIT actually does is confirmed by a person with SIT access, once the MTM onboarding has registered the login and service clients, the EC public key (kid in `ANNUALVA_MCC_SIGNING_KID`) and the redirect URI `https://<sit-host>/login/oauth2/code/mcc-sso-login`. Put the SIT CA certificate (PEM text) at `backend/src/main/resources/sit/mcc-sso-ca.crt`, or point `ANNUALVA_MCC_TRUST_CERTIFICATE` at another `classpath:` or `file:` location. Then sign in and read the ECS log lines (they carry user id and fixed codes only, never claim values):

| Question | How to check | What decides |
|---|---|---|
| Does MCC SSO supply `amr` or `acr` for MFA? | Sign in with `ANNUALVA_SIGNIN_REQUIRE_MFA_CLAIM=true`. | `event.action=sign-in` means yes. `sign-in-refused` with reason `mfa-not-evidenced` means the claim is absent or has other values: read the `amr`/`acr` values in the browser's id token (SIT test account), set `ANNUALVA_SIGNIN_MFA_AMR_VALUES` or `ANNUALVA_SIGNIN_MFA_ACR_VALUES`; only if MCC SSO supplies neither, record that and turn the check off for SIT (logged at startup as `sign-in-mfa-check-disabled`). |
| Is `email_verified` a boolean `true`? | Same sign-in. | Reason `email-not-verified` means it is missing, a string or false: record what is sent; only then set `ANNUALVA_SIGNIN_REQUIRE_VERIFIED_EMAIL=false` (logged at startup). |
| Is `auth_time` returned? | Same sign-in. | Reason `missing-auth-time`: the provider must be configured to return it; there is no application fallback (sign-in and step-up fail closed). |
| Is `afcas.uuid` mapped? | Same sign-in. | Reason `missing-identity`: the `afcas.uuid` mapper is missing on the client. |
| Does MCC SSO honour `prompt=login` and `max_age=0`? | Signed in, open `/auth/step-up?intent=sit-check&returnTo=/` in the same browser. | A password and MFA prompt appears and the log shows `step-up` success: yes. No prompt and `step-up-refused` with reason `stale-auth-time`: it does not. Set `ANNUALVA_STEPUP_MODE=full-sign-in`, re-run the same check through a sensitive action once ticket 10 exists, and update ADR 0004. If MCC SSO keeps its own browser session, an application-only sign-out is not enough: an end-session call to MCC SSO is then needed and is a new ticket. |

Record each answer under ticket 56's Comments.

## Roles and access

Roles are held in the app (table `role_grant`), never taken from token claims, and are read from the store on every request, so a revoked, lapsed, suspended or expired grant stops working on the next call (ADR 0011).

- **VA POCs:** `annualva.va-pocs` (environment variable `ANNUALVA_VA_POCS`) is a comma-separated list of exactly two distinct email addresses. The application refuses to start with fewer or more. At startup it grants each of them `VA_POC` (source `CONFIG`) and revokes a `CONFIG` grant for anyone no longer listed; changing a VA POC is a configuration change request plus a restart. `dev-mcc` lists the two VA POC personas.
- **SMO/Tech Leads and Cyber Managers:** granted per System by the System Register apply (ADR 0018). A grant made by email before the person has signed in attaches to them at their first sign-in.
- **Nobody grants themselves a role:** there is no endpoint that grants one, and an architecture test lists the only classes allowed to write `role_grant`.
- **Seeing a System:** every service path that addresses a System calls `AccessGuard` (ADR 0013); a System the caller may not see answers `404 not-found`, exactly like one that does not exist.
- **Front end:** `GET /api/session` lists the roles held, highest privilege first. The shell shows one nav entry per role and lands the person on the first role's area (`/va-poc`, `/cyber-manager`, `/smo`, `/auditor`); deep links need the host to serve `index.html` for those paths (a hosting decision, ticket 55).

## VA Cycle calendar

A VA Cycle is named after its starting year and has four Quarters, each starting on the first Monday of February, May, August and November and ending the day before the next one starts (12 to 14 weeks; Q4 ends the day before the next Cycle's Q1). A Quarter's Submission Window is weeks 1 and 2 (`submitDue` = start + 13 days), its Review Window weeks 3 and 4 (`reviewDue` = start + 27 days) and its Endorsement Window week 5 to its last day (`endorseDue`). A Cycle's `closesOn` is Q4's end + 28 days, or the day a VA POC closed it early. Everything is computed in `Asia/Singapore` from the `Clock` bean; only a Cycle's opening and close are stored (ADR 0015, ADR 0044).

- **First live Quarter:** `annualva.calendar.first-live-cycle` and `first-live-quarter` (2027 and 3: go-live on Monday 2 August 2027). Earlier Quarters of that Cycle, and every earlier Cycle, are `handledOutsideApp`. The application refuses to start without valid values.
- **API:** `GET /api/cycles` (the Cycles the app runs, the current one, today's business date) and `GET /api/cycles/{year}` (2000 to 2099; anything else is `404`), for anyone who holds a role. Each Cycle lists its Quarters with their windows and due dates, its `phase` (`UPCOMING`, `RUNNING`, `CLOSING`, `CLOSED`: closed once its close is recorded or the day after `closesOn`), `open` (running or closing), `closedAt` and `current` (Quarter, week, window and the window's last day, or `null` when today is outside it).
- **Front end:** the header shows VA Cycle, Quarter, week and the current window, and says when the Quarter is handled outside the app.

## VA Cycle lifecycle

A Cycle opens when its Q1 starts and closes 4 weeks after its Q4 ends, or earlier when a VA POC closes it; until then the older Cycle overlaps the newer one so late Q4 endorsements still have time (stories 17 and 68, ADR 0044).

- **Lifecycle job:** `CycleLifecycleJob` runs at startup and hourly when `annualva.scheduling.enabled` is true (`annualva.cycle.lifecycle-interval`, default `1h`). A pass records the opening of every Cycle whose Q1 has started (`va_cycle`, a `CYCLE_OPENED` entry with the `cycle`, once), keeps the older Cycle's Systems (below), and closes, for nobody, every Cycle past its `closesOn`. In tests, `POST /api/test/jobs/cycle-lifecycle` runs one pass after the clock is moved.
- **Overlap:** the new Cycle takes its Systems and Quarters from the standing Register. From the day it starts, the older Cycle keeps its Systems and their Quarters as they were (`cycle_register`, `cycle_register_system`, V141), so a Register apply changes only the newer Cycle; every apply keeps them first, even before the job's pass. The dashboards, the Overdue sweep, the start and the close all read a Cycle's own Systems; starting a System in a Cycle it was not in is `409 invalid-transition` (reason `not-in-cycle`). Who may see or act on a System is still the Register as it is.
- **Close:** `POST /api/cycles/{year}/close` (a VA POC, body `{}`, step-up intent `cycle-close`) answers `200` with `{year, closesOn, closedAt, notEndorsed}`; a year the app does not run is `404`, a Cycle whose Q4 has not ended `409 invalid-transition` (reason `cycle-running`) and one already closed `409` (reason `cycle-closed`). The close, the VA POC's or the job's, makes every VA Submission of an active System in a Quarter the app runs that is not Endorsed, Exempted, Withdrawn or already Not Endorsed `NOT_ENDORSED` (Exemption Requested included; the Overdue flag clears), gives each Not Started System a `NOT_ENDORSED` VA Submission of its own (nobody started it: `startedAt` is null), records `closed_at`, `closed_by` and an early `closes_on`, audits each change as `SUBMISSION_NOT_ENDORSED` (`state_from`, `NOT_STARTED` for a System, `state_to`, `cycle`) and the close as `CYCLE_CLOSED` (`cycle`, `count`), attributed to the VA POC or to nobody, and publishes one `CycleClosed` event, on which each System's SMO/Tech Lead gets a `NOT_ENDORSED` notification after the commit (a VA POC's close also clears the endorsement pair of what was Awaiting Endorsement). Quarters handled outside the app and retired Systems are left alone.
- **After the close:** no transition is accepted: every step command, the submit and the start answer `409 invalid-transition` with reason `cycle-closed`, from the day after `closesOn` even before the job's pass. A start holds its Cycle shared and a close holds it exclusively (an advisory lock), so no VA Submission is started in a Cycle while it closes.
- **Front end:** the shell reads the Cycles once and, while two are open, shows one VA Cycle selector in the header whose choice every dashboard call uses (it falls back to the Cycle running today once the chosen one closes). The VA POC's Cycle matrix offers Close VA Cycle while the shown Cycle is closing, with a confirm dialog and the fresh sign-in. The SMO inbox lists a Not Endorsed System under Done, flagged and labelled "Not endorsed: the VA Cycle closed before it was endorsed".

## System Register template

A VA POC loads the System Register from a fixed Excel template (story 1, ADR 0016).

- **API:** `GET /api/system-register/template` (VA POC only; an SMO, Cyber Manager, Auditor or a person with no role gets `403`, no session `401`) returns `system-register-template.xlsx` as `Content-Disposition: attachment`. One sheet, five columns in this order: System ID, System Name, SMO/Tech Lead email, Cyber Manager email, Quarter (`Q1` to `Q4`); a hint comment on each header, a Quarter drop-down, an email shape check, text-formatted columns and one example row to delete before uploading.
- **Audit:** each download is a `REGISTER_TEMPLATE_DOWNLOADED` entry (ECS `register-template-downloaded`) with the user id and roles, written in the same transaction; it carries no System and no detail.
- **Front end:** the VA POC area links to the System Register screen (`/va-poc/register`), which has the Download template button under the classification banner.

## System Register upload and preview

A VA POC uploads the filled-in template and sees every change before anything happens (stories 2, 12 and 14, ADR 0017).

- **API:** `POST /api/system-register/uploads` (VA POC only, multipart field `file`, `.xlsx` up to 2 MB, the type decided from the bytes) answers `201` with a preview: an id, `expiresAt` (an hour), `canApply`, `counts` and `rows`. Each row has exactly one `outcome`: `ADD`, `UPDATE`, `RETIRE`, `NO_CHANGE` by System ID (case-insensitive), or `BLOCKED`, with `before` and `after` values, an `unlinkedSmo` flag and, when `BLOCKED`, fixed `reasons` codes. `GET /api/system-register/previews/{id}` reads it back (`404` unknown, `410` after the hour). Nothing in the Register changes until the apply (next section).
- **Blocked rows:** no Cyber Manager, the System's own SMO as its Cyber Manager, an invalid email or Quarter (only `Q1` to `Q4`), a duplicate System ID, a System ID starting `EXAMPLE-` (the template's sample row), or a missing name or System ID. A preview with any `BLOCKED` row has `canApply: false`. The preview is stored as one JSON list on `register_upload`.
- **The file is untrusted:** headers must be the template's, as written; macro workbooks, archives that unpack past 20 MB, empty sheets and sheets with more than 1000 rows are refused; formulas are never evaluated; an error never repeats the file. Each refusal is a fixed `problem+json` type (`unsupported-file-type`, `file-too-large`, `file-empty`, `register-header-mismatch`, `register-sheet-missing`, `register-no-rows`, `register-too-many-rows`, `register-file-unreadable`), and, from the malware scan, `file-rejected-malware`, `file-modified-by-scan` (the scanner had to change the file; upload the original again), `scan-timeout` and `scan-mismatch`.
- **Audit:** `REGISTER_PREVIEWED` (the preview id and the row count), `REGISTER_PREVIEW_VIEWED` and `REGISTER_UPLOAD_REJECTED` (a fixed `reject_code`); never a cell.
- **Scanning needs the real adapters (ticket 51):** the Register workbook and every Scan Report file are quarantined and malware-scanned before they are read (ADR 0017, ADR 0021), but the object-store and scanner adapters are not built yet. Until then they fail closed (`adapters.pending`), so an upload is refused rather than read unscanned; Seam 1 tests use the fakes. A file the scanner had to modify (Sanitized) is rejected, not accepted: the person uploads the original again. Tune the scan with `annualva.scan.attempt-timeout`, `poll-interval`, `max-in-flight`, `sync-wait` and `sync-poll-interval`.
- **Front end:** the Register screen (`/va-poc/register`) has the file chooser, the grouped preview (Blocked, Add, Update, No change, Retire) and the Unlinked SMO flag.

## System Register apply and the Register table

A VA POC applies a confirmed preview with a fresh sign-in, and the SMO/Tech Lead and Cyber Manager roles follow the Register (stories 2 to 4, 73 and 79, ADR 0018).

- **API:** `POST /api/system-register/previews/{id}/apply` (VA POC only, step-up intent `register-apply`: a sign-in older than five minutes is refused with `403 step-up-required`) answers `200` with what it did (`added`, `updated`, `retired`, `unchanged`, `rolesGranted`, `rolesRevoked`). In one transaction ADD rows are added, UPDATE rows are changed (a retired System listed again is reinstated), RETIRE rows are marked retired (never deleted; history stays) and the role grants are reconciled. `404` for an unknown preview; `409` with `preview-applied`, `preview-expired`, `preview-blocked` or `register-changed` (the Register is no longer the one the preview was made from: two VA POCs can hold previews at once, so upload again).
- **Roles from the Register:** every active System has one SMO and one Cyber Manager grant, source `REGISTER`, scoped to it; by email where the person has not signed in (the first sign-in attaches it). A person the Register no longer names, and everyone on a retired System, loses the grant in the same transaction, so their next request is refused. VA POC grants come only from configuration and are never touched.
- **Audit:** `REGISTER_APPLIED` (preview id and counts), one `REGISTER_SYSTEM_RETIRED` per retired System and one `ROLE_GRANTED` or `ROLE_REVOKED` per grant (System, role, source and grant id); no email, name or System ID.
- **Reading the Register:** `GET /api/systems` (VA POC all; SMO/Tech Lead and Cyber Manager only their Systems; an Auditor is refused) lists `id`, `systemId`, `name`, `smoEmail`, `cyberManagerEmail`, `quarter` (`Q1` to `Q4`), `retired` and `unlinkedSmo` (recomputed on each read, shown to a VA POC only, `null` for anyone else).
- **Front end:** the Register screen shows the Apply button on a preview with no blocked row, explains the fresh sign-in (the step-up dialog, then the screen reopens the same preview to apply again), and shows the Register table, reloaded after an apply.

## System Register effects on in-flight work

The preview says what each row would do to in-flight work (a VA Submission that is not Endorsed, Exempted, Withdrawn or Not Endorsed), and the apply withdraws a retired System's in-flight VA Submission only once the VA POC has confirmed it (stories 5 to 7, ADR 0049).

- **Preview:** each row has `effects` and `inFlight` (each VA Submission's `submissionId`, `cycle` and `state`); `counts` gains `willWithdraw`, `willMove`, `willTransfer` and `heldBack`. A row keeps its outcome; what holds it back is in its `reasons`, and any reason on any row makes `canApply` false. `WILL_WITHDRAW`: a retired System with in-flight work, held back while a file of it is still being checked (`FILES_SCANNING`, until the scan settles). `WILL_MOVE` (a Quarter change) and `WILL_TRANSFER` (an SMO/Tech Lead or Cyber Manager change) of a System with in-flight work are held back in Release 1 (`MOVE_IN_FLIGHT`, `TRANSFER_IN_FLIGHT`); a transfer that would give one person two steps of the VA Submission also has `SEGREGATION_OF_DUTIES`.
- **Apply:** the JSON body names the confirmed withdrawals, `{"previewId": "...", "withdraw": ["<submission id>", ...]}`; it must be exactly the preview's withdrawals, else `400 withdrawal-unconfirmed`. The apply checks the in-flight work again with it held; a VA Submission started, finished or given a file since the preview is `409 work-changed`. The answer gains `withdrawn`.
- **Withdrawn:** final and read-only; the Overdue flag clears; one `SUBMISSION_WITHDRAWN` entry per VA Submission (`state_from`, `state_to`, `preview_id`); the SMO/Tech Lead is told (`WITHDRAWN`, mailed with the `register-change` template, `change_kind` "Withdrawn"); a VA POC pair on it clears. A retired System leaves every dashboard and count, so the Quarter board's Withdrawn column stays empty.
- **A Not Started System moved** to another Quarter loses its Overdue flag while the new Quarter's Submission Window is open; the sweep sets it again when it passes.
- **Migration:** V144_43 adds `WITHDRAWN` to `notification_action_check`.
- **Front end:** the preview shows Will withdraw (a tick per VA Submission; Apply stays disabled until each is ticked, and the ticks survive the step-up sign-in), Will move and Will transfer (with why each is blocked), then every row by its outcome, a held-back one with what holds it back.

## SMO Unreachable

When the mail relay refuses an SMO/Tech Lead's address, every System naming them is flagged SMO Unreachable for a VA POC to fix in the Register (story 13, ADR 0051).

- **Set:** a mail settled `REJECTED` (see Email below) flags every active System whose SMO/Tech Lead is that address (matched without regard to letter case), whoever the mail was for and whichever System it was about, from that instant. A System flagged already keeps the first date. Written in the transaction that settles the mail.
- **Cleared:** a later mail the relay takes for that address clears every flag of it set no later than that mail; a Register apply that names another SMO/Tech Lead for a System clears that System's flag.
- **Shown:** `smoUnreachableOn` (the Singapore business date it was set, or `null`) on `GET /api/systems` and on the cards of `GET /api/dashboards/quarter-board`, to a VA POC only (`null` for anyone else and for a retired System). The Register table and the VA POC's Quarter board show "SMO Unreachable since 16 Aug 2027".
- **Audit:** one `SMO_UNREACHABLE` entry per System flagged (no actor) and one `SMO_UNREACHABLE_CLEARED` per System cleared (`source` `mail-accepted` with no actor, or `register` by the VA POC who applied); never the address.
- **Limitation (for the PO):** MCNS answers only at hand-over. An address it accepts and that bounces later is never reported, so such a System is not flagged (ADR 0051).
- **Migration:** V139 adds `va_system.smo_unreachable_at`.
- **Tests:** `CapturingMailRelay.rejectAddress` refuses an address and `acceptAddress` takes it again.

## SMO inbox

An SMO/Tech Lead sees their Systems and what to do by when (stories 18 and 71, ADR 0019).

- **API:** `GET /api/dashboards/smo-inbox?cycle=` (SMO/Tech Lead only; a Cyber Manager, VA POC, Auditor or a person with no role gets `403`, no session `401`) answers `cycle` and two lists. `systems` holds the caller's own active Systems in Quarters the app runs, by Quarter then System ID, each with `quarter`, `state` (`NOT_STARTED`, otherwise the VA Submission's state), `submissionId` (null until it is started), `submitDue`, `reviewDue`, `endorseDue`, `nextAction` (`START_SUBMISSION`; `PREPARE_SUBMISSION` for a Draft or one Returned for Rework; `AWAIT_REVIEW`, `AWAIT_ENDORSEMENT` or `AWAIT_EXEMPTION_DECISION` while someone else acts; null in a final state), `nextActionDueOn` (the last day of the window the state waits on, by the Overdue rule, so Returned for Rework is due on `reviewDue`; null when no window runs), the `group` it is listed under (`NEEDS_YOUR_ACTION`, `WAITING_ON_OTHERS` or `DONE`) and `overdue`, the flag the Overdue sweep set (for a Not Started System too). `handledOutsideApp` holds Systems in Quarters before the first live Quarter, with id, name and Quarter only. `cycle` omitted means the Cycle running today (before the first live Cycle starts, that Cycle); a year the app does not run is `404`, a value that is not a year `400`.
- **Scope:** the caller's Systems come from the access guard (`Need.SUBMIT`), so nobody sees another person's System; a VA POC who is also named as an SMO sees only the Systems they are SMO for.
- **Not audited:** the inbox names no report or Finding, like the Register list (ADR 0018).
- **Front end:** the SMO area (`/smo`) groups the Systems under Needs your action, Waiting on others and Done, lists Systems handled outside the app apart, shows an Overdue pill when `overdue` is true, offers a Cycle selector while two Cycles are open, and has a Start button per Not Started System that starts the VA Submission and opens its prepare screen, and a Continue link per Draft.

## Cyber Manager inbox and Quarter board

A Cyber Manager sees the VA Submissions of the Systems assigned to them, Overdue first, and a Quarter board with one column per state (stories 48 and 49, ADR 0034).

- **Inbox API:** `GET /api/dashboards/cm-inbox?cycle=` (Cyber Manager only; an SMO/Tech Lead, VA POC, Auditor or a person with no role gets `403`, no session `401`) answers `cycle`, `systems` and `handledOutsideApp`. Each System, Not Started included, has `quarter`, `state`, `submissionId`, the three due dates, `dueOn` (the last day of the window its state waits on, null for a final or frozen state), `group` (`NEEDS_YOUR_ACTION` for In Review), `overdue`, `confirmed` and `awaitingReview` (its Findings by review) and `sodConflict` (segregation of duties refuses the caller's review: they acted on that VA Submission at another step, or are assigned to another step of its System, by the one rule the review itself is refused by, `Submissions.conflictedAt`, ADR 0035). Overdue first, then by `dueOn`, then by Quarter and System ID. `cycle` behaves as in the SMO inbox.
- **Board API:** `GET /api/dashboards/quarter-board?cycle=&quarter=` (Cyber Manager or VA POC, see below) answers `cycle`, `quarter` and ten `columns` (`state`, `systems`) from `NOT_STARTED` to `NOT_ENDORSED` in the spec's order, each System with `submissionId`, `overdue`, `confirmed`, `awaitingReview` and `sodConflict`. `quarter` is 1 to 4 (otherwise `400`), and omitted it is the Quarter today falls in, even one handled outside the app (before the Cycle starts its first live Quarter, after it Q4). A Quarter handled outside the app has empty columns and its Systems under `handledOutsideApp`.
- **Scope:** the Systems come from the access guard (`Need.REVIEW`), so nobody sees a System assigned to another Cyber Manager.
- **Not audited:** both name no report or Finding, only counts (ADR 0019).
- **Front end:** the Cyber Manager area (`/cyber-manager`) has two tabs, Inbox and Quarter board (`/cyber-manager/quarter-board`), with the Overdue and segregation-of-duties flags, the Findings counts, a Cycle selector while two Cycles are open and, on the board, a Quarter selector. Each inbox row with a VA Submission links to its review screen, `/cyber-manager/submissions/{id}` (see Review below).

## VA POC Quarter board and Cycle matrix

A VA POC sees a Quarter board of every System and a matrix of the whole VA Cycle, as two tabs (story 64, ADR 0037).

- **Board:** the same `GET /api/dashboards/quarter-board` read for the endorse scope (`Need.ENDORSE`, every System). A person who is both a VA POC and a Cyber Manager gets the VA POC's board. `sodConflict` marks where segregation of duties refuses the caller the endorsement (ticket 34), and a started System's card opens its VA Submission at `/va-poc/submissions/{id}`.
- **Matrix API:** `GET /api/dashboards/cycle-matrix?cycle=` (VA POC only; an SMO/Tech Lead, Cyber Manager, Auditor or a person with no role gets `403`, no session `401`; a Cycle the app does not run `404`) answers `cycle`, `quarters`, `systems` and `handledOutsideApp`.
  - Each of the four `quarters` has `quarter`, `startsOn`, `endsOn`, `phase` (`HANDLED_OUTSIDE_APP`, `CLOSED`, `CURRENT` or `UPCOMING` on today's business date), `counts` (every state but `WITHDRAWN`, zeros included), `total` and `endorsedLate`. Withdrawn VA Submissions and Quarters handled outside the app are not counted.
  - Each of the `systems`, by Quarter then System ID, has `quarter`, `smoEmail`, `state`, `submissionId`, `overdue`, `endorsedLate` and three milestones, `submitted`, `reviewed` (passed to endorsement) and `endorsed`, each with `dueOn`, `doneOn` (the business date it was last reached, null until then) and `current` (the state waits on it now, by the one window rule).
- **Milestone dates:** `submitted_at` (written by submit), and `passed_to_endorsement_at` and `endorsed_at` (migration `V133`), which the pass-to-endorsement (ticket 30) and endorse (ticket 34) commands write.
- **Not audited:** states, dates and counts only (ADR 0019).
- **Front end:** the VA POC area (`/va-poc`) has the Quarter board tab and the Cycle matrix tab (`/va-poc/cycle-matrix`), beside the System Register and the audit log.

## Exports and the management summary

A VA POC asks for the management summary, the export job makes it in the background, and only they download it, for 24 hours (stories 81, 84 and 86, ADR 0045).

- **Ask:** `POST /api/exports` (VA POC only) with `{"type":"MGMT_SUMMARY","format":"XLSX","cycle":2027,"quarter":3,"systems":[...]}`; `cycle` (default: the running Cycle), `quarter` (default: the whole Cycle) and `systems` (default: every System) are optional. A step-up action (intent `export-mgmt-summary`): without a sign-in from the last five minutes it is `403 step-up-required` and nothing is queued. Then `400 invalid-field` names a wrong `type`, `format`, `quarter` (not 1 to 4, or handled outside the app) or `systems` (empty, or a System not in the Quarter or Cycle, or Withdrawn), and an unknown Cycle is `404`. Answers `202` with the export (`status` `QUEUED`) and its `Location`.
- **What it holds:** read when asked for, through the Cycle matrix with the caller's access: a `Summary` sheet (counts by Quarter and state with Endorsed Late, for the Quarters the app runs) and a `Systems` sheet (System ID, name, Quarter, SMO/Tech Lead email, state, Overdue, Endorsed Late, open Deviations: Findings whose current proposal is Risk Accepted or Remediation Planned). Withdrawn VA Submissions and Quarters handled outside the app are left out; no Finding text is ever in it.
- **Classification (A-1):** `Confidential` when it covers every System of the Quarter or Cycle (no `systems`, or all of them), otherwise `Restricted / Sensitive-Normal`; in each sheet's header, footer and first row.
- **Read and download:** `GET /api/exports` (the caller's exports of the last 48 hours), `GET /api/exports/{id}` and `GET /api/exports/{id}/download` are the requester's alone (anyone else, the other VA POC included, gets `404`). The download is an attachment (`management-summary-2027-q3.xlsx`, `no-store`, `nosniff`); `409 export-not-ready` while `QUEUED` or after `FAILED`, `410 export-expired` once `EXPIRED`, `503 storage-unavailable` when the store cannot be read.
- **Export job:** `ExportWorker.run()` (scheduled by `ExportWorkerJob` every `annualva.export.poll-interval`, 5 s; tests call `POST /api/test/jobs/exports`) makes queued files into the file store's `EXPORT` zone (encrypted at rest; key = export id), marks them `READY` for 24 hours (`FAILED`, that export alone, if it cannot be read back or made or the store refuses), and removes the files of expired ones. Migration `V144` adds `export_request`.
- **Audit:** `EXPORT_REQUESTED` and `EXPORT_DOWNLOADED` (refusals with `reason`), with the detail keys `export_id`, `export_type`, `format`, `classification`, `cycle`, `quarter` and `count`; never a System name or an email.
- **Front end:** the Exports tab of the VA POC area (`/va-poc/exports`) asks, reads the list again every few seconds while one is being made, and downloads.

## VA Submission

An SMO/Tech Lead starts the VA Submission for one of their Systems (story 19, ADR 0020).

- **Start:** `POST /api/submissions` with `{"systemId": "<the System's id>", "cycle": <year, optional>}` (SMO/Tech Lead only; a Cyber Manager, VA POC who is not the System's SMO, Auditor or a person with no role gets `403`; an SMO of another System, or a System that does not exist or is retired, gets `404 not-found`) answers `201` with the Draft and its address. `cycle` omitted means the Cycle running today (before the first live Cycle starts, that Cycle); a year the app does not run is `404`. It is allowed before the Quarter begins. There is one VA Submission per System and Cycle: a second start, or the start of a System whose Quarter is handled outside the app, is `409 invalid-transition`; an SMO/Tech Lead who is also the System's Cyber Manager is refused with `403 sod-conflict` (ADR 0035).
- **Read:** `GET /api/submissions/{id}` (the System's SMO/Tech Lead or Cyber Manager, or a VA POC; anyone else `404`, an Auditor `403`) answers `state`, `overdue` with `overdueSince` (when the Overdue sweep set it; null while clear), `endorsedLate` (set by the endorsement, ticket 34), `submitDue`, `reviewDue`, `endorseDue` (copied from the Quarter when the submission starts), `startedAt` and `acted`: who first acted at which step (`SUBMIT` for the person who started it), as user ids and times, never names or emails.
- **Segregation of duties (story 58, ADR 0035):** starting and submitting record the caller in `submission_participation` at the `SUBMIT` step, and a review at the `REVIEW` step. One rule refuses a person a step when they acted at another step of the same VA Submission, or are assigned in the Register to another step of its System (its SMO/Tech Lead counts as the submitter and its Cyber Manager as the reviewer even before they act). It runs on start (the assignment only: an SMO/Tech Lead who is also the System's Cyber Manager), submit, both reviews, the return, the pass to endorsement and the endorsement; each refusal is `403 sod-conflict`, audited as the command's own action with outcome `REFUSED` and `reason` `sod-conflict`. Holding the VA POC role assigns nobody to the endorsing step: a VA POC counts there (`ENDORSE`) only once they act, while a VA POC the Register names as a System's SMO/Tech Lead or Cyber Manager is assigned to that step of it (ADR 0039 item 5, ADR 0042).
- **Audit:** a start is a `SUBMISSION_STARTED` entry (SUCCESS) about the System and the VA Submission; a refused start is the same action with outcome `REFUSED` and a fixed `reason` (`already-started` or `quarter-handled-outside-app`). A read of one VA Submission by a Cyber Manager or a VA POC is a `SUBMISSION_VIEWED` entry (ids only, no detail); the System's own SMO/Tech Lead reading it writes none, and the inbox and lists are not audited (ADR 0019, ADR 0020).
- **Supporting evidence (story 22, ADR 0026):** a PDF or HTML report is attached to a Scan Report with the same `POST /api/submissions/{id}/files`, `kind=EVIDENCE` (any of the three Scan Reports; PDF up to 20 MB, HTML up to 10 MB, at most 20 per Scan Report). It is quarantined, malware-scanned and type-checked from its leading bytes (`%PDF-` at the very start, or an HTML doctype or `<html>` tag in the first 4 KB), never parsed or read, and rests in `READY`; anything else is `REJECTED_TYPE`; a PDF whose tail names `/Encrypt` is `REJECTED_ENCRYPTED` (a byte check, nothing is parsed). `GET .../files/{fileId}/content` serves every file, evidence included, only as an attachment (`application/octet-stream`, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`): the app never renders an evidence file, and the download is audited for every role. An evidence download is always offered as `.pdf` or `.html` by what its bytes are, never under the extension it was uploaded with.
- **Findings and Finding Statuses (stories 28 and 35, ADR 0027):** `GET /api/submissions/{id}/findings` lists the Findings of a VA Submission (anyone who may see the System), the most severe first, in pages of up to 500; it filters by `reportType`, `severity` (repeat it or separate values with commas), `reviewState`, `needsAttention` (no proposal yet, or Disputed) and `changedSinceLastReview` (see Re-review only what changed), and each Finding carries `reviewState` and `currentProposal`. `POST /api/findings/{id}/proposals` (the SMO/Tech Lead of the System, in Draft or Returned for Rework) proposes Remediated with `evidence`, False Positive with `justification`, Risk Accepted with `reason`, `approverName`, `approverRole` and an optional `approvalMemoFileId` (a READY supporting evidence file of the same VA Submission, uploaded with `kind=EVIDENCE`), or Remediation Planned with `plan` and a `targetDate` after today in Singapore (at most ten years ahead). A field that is missing, not used by the status, too long (4000 characters; names and roles 200) or malformed is a 400 `invalid-field` problem whose `field` names it. Every proposal is a new row that a database trigger keeps from ever changing (`GET /api/findings/{id}/proposals` reads the history), the Finding points at the latest and its review state goes back to `PENDING`. A proposal is a `STATUS_PROPOSED` audit entry (ids, the status code and the memo file id; no text), and a read of the history is `FINDING_PROPOSALS_VIEWED` for every role.
- **Bulk-set and progress (stories 36 to 38, ADR 0028):** `POST /api/submissions/{id}/findings/bulk-proposals` (the SMO/Tech Lead of the System, in Draft or Returned for Rework) takes `findingIds` (1 to 1000 distinct ids) and one status with its fields in the same body as a single proposal, and answers `201` with `batchId` and `count`. It makes one `bulk_batch` (append-only, like the proposals) and one proposal per Finding carrying that `batchId` (each proposal now shows its `batchId`, null for a single one). The list is refused as a whole with a 400 `invalid-field` naming `findingIds` when it names anything that is not a Finding of this VA Submission; the fields are checked as for one Finding. A batch is one `BATCH_PROPOSED` audit entry (`batch_id`, `count`, `finding_status`, the memo's `file_id`) plus one `STATUS_PROPOSED` entry per Finding carrying the `batch_id`; a refusal for the state is the same action with outcome `REFUSED`. `GET /api/submissions/{id}/readiness` (anyone who may see the System) answers `total`, `proposed`, `unproposed` (no proposal yet), `awaitingReview`, `disputed`, `carriedOver` and `targetDateMissed` (both 0 until Release 2); a read by a Cyber Manager or a VA POC is a `READINESS_VIEWED` entry with ids only.
- **Replacing a file with a rescan (story 39, ADR 0029):** `POST /api/submissions/{id}/files/{fileId}/replace` (the SMO/Tech Lead of the System, in Draft or Returned for Rework; multipart `file` only) takes a rescan of one parsed report file and answers `202` with the rescan's status; it walks the whole pipeline and is not counted against the 20 files. Nothing changes until it is parsed, and a rejected rescan changes nothing. Once it is parsed, in one transaction, the Findings are compared with the old file's places only: a key it still reports keeps its Finding, proposals and review with the rescan's places (and its severity from the places it has now), a key it no longer reports loses the old file's places, a Finding then reported by no file gets a Remediated proposal with `proposedAs` `RESCAN` whose evidence names the rescan, the scan date its report gives and its upload date, and whose `replacedFile` names the old file (review back to `PENDING`; a Finding already proposed Remediated is left as it is), and a new key is a new Finding. A later file that reports such a Finding again takes the rescan's proposal away as current (the history keeps it; a `PROPOSAL_WITHDRAWN` entry by the uploader with `file_id` and `proposed_as`), so the Finding needs attention again. Settlements of one VA Submission run one at a time (a transaction-scoped advisory lock on the VA Submission), and each locks the Findings it will write once, in id order, before writing. The old file stays `PARSED`, downloadable and marked `supersededBy`; the rescan carries `replacesId`; retention lists superseded files once the VA Submission is Endorsed and an approved disposal deletes their content (ADR 0050). A file that is not a parsed report file or is already replaced is `409 file-not-replaceable`, a second rescan while one is being checked `409 replace-in-progress`, a VA Submission that takes no files `409 invalid-transition`. The upload is a `FILE_UPLOADED` entry with `file_id` and `replaced_file_id` (refusals with a `reason`), the replacement a `FILE_REPLACED` entry by the scan job, and each rescan proposal a `STATUS_PROPOSED` entry with `proposed_as` `RESCAN`, `rescan_file_id` and `replaced_file_id` (every `STATUS_PROPOSED` entry now carries `proposed_as`, and on a proposal `file_id` is only the approval memo); these name the uploader as the actor. A Finding's severity is rated from its current places after every settlement.
- **Not applicable and Findings entered by hand (story 23, ADR 0030):** `GET /api/submissions/{id}/reports` (anyone who may see the System) gives the three Scan Reports with `mode` (`UPLOAD`, the default, `NOT_APPLICABLE` or `MANUAL`), `justification` and `reviewState` (`PENDING`, `CONFIRMED` or `DISPUTED`, for a not-applicable one only); every read is a `SCAN_REPORTS_VIEWED` entry with the count. `PUT /api/submissions/{id}/reports/{type}/mode` (the SMO/Tech Lead of the System, in Draft or Returned for Rework) takes `mode` and, for `NOT_APPLICABLE` (Dependency-Check or Burp Suite only; Secure Configuration is a 400 `invalid-field` naming `mode`) and `MANUAL`, a `justification` of up to 4000 characters; a not-applicable justification goes to `PENDING` for the Cyber Manager whenever it changes. The mode changes only while the Scan Report holds no report file that was not rejected and no Finding (`409 report-not-empty`); setting the mode it already has always works. A Scan Report not uploaded refuses report files (`409 wrong-report-mode`) and still takes supporting evidence. `POST /api/submissions/{id}/findings/manual` (same caller and states, Scan Report in `MANUAL`) takes `reportType`, `title` (200 characters), `identifier` (200), `packageOrRule` (500) and `severity` and answers `201` with a Finding whose `source` is `MANUAL` (every parsed Finding says `PARSED`); the same identifier and package or rule twice is `409 duplicate-finding`. Mode changes are `REPORT_MODE_SET` entries (`report_type`, `mode`) and entries by hand `FINDING_ENTERED` entries (`report_type`), refusals with a `reason`; no text a person typed is audited or logged.
- **Scan date, target and the age rules (stories 25 and 26, ADR 0031):** the pipeline's last stage is the age check: a report whose scan date is after today's business date in Singapore is `REJECTED_FUTURE_DATED` after the parse (stages `SCAN_CLEAN`, `TYPE_OK`, `SCHEMA_OK`, `REJECTED_FUTURE_DATED`; no Findings kept; a `FILE_REJECTED` entry with `reject_code` `future-dated`). `GET /api/submissions/{id}/files/{fileId}/metadata` now also gives `scanDay` (the business date of the file's scan date), `confirmedScanDate`, `confirmedTarget`, `scanDateEdited` and `targetEdited`. `PUT` on the same path (the SMO/Tech Lead of the System, in Draft or Returned for Rework, for a parsed report file) takes `scanDate` (yyyy-mm-dd, not after today, at most ten years back) and `target` (one line, up to 200 characters) and answers `200` with the metadata; a scan date or target that differs from the file's is flagged (`scanDateEdited`, `targetEdited`), never refused, and the confirmed date is the one judged; a file a rescan replaced is `409 file-superseded`. Each confirmation is a `FILE_METADATA_CONFIRMED` entry with the `file_id` and the flags `date_changed` and `target_changed` (refusals with a `reason`); no date or target is logged or audited. `GET /api/submissions/{id}/readiness` also names, as `{fileId, name, reportType}` in upload order, the report files more than 90 days old at today's business date (`tooOld`) and those with no scan date to judge (`undated`: none in the file and none given, or only a Burp export time), judging the confirmed scan date before the file's; only parsed report files that no rescan replaced count.
- **Declaration and submit (stories 40 and 41, ADR 0032):** `GET /api/declaration-text` (SMO/Tech Lead, Cyber Manager, VA POC) answers the current Declaration `version`, `text` and `placeholder`; version 1 is a placeholder seeded by V19 until ticket 24 adds the agreed wording as a new version by migration (the highest version is current, and no version is ever changed). `POST /api/submissions/{id}/submit` (the SMO/Tech Lead of the System, in Draft or Returned for Rework, else `409 invalid-transition`; someone who acted at, or is assigned to, the reviewing step gets `403 sod-conflict`, ADR 0035) takes `declarationAccepted` and `declarationVersion` (the current version) and answers `200` with the VA Submission `IN_REVIEW`, its `submittedAt` and the `declaration` accepted (`version`, the exact `text`, `acceptedBy`, `acceptedAt`), which `GET /api/submissions/{id}` also gives. While anything stands in the way it is one `409 not-ready` whose `reasons` list each as `{reason, message, reportType, files}`, in the order `files-scanning`, `report-missing` (per Scan Report: Secure Configuration needs a report file that was read or Findings entered by hand; Dependency-Check and Burp Suite may also be not applicable), `findings-unproposed`, `files-too-old`, `files-undated`, `files-future-dated`, then `declaration-not-accepted` or `declaration-changed`; `GET /api/submissions/{id}/readiness` gives the same list, without the Declaration, as `blockers`. The submit holds the VA Submission's row, and every write to what the SMO/Tech Lead prepares holds it shared, so nothing changes between the checks and the move. A submit is a `SUBMISSION_SUBMITTED` entry with `state_from`, `state_to` and `declaration_version` (refusals with a `reason` and, for `not-ready`, the `count`), records the caller at step `SUBMIT`, and publishes a `SubmissionEvent` after the commit. Afterwards every change to the files, Findings, proposals, scan dates and Scan Report modes is `409 invalid-transition`, and the screen is read-only.
- **Overdue (stories 42 and 71, ADR 0033):** Overdue is a flag, not a state, and nothing locks: an Overdue VA Submission uploads, proposes and submits as before. The Overdue sweep (`OverdueSweepJob`, at startup and hourly when `annualva.scheduling.enabled` is true; `annualva.overdue.sweep-interval`) flags, on the business day after the window's last day in Singapore, a Draft after `submit_due`, In Review and Returned for Rework after `review_due`, Awaiting Endorsement after `endorse_due`, and an active System with no VA Submission (Not Started) after its Quarter's `submit_due`, in every VA Cycle the app runs that has not closed; final and frozen states, retired Systems and their VA Submissions, and Quarters handled outside the app are skipped. It records when (`overdue_since`, and `not_started_overdue` for a System), flags only what is not flagged yet, so a second pass changes nothing, and writes one `SUBMISSION_OVERDUE` entry per flag (no actor; ids and the `state` it was in, `NOT_STARTED` for a System). A VA Submission started for a flagged System is Overdue from when the System was flagged; a submit keeps the flag only if the Review Window has passed too. In tests, `POST /api/test/jobs/overdue` runs one pass after the clock is moved.
- **Review: confirm or Dispute, one item at a time (stories 50, 52 and 58, ADR 0035):** `POST /api/findings/{id}/reviews` (the Cyber Manager assigned to the System, while the VA Submission is In Review) takes `decision` (`CONFIRMED` or `DISPUTED`), `comment` (up to 4000 characters once cleaned; required to Dispute, optional to confirm) and `proposalId`, the proposal the screen showed, which must still be the Finding's current one (else `409 proposal-changed`); it answers `201` with the review (`id`, `decision`, `comment`, `proposalId`, `reviewedBy`, `reviewedAt`). `POST /api/submissions/{id}/reports/{type}/review` does the same for the justification of a Scan Report marked not applicable, with `justificationVersion` (the Scan Report's `justificationVersion` as read, sent as text) instead of `proposalId` (else `409 justification-changed`; a Scan Report not marked not applicable is `409 not-reviewable`); its review also carries the `justification` it reviewed and that `justificationVersion`. Checks run in the order: who may see it (an SMO/Tech Lead, VA POC, Auditor or a person with no role `403` by the role rule, no session `401`, another System's Cyber Manager or an id that does not exist `404`), segregation of duties (`403 sod-conflict`), the state (`409 invalid-transition`), the fields (`400 invalid-field` naming `decision`, `comment`, `proposalId` or `justificationVersion`), then the version. A review records the caller at step `REVIEW`. Reviews are append-only rows (`finding_review`, `report_review`, V21, triggers like the proposals'); the latest is current, and a Finding is `CONFIRMED` or `DISPUTED` only while the proposal reviewed is its current one, a new proposal putting it back to `PENDING`. `report_slot.justification_version` goes up whenever a justification or a mode changes. The Findings list now gives each Finding's `latestReview` (with its `proposalId`, so a review of an earlier proposal is told apart), and the Scan Reports read gives `justificationVersion` and, for a not-applicable one, `latestReview` with the wording reviewed, kept after a rewrite (decision 2026-10-24). Audit: `FINDING_REVIEWED` (about the Finding) and `REPORT_REVIEWED` (with `report_type`) carry the `decision`; refusals carry a `reason` (`sod-conflict`, `state-not-reviewable`, `proposal-changed`, `not-reviewable`, `justification-changed`); no comment or justification is ever audited or logged. Front end: `/cyber-manager/submissions/{id}` lists the not-applicable Scan Reports, flagged, with their justification and latest review, and every Finding (Manually Entered ones flagged) with what was proposed, its review state and latest review, and Confirm and Dispute with a labelled, classified comment box; the controls show only In Review, and every refusal is the server's problem, after which a `409` reads the item again.
- **Review: confirm or Dispute a Bulk-set batch (stories 51 and 52, ADR 0036):** `GET /api/submissions/{id}/batches` (anyone who may see the System; every read a `BATCHES_VIEWED` entry with the `count`) lists the batches in the order they were made, each with `batchId`, `proposedBy`, `proposedAt`, `proposal` (its first member's: the status and fields every member was given) and the counts `count`, `awaitingReview`, `confirmed`, `disputed`, `changedSince` (members whose current proposal is no longer the batch's) and `manuallyEntered`. The Findings list also filters by `batchId` (the members still in that batch) and `batched` (`true` or `false`: whether the current proposal was made in a batch). `POST /api/batches/{id}/reviews` (the Cyber Manager assigned to the System, In Review) takes `decision` and `comment` (as for one Finding; `proposalId` and `justificationVersion` are refused) and decides every member whose current proposal is the batch's and is `PENDING`: one `batch_review` row (append-only, V129) and an ordinary `finding_review` per member carrying `batch_review_id`. It answers `201` with `id`, `batchId`, `decision`, `comment`, `reviewedBy`, `reviewedAt`, `reviewed` (the Finding ids decided) and `leftOut` (`findingId` and `reason`: `PROPOSAL_CHANGED` when proposed again or withdrawn by a rescan, `REVIEWED` when already confirmed or Disputed). With nothing to decide it is `409 nothing-to-review`. Ownership, segregation of duties and the state are checked as for one review (`404`, `403 sod-conflict`, `409 invalid-transition`), and the caller is recorded at step `REVIEW`. Audit: one `BATCH_REVIEWED` entry (`batch_id`, `count`, `decision`; refusals with `batch_id` and a `reason`) and a `FINDING_REVIEWED` entry per Finding decided with its `batch_id`; never the comment. Front end: the review screen lists each batch with Confirm batch and Dispute batch, a Manually Entered flag when it holds any, how many members were left out and why after a batch review, and its members grouped under it (collapsed until opened); the Findings in no batch are listed below, and Manually Entered Findings stay flagged wherever they appear.
- **Return for rework and pass to endorsement (stories 55 and 57, ADR 0039):** `POST /api/submissions/{id}/return` (the Cyber Manager of the System, In Review) takes an optional `comment` (up to 4000 characters once cleaned; `{}` gives none) and answers `200` with the VA Submission `RETURNED_FOR_REWORK`. Every Disputed Finding and not-applicable justification is attached, each named by the review that Disputed it; with nothing Disputed it is `409 nothing-disputed`. No review changes, so what was confirmed stays confirmed. `POST /api/submissions/{id}/pass-to-endorsement` (same caller and state, body `{}`) answers `200` with it `AWAITING_ENDORSEMENT`, and sets `passed_to_endorsement_at` (the Cycle matrix's reviewed milestone), once every Finding and justification is confirmed; otherwise `409 not-confirmed` whose `reasons` list, in order, `findings-awaiting-review` and `findings-disputed` (with counts in the message), then `justification-awaiting-review` or `justification-disputed` per Scan Report (`reportType`). Both run the review's checks in order (`403` by role, `404` for another System's Cyber Manager, `403 sod-conflict`, `409 invalid-transition` with reason `state-not-reviewable`), hold the VA Submission's row exclusively (a review in progress finishes first), record the caller at step `REVIEW`, move the Overdue flag to the new state's window, are audited as `SUBMISSION_RETURNED` (with `state_from`, `state_to` and the `count` attached) and `SUBMISSION_PASSED` (refusals with a `reason`; `not-confirmed` with the `count` of reasons), and publish a `SubmissionEvent` after the commit for the SMO/Tech Lead's and the VA POCs' notifications (tickets 36 and 37). `GET /api/submissions/{id}/returns` (anyone who may see the System) lists the returns, the latest first, as `{id, step, comment, returnedBy, returnedAt, disputedFindings: [{findingId, reviewId}], disputedReports: [{reportType, reviewId}]}`; every read is `SUBMISSION_RETURNS_VIEWED`, the owner's too, because it carries a comment. Returns are append-only (`submission_return`, `submission_return_item`, V130). `GET /api/submissions/{id}/readiness` now also gives `review: {returnable, endorsementBlockers}`, by the same rule. Front end: the review screen's "Finish the review" panel offers Pass to endorsement (listing what is left) and Return for rework (with a labelled, classified, optional comment), each saying when it is possible.
- **Re-review only what changed (story 56, ADR 0040):** a return and a resubmission change no review, so a Finding whose current proposal is the one the Cyber Manager confirmed stays `CONFIRMED`, and only a Finding proposed again since is `PENDING`; the pass to endorsement then needs only those confirmed. `GET /api/submissions/{id}/findings` takes `changedSinceLastReview`: `true` lists the Findings that have a review and whose latest review is not of their current proposal (proposed again since, even with the same status, or left with none by a rescan), `false` the others; a Finding never reviewed is not changed (it is `reviewState=PENDING`). It combines with every other filter, and the total is of the narrowed list. Front end: the review screen's chips switch between All Findings (the batches, then the Findings proposed one by one) and Changed since last review (one table of every changed Finding, batched or not, each with Confirm and Dispute).
- **Rework queue (stories 60 to 62, ADR 0041):** `GET /api/submissions/{id}/rework-queue` (the SMO/Tech Lead of the System only: a Cyber Manager, VA POC or Auditor `403`, another System's SMO/Tech Lead or an id that does not exist `404`; `page` and `size` up to 500) answers `{stages: [{stage, count}], items: [{stage, finding, dispute}], page, size, total}`: the Findings that need the SMO/Tech Lead (no proposal yet, or Disputed: the Findings list's `needsAttention`), in the stages `DISPUTED`, `NEW_CRITICAL_HIGH` and `NEW_MEDIUM_LOW` (Medium, Low and Informational), the most severe first within each. `finding` is as the Findings list gives it, with its current proposal; `dispute` is the Cyber Manager's latest review when it Disputed, else null. A new proposal puts a Disputed Finding back to `PENDING` and takes it off the queue, and the ordinary submit resubmits it to In Review. Every read is a `REWORK_QUEUE_VIEWED` entry with the `count`. Front end: `/smo/submissions/{id}/rework` (linked from the SMO inbox and the prepare screen once Returned for Rework) shows why it came back (the return's comment and each Disputed not-applicable justification with its Dispute, rewritten on the prepare screen), the stages with what is left, and one Finding at a time with the Dispute as text and the four statuses on keys `1` to `4`; `Enter` saves and moves on, the keys are text while a field has them, `Esc` leaves a field, and Previous and Skip move without saving. Resubmit for review is the prepare screen's Declaration form.
- **Endorse (stories 65, 67 and 70, ADR 0042):** `POST /api/submissions/{id}/endorse` (a VA POC, body `{}`) answers `200` with the VA Submission `ENDORSED`. It is a step-up action (intent `submission-endorse`): without a sign-in from the last five minutes it is `403 step-up-required` and nothing changes. Then an id that does not exist is `404`, segregation of duties `403 sod-conflict` (the VA POC acted at another step of it, or the Register names them its System's SMO/Tech Lead or Cyber Manager; the other VA POC endorses it), and anything but Awaiting Endorsement `409 invalid-transition` (reason `state-not-endorsable`). It holds the row exclusively, records the caller at step `ENDORSE`, sets `endorsed_at` (the Cycle matrix's endorsed milestone) and `endorsed_late` when today's business date is after `endorse_due` (the Quarter's last day, by the Overdue rule's window), clears the Overdue flag (Endorsed waits on no window; Endorsed Late is the lasting mark), is audited as `SUBMISSION_ENDORSED` with `state_from`, `state_to` and `endorsed_late` (refusals with a `reason`; a missing step-up is the usual `request-refused` entry), and publishes a `SubmissionEvent` after the commit for the FYI notification (ticket 37). Migration V134 adds `ENDORSE` to the steps and `endorsed_late` to the audit detail keys. Front end: `/va-poc/submissions/{id}`, opened from a card on the VA POC's Quarter board, shows the state with the Overdue and Endorsed Late flags, the not-applicable justifications and every Finding with what was proposed and its review, read only, and Endorse while it is Awaiting Endorsement; a missing step-up opens the fresh sign-in and brings the VA POC back to press Endorse again, and every refusal is the server's problem.
- **VA POC return and resubmission (stories 66 and 63, ADR 0047):** a VA POC returns a VA Submission Awaiting Endorsement to its SMO/Tech Lead with the same `POST /api/submissions/{id}/return`, to challenge something the Cyber Manager confirmed; `comment` is required (up to 4000 characters once cleaned; missing, blank or too long is `400 invalid-field` naming `comment`), and it answers `200` with the VA Submission `RETURNED_FOR_REWORK`. It is a step-up action (intent `submission-return`), then runs the endorsement's checks (`404` for an id that does not exist, `403 sod-conflict` for a VA POC who acted at another step or whom the Register names its SMO/Tech Lead or Cyber Manager, `409 invalid-transition` with reason `state-not-endorsable` outside Awaiting Endorsement, `cycle-closed` after the close) and records the caller at step `ENDORSE`, so the same VA POC may endorse the resubmission but never review it. A caller who is both a Cyber Manager and a VA POC returns as the System's Cyber Manager while it is not Awaiting Endorsement, and as a VA POC otherwise. The return is kept with `step` `ENDORSE` and attaches nothing (nothing is Disputed Awaiting Endorsement); no review changes, so everything stays confirmed until the SMO/Tech Lead proposes again. It is audited as `SUBMISSION_RETURNED` (`state_from` `AWAITING_ENDORSEMENT`, `count` 0), keeps the Cycle matrix's reviewed date until the next pass, and is Overdue after `review_due` like any Returned for Rework. The resubmit is the ordinary submit to In Review, where the Cyber Manager re-reviews only what changed (`changedSinceLastReview=true`) and passes it again. Migration V135 allows the `ENDORSE` step on a return (with a comment). Front end: the VA POC's endorsement view offers Return for rework with a labelled, classified, required comment beside Endorse (a comment typed before the fresh sign-in is kept across it), and the SMO/Tech Lead's rework screen says who returned it and shows the VA POC's comment, pointing at the prepare screen when the queue is empty.
- **Front end:** `/smo/submissions/{id}` is the prepare screen: the state and dates (with the Overdue pill and since when), a Scan Report card for each of the three reports with how it is provided (a select of upload, entered by hand and, except for Secure Configuration, not applicable, with a justification box and the review of a not-applicable one), a form to enter a Finding by hand when its tool cannot export one, its report files while it is uploaded and, apart from them, its supporting evidence (upload, per-file status and rejection message, download, and Replace with a rescan for a report file whose findings were read), the scan date and target of each parsed report file, pre-filled from the file for the SMO/Tech Lead to confirm or correct (a Burp export time is said to be only that, and an edited scan date or target is marked), Findings entered by hand marked "Manually Entered", the Findings as a spreadsheet-style list with filter chips (Needs attention, All, Disputed, Critical/High), a progress bar with the files too old to submit or with no scan date yet named under it, tick boxes with a select-all, a status select on each row and the fields the chosen status requires (each with its classification label), a sticky bulk bar that applies one status to every ticked Finding, and a disabled Declaration until the submit ticket fills it.

## Exemptions

An SMO/Tech Lead requests an Exemption for a System that had, or will soon have, a separate VA; the VA Submission is frozen until a VA POC decides (stories 43 to 46, ADR 0048).

- **Request:** `POST /api/systems/{id}/exemptions` (the System's SMO/Tech Lead; another role `403`, another System `404`) with `{"basis": "PRIOR_VA" | "SCHEDULED_VA", "vaDate": "yyyy-mm-dd", "evidence": "...", "evidenceFileId": "<optional>", "cycle": <optional>}` answers `201` with the request (`id`, `submissionId`, `basis`, `vaDate`, `evidence`, `evidenceFileId`, `previousState`, `requestedBy`, `requestedAt`, `decision` null, `conditional`, `lapsesOn`). A prior VA falls in the 3 months before the Quarter (and not after today), a scheduled VA in the 3 months after it; `evidence` is up to 4000 characters once cleaned; `evidenceFileId` is a READY supporting evidence file of the same VA Submission (upload it first with `kind=EVIDENCE`). A wrong field is `400 invalid-field`; a file still being checked, a rescan included, `409 files-scanning` naming it; Endorsed, final or already Exemption Requested `409 invalid-transition`; a closed Cycle `409` (reason `cycle-closed`); the System's Cyber Manager `403 sod-conflict`. A Not Started System gets its VA Submission in the same call (from state `NOT_STARTED`). The VA Submission moves to `EXEMPTION_REQUESTED` (the Overdue flag clears), takes no edit and no submit, and both VA POCs get `DECIDE_EXEMPTION`.
- **Decide:** `POST /api/exemptions/{id}/approve` or `/reject` (a VA POC, body `{}`, step-up intent `exemption-decide`). Approve makes it `EXEMPTED` with its work kept; a scheduled VA is `conditional: true` with `lapsesOn` the Quarter's last day plus 3 months (ticket 42). Reject puts back the state it froze, untouched, with the Overdue flag from before if its window has still passed; one the request created goes back to `NOT_STARTED`, which Start then takes. A VA POC the Register names as the System's SMO/Tech Lead or Cyber Manager, or who acted at another step, is `403 sod-conflict`; not Exemption Requested `409 invalid-transition` (reason `state-not-decidable`), an older request `409` (reason `already-decided`). The SMO/Tech Lead gets `EXEMPTION_APPROVED` or `EXEMPTION_REJECTED`, and the other VA POC's item clears; these notices are in the app only, not mailed.
- **Queue:** `GET /api/dashboards/exemption-queue?cycle=` (VA POC) lists the pending requests of a VA Cycle, oldest first, with the System, Quarter, basis, VA date, evidence, evidence file, `previousState` and `sodConflict`; every read is an `EXEMPTIONS_VIEWED` entry with the `count`.
- **Audit:** `EXEMPTION_REQUESTED`, `EXEMPTION_APPROVED` and `EXEMPTION_REJECTED` with `state_from`, `state_to`, `exemption_id` (and `basis` on a request); refusals with a `reason`. The evidence is never audited or logged. Migration V144_40 adds the `exemption` table, the `NOT_STARTED` row state, the detail keys and the notification actions.
- **Front end:** the SMO inbox has Request Exemption on each row that can take one (`/smo/systems/{id}/exemption`: basis, VA date, evidence and an evidence file, each with its classification label); the prepare screen says when the VA Submission is frozen or Exempted. The VA POC area has an Exemption requests tab (`/va-poc/exemptions`) with Approve and Reject (step-up) per request.

## Notifications

Whoever acts next is told in the app once a move commits (stories 92 and 69, ADR 0043), and by email for a required message (see Email below).

- **Who is told:** a submit tells the System's Cyber Manager (`REVIEW`); a Return for Rework by the Cyber Manager tells the SMO/Tech Lead to rework what is Disputed (`REWORK`), and one by a VA POC tells the SMO/Tech Lead to read the VA POC's comment (`VA_POC_REWORK`) and the Cyber Manager that it comes back to them (`VA_POC_RETURNED`; migration V141_35); a pass to endorsement tells both VA POCs (`ENDORSE`); the Overdue sweep tells the person whose step it is (`SUBMIT_OVERDUE` to the SMO/Tech Lead while Not Started, Draft or Returned for Rework, `REVIEW_OVERDUE` to the Cyber Manager, `ENDORSE_OVERDUE` to both VA POCs); a Register apply that moves a System to another Quarter tells its SMO/Tech Lead (`SYSTEM_MOVED`), and one that transfers it tells the new SMO/Tech Lead (`SYSTEM_TRANSFERRED_TO_YOU`) and the former one (`SYSTEM_TRANSFERRED_FROM_YOU`); one that retires it and withdraws its VA Submission tells its SMO/Tech Lead (`WITHDRAWN`; migration V144_43). Endorsed is an FYI for the weekly digest (Release 2) and tells nobody yet. A refused or rolled-back command tells nobody. A person the Register names who has not signed in yet is pre-registered by email and finds the notification at the first sign-in.
- **Content:** only the System (`systemId`, `systemCode`, `systemName`), the `state`, the `action` with the app's fixed `message`, `dueOn` (the last day of the window the state waits on, a Singapore business date) and the `link` (an app path). Never a Finding, a vulnerability or a comment.
- **Both VA POCs:** a VA POC item is two rows sharing a group key. When either VA POC endorses or returns the VA Submission, every open VA POC item on it clears for both, with `handledBy` (the handler's name) and `handledAt`.
- **API:** `GET /api/notifications?page=&size=` (every role; a person with no role `403`, no session `401`) lists the caller's own, newest first, with `readAt` (null while unread), `handledBy` and `handledAt`; `size` is 1 to 200 (default 50). `POST /api/notifications/{id}/read` marks one read, keeping the first time, and answers it; another person's, or one that does not exist, is `404`. Neither is audited: they read and mark the caller's own messages, which carry no report content.
- **Sending one (later tickets):** build a `Notice` and call `Notifications.toSmo`, `toCyberManager`, `to(email, ...)` or `toVaPocs(notice, Awaits...)`, and `Notifications.handled` when a VA POC decision clears a pair, from a listener that runs after the commit (`WorkflowNotices`). A new action or decision is a constant in `NoticeAction` or `Awaits` and a migration that widens `notification_action_check` or `notification_awaits_check`.
- **Front end:** `/notifications`, in the nav for every role, lists them with the System, state, what to do, the due date and the status (Unread, Read, or Handled by a VA POC); Open marks one read and goes to its link.

### Email

A required notification also goes out by email through the mail relay (stories 91 and 94, ADR 0046); it is the same notification, queued in the same transaction.

- **What is mailed:** Return for Rework, which names what is Disputed (`REWORK`, template `returned-for-rework`), and a VA POC's return, to the SMO/Tech Lead and the Cyber Manager (`VA_POC_REWORK`, `VA_POC_RETURNED`, same template, ADR 0047); every Overdue (`SUBMIT_OVERDUE`, `REVIEW_OVERDUE`, `ENDORSE_OVERDUE`, template `overdue`); a Register move, transfer or withdrawal, to the SMO/Tech Lead and on a transfer the former one (template `register-change`, ADR 0049 for `WITHDRAWN`). A submit (`REVIEW`), a pass to endorsement (`ENDORSE`) and the Cycle close's `NOT_ENDORSED` are in-app only; the reminders (ticket 38) mail the people who must act.
- **Content:** the relay's template id and these values only: `system_id`, `system_name`, `state` (as the screens name it), `action` (the app's sentence), `due_date` (`29 August 2027`; left out when none applies), `link` (`annualva.mail.app-url` plus the app path) and, for a Register change, `change_kind`. The System ID and name must still be the Register's plain text, or the mail is `REFUSED` and the relay is never called; the state and the link are held to the app's own by the notification table's CHECKs. No Finding, vulnerability or comment can reach a mail.
- **Dispatch:** `MailDispatchJob` runs `MailOutbox.dispatch` every 30 seconds (`annualva.mail.dispatch-interval`), handing over up to 50 mails, each leased for five minutes just before its own hand-over (the relay adapter's timeout must stay below that). A mail the relay takes is `SENT` with the relay's message id; an address the relay refuses is `REJECTED`, not tried again, and flags SMO Unreachable (see above); a failure is tried again after 1, 2, 4 and 8 minutes and is `FAILED` after the fifth attempt (`annualva.mail.max-attempts`, `first-retry`). A mail whose instance stopped mid-call is claimed again when its lease runs out, or `FAILED` if that was its last attempt; several instances share the outbox safely (`SKIP LOCKED`), and delivery is at least once. Logs name the outbox id and a fixed `event.action` (`mail-send-failed`, `mail-abandoned`, `mail-address-rejected`, `mail-refused`, `mail-claim-lost`, `mail-record-failed`), never an address or a value.
- **Configuration:** `ANNUALVA_APP_URL` (https, no trailing slash) and one MCNS template id per template, `ANNUALVA_MAIL_TEMPLATE_RETURNED_FOR_REWORK`, `ANNUALVA_MAIL_TEMPLATE_OVERDUE` and `ANNUALVA_MAIL_TEMPLATE_REGISTER_CHANGE`; the application refuses to start without them. `dev-mcc` sets mock ids and `sit` placeholders until ticket 57 records the onboarded ones. Until the MCNS adapter (ticket 51) is wired, every hand-over fails and a mail ends `FAILED` in the outbox.
- **Tests:** the Seam 1 harness's `CapturingMailRelay` records every accepted message (recipient, template id, values, message id) and can refuse an address (`rejectAddress`) and take it again (`acceptAddress`), fail the next calls (`failNext`) or stop the dispatcher mid-call (`stopNext`); `POST /api/test/jobs/mail` runs one pass and `GET /api/test/mail-outbox` shows the outbox.
- **Mailing a new kind:** a `MailTemplate` constant, a migration widening `mail_outbox_template_check` and a template id in every profile. A new `NoticeAction` must be given a template and its `change_kind`, or none, in `MailTemplate.of`.

## Retention and disposal

Records are kept for the VA Cycle plus 3 years, a superseded Scan Report file's content until its VA Submission is Endorsed, and an export's row until its 24 hours are up; then they are listed, a VA POC approves the list with a fresh sign-in, and the app hard-deletes them and logs it (story 87, ADR 0050).

- **Due:** a Cycle is due the day after the third anniversary of the business date it closed on (a Cycle not closed never is): its VA Submissions with everything in them, its files, its `not_started_overdue` and kept Register rows, and the records with no Cycle written before the next Cycle started (the cutoff: audit entries, Register previews, notifications about no VA Submission). Also: a System retired before the cutoff with nothing left in a later Cycle, the superseded files of Endorsed VA Submissions (content only; the record stays until its Cycle goes), and exports `EXPIRED`. A listed System is deleted only while it is still retired.
- **List:** the retention job (`DisposalPlanner.plan()`, daily at `annualva.retention.list-cron`, 02:30 in `annualva.time-zone`) writes a `DRAFT` list of items (`SUBMISSION`, `FILE`, `SUPERSEDED_FILE`, `EXPORT`, `SYSTEM`, `CYCLE`, `AUDIT_RANGE`) with reasons; the same records keep the same list, anything else supersedes it. `GET /api/disposal-lists` (VA POC only) gives the newest 20 that were not superseded, items included.
- **Approve:** `POST /api/disposal-lists/{id}/approve` (VA POC only), a step-up action (intent `disposal-approve`): `403 step-up-required` without a sign-in from the last five minutes, `404` for no such list, `409 list-not-draft` for one superseded, approved or executed. Audited `DISPOSAL_APPROVED`.
- **Execute:** `DisposalExecutor.execute()` (every `annualva.retention.execute-interval`, 5 minutes; tests call `POST /api/test/jobs/retention`, which executes and then lists) deletes the file-store objects first (a store that refuses stops the pass, nothing in the database changes, and the next pass retries), then the records in foreign-key order in one transaction (`DisposalStore.STEPS`; `DisposalSchemaTest` fails when a new table names a disposed table and is not disposed of before it), the audit entries before the cutoff only (the disposals' own entries are kept for good), and writes one tombstone, `DISPOSAL_EXECUTED`, with `disposal_list_id` and the counts `submissions`, `files`, `superseded_files`, `exports`, `systems` and `audit_entries`.
- **Append-only tables:** migration `V149` lets a `DELETE` through the append-only triggers only inside the executor's transaction for a list that is `APPROVED` (the transaction-local setting `annualva.disposal_list`), and an audit entry only before that list's cutoff; `UPDATE` and `TRUNCATE` are refused always, and the Declaration wordings are never deleted. Every other removal before retention ends is a soft delete.
- **Superseded file:** once disposed of, its file view has `contentDisposedAt`, the Scan Report card says "Content disposed of", and a download is `410 disposed` (audited `FILE_DOWNLOADED` `REFUSED`, `reason` `disposed`).
- **Front end:** the Disposal tab of the VA POC area (`/va-poc/disposal`) shows the waiting list with Approve and the lists disposed of before.

## Audit log

Every sign-in, sign-out, failed sign-in, step-up step and refused request (401 or 403, including a missing CSRF token and `step-up-required`) is a row in `audit_entry` (IM8 lm-4, story 84), and from now on so is every action a later ticket adds. A row holds the actor (user id), the roles held at the time, the action, the outcome (`SUCCESS`, `REFUSED`, `FAILED`), the System, VA Submission and Finding ids, the request's correlation id and an allow-listed `detail` (fixed codes, ids and counts: never a CVE id, rule name, host, comment, justification, email or name). Nobody can change or delete a row: a database trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` for every connection, the application's own included (ADR 0014). Because the application's database user owns the table, the trigger is a guard against mistakes and application bugs, not against someone who holds that database login: run the application under a role that has `INSERT` and `SELECT` only on `audit_entry`, and migrations under a separate owner (hosting, ticket 55).

- **Writing:** `AuditLog.record(event)` joins the caller's transaction (and fails if there is none), so the entry commits and rolls back with the action. `AuditLog.recordIndependently(event)` commits on its own; the access module uses it for sign-in and refusals. A refusal is recorded where the 401 or 403 is written, so it is kept even when the command it refused had rolled back. A request that answers 404 for a System the caller may not see (ADR 0013) is not a refusal and is not recorded. A 429 from the anonymous-session cap is not recorded (it stays an ECS warning), so a flood of throttled requests does not become a flood of rows. If an independent write fails, the application logs `audit-write-failed` with the exception type only and carries on.
- **Reading:** `GET /api/audit-entries` (a VA POC or a Cyber Manager; an SMO/Tech Lead, Auditor or a person with no role `403`, no session `401`), newest first, with `actor`, `action`, `system`, `submission`, `from` and `to` (business dates in `Asia/Singapore`, both inclusive), `page` (from 0) and `size` (default 50, at most 200). The VA POC area of the front end has the viewer at `/va-poc/audit-log`; it shows Finding ids and no Finding detail. Auditor scope comes in Release 2.
- **Cyber Manager history (story 85, ADR 0038):** a VA POC reads every entry; a Cyber Manager reads only the entries about the VA Submissions where they acted at the `REVIEW` step (a confirm or Dispute of a Finding, a justification or a batch), on Systems the Register still assigns to them. `submission=` naming any other VA Submission (not reviewed yet, of a System reassigned since, another System's, or none at all) is `404 not-found`, unaudited; the other filters narrow within the history, so another System answers an empty page. Every entry about such a VA Submission is listed, whoever wrote it; an entry with no VA Submission (a sign-in, a Register apply) never is. The scope comes from the `submission` module through the `AuditReaders` port, so `audit` still depends on config and web only. Reading the log is not itself audited, for either role. Front end: the Cyber Manager area has an **Audit history** tab (`/cyber-manager/audit-history`) and each review screen links to the history of its VA Submission (`/cyber-manager/submissions/{id}/audit-history`), both the VA POC's viewer with the same filters; the action filter names every action the log records.
- **ECS events:** each entry is also emitted, after its transaction commits, on the logger `annualva.audit` (so it can be routed apart from the application log) with `event.action` (`sign-in`, `sign-out`, `sign-in-refused`, `step-up-started`, `step-up`, `step-up-refused`, `step-up-full-sign-in`, `request-refused`, `role-granted`, `role-revoked`, `register-template-downloaded`, `register-previewed`, `register-preview-viewed`, `register-upload-rejected`, `register-applied`, `register-system-retired`), `event.outcome`, `event.reason`, `user.id`, `user.roles`, `trace.id` and the ids and detail as `labels.*`. A step-up that is needed is now `request-refused` with reason `step-up-required` (it was the event `step-up-required`).
- **Adding an action:** add a constant to `AuditAction`; add any new detail key to both `DetailKey` and the CHECK constraint `audit_entry_detail_check` (a new migration); call `record` from the command's transaction. A detail value must be a short code, an id or a number (`AuditDetail` refuses anything else).
- **Retention:** entries are kept for the VA Cycle plus 3 years and then deleted only by an approved disposal list, before its cutoff (see "Retention and disposal", ADR 0050). Nothing in the application can switch the trigger off.

## Troubleshooting

- **`PKIX path building failed` inside the mock containers:** corporate TLS proxy. Copy `compose.override.yml.example` to `compose.override.yml` and point it at your root CA.
- **Browser refuses `https://localhost:5173` or `:8443`:** accept the self-signed certificate once for each port.
- **Init scripts do nothing in LocalStack:** check they have LF line endings (`.gitattributes` enforces it) and the executable bit.
- **`../mock-m-sso` missing:** `docker compose up -d postgres localstack` still works; sign-in, scanning and mail need the sibling repo.
- **Port already in use:** stop the other process; the dev servers use strict ports.
