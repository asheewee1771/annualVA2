# SMO Unreachable is set by the relay's refusal of an address, and cleared by a later delivery or a new SMO

Status: accepted (items 5 and 6 decided 2026-10-25, item 7 acknowledged the same day, docs/agents/reviewer-decisions.md)

Ticket 39 (story 13) flags a System SMO Unreachable when the mail relay refuses its SMO/Tech Lead's address, so a VA POC can fix the System Register. It builds on the outbox of ADR 0046, which settles such a mail `REJECTED`. It adds one migration (V29), one service in the register module (`SmoReachability`), two audit actions and a field on two existing reads. It adds no endpoint, no table and no notification.

1. **Stored on the System.** `va_system.smo_unreachable_at` holds the instant the relay first refused the SMO/Tech Lead's address since a mail to it last went through, or null. Unlike Unlinked SMO (ADR 0017), which is read from `app_user` when asked, nothing else remembers what the relay said, so the flag is stored. It is a column, not a table, so retention (ADR 0050) has no new foreign key to order. The screens show it as the Singapore business date (`smoUnreachableOn`, from the `CycleCalendar`).

2. **Set by address, on every System naming it.** When the dispatcher settles a mail `REJECTED`, `SmoReachability.refused(address, at)` flags every active System whose SMO/Tech Lead is that address, matched by the Register's citext rule (without regard to letter case). It does so whoever the mail was for and whichever System it was about: a Cyber Manager's refused address flags the Systems that person is the SMO/Tech Lead of, and nothing when there are none. A System that is flagged already keeps the time of the first refusal, so the date says how long the address has been failing; a retired System is never flagged. The settle and the flag are written in one transaction (`TransactionTemplate` in `MailOutbox`), so a flag is never set for an outcome that was dropped because the claim was lost (ADR 0046 item 4).

3. **Cleared by a later delivery or a new SMO/Tech Lead.** A mail the relay takes for the address clears, in the transaction that writes `SENT`, every flag of that address set no later than the moment it was taken; a refusal written after that moment stands, so two dispatchers finishing out of order cannot clear a newer refusal. A Register apply that names another SMO/Tech Lead for a System (an UPDATE where `SystemSnapshot.changesSmoIn`) clears that System's flag in the apply's transaction: whether the old address was refused says nothing of the new one. But when another active System already names the new address and is flagged, the System is flagged from that System's earliest date, so every System naming a refused address shows it (story 13); an ADD is flagged the same way. An apply that keeps the same address keeps the flag, and the flag never makes an apply's baseline differ (`stillTrue` compares snapshots, which hold no flag).

4. **Audited, with no address.** Each System flagged is one `SMO_UNREACHABLE` entry and each System cleared one `SMO_UNREACHABLE_CLEARED` entry, both about the System and `configuration` in ECS. The dispatcher acts for nobody, so its entries have no actor, and a clearing by delivery says `source` `mail-accepted`; a flag or a clearing by an apply is attributed to the VA POC who applied it, with `source` `register`. No entry, log line or error holds the address (lm-19). `refused` and `accepted` skip the access guard, so the architecture test names `MailOutbox` as their only caller.

5. **Shown to the VA POCs only** (decided 2026-10-25). `GET /api/systems` and the cards of `GET /api/dashboards/quarter-board` carry `smoUnreachableOn` for a VA POC, and null for anyone else and for a retired System, as `unlinkedSmo` is: the flag is the VA POCs' to fix (story 13). `RegisterSystems.ActiveSystem` carries the date, so every read model that lists a Cycle's Systems has it; the Quarter board shows it only when read for the endorse scope. The Register table and the VA POC's Quarter board show "SMO Unreachable since" the date. The Cycle matrix does not show it.

6. **No notification** (decided 2026-10-25). The spec's required messages and FYIs (Notifications section) do not include SMO Unreachable, and a VA POC pair (ADR 0043 item 3) is cleared only by a VA POC's decision on a VA Submission, while this flag clears without any VA POC acting (a later delivery) and is about a System, not a VA Submission. So no `NoticeAction` is added; the VA POCs find the flag where they fix it. Telling both VA POCs in the app is a `NoticeAction` (in-app only in `MailTemplate.of`), a migration widening `notification_action_check` after V38 (its latest rebuild) with the union of every action, and a pair that clears by System, if the PO wants it.

7. **The relay gives no asynchronous bounce feedback** (for the PO). MCNS answers a hand-over with accepted or address refused, and reports nothing afterwards (implementation plan, risks: "MCNS has no bounce feedback"). An address MCNS accepts and that bounces later at the receiving mail server is therefore never seen, and its Systems are not flagged; only a refusal at hand-over sets SMO Unreachable. The compensating measure the plan names, a weekly digest to the VA POCs of Unlinked, Unreachable and never-signed-in SMO/Tech Leads, is Release 2 (story 93's digest). The PO is asked to acknowledge this limitation (ticket 39). Acknowledged 2026-10-25 (docs/agents/reviewer-decisions.md).

Consequences:
- A test that needs an unreachable SMO/Tech Lead calls `CapturingMailRelay.rejectAddress` and dispatches a mail to them; `acceptAddress` takes the address again.
- The MCNS adapter (ticket 51) must map only a definite refusal of the recipient to `AddressRejected`; anything that may pass must still throw, or a passing fault would flag Systems.

Amends ADR 0046 item 4 (a `REJECTED` or `SENT` outcome now also sets or clears the flag, in the same transaction).
