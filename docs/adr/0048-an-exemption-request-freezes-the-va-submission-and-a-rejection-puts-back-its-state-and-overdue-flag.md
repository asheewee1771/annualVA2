# An Exemption request freezes the VA Submission, and a rejection puts back its state and Overdue flag

Status: accepted (items 3, 4, 5 and 6 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 40 (stories 43 to 46) lets an SMO/Tech Lead request an Exemption for a System, freezes the VA Submission while a VA POC decides, and makes a rejection restore it exactly. It adds one migration (V144_40), one table (`exemption`), three endpoints, a dashboard read, two screens and no module. The commands are in `submission`, which owns the state machine and segregation of duties (ADR 0035), and they are step commands through `Submissions.atStep` (ADR 0042 item 1).

1. **Request.** `POST /api/systems/{id}/exemptions` (role `SMO`; body `{basis, vaDate, evidence, evidenceFileId?, cycle?}`) answers `201` with the request (no `Location`: nothing reads one request on its own; the VA POCs read the queue, item 7). The checks, in order: ownership through `RegisterSystems.active(id, Need.SUBMIT)` (another System is `404`); the Cycle as a start checks it (running, open, held shared against a close, the System in a Quarter the app runs; ADR 0044); then `atStep` with the `REQUESTING` gate (step `SUBMIT`, from Not Started, Draft, In Review, Returned for Rework or Awaiting Endorsement, `409 invalid-transition` with `reason=state-not-exemptible` otherwise, so a second request while one is pending and a request once Endorsed or final are refused), which also checks segregation of duties and the closed Cycle and holds the row exclusively; then the fields (`400 invalid-field`); then that no file of the VA Submission is still being checked, a rescan included, by the submit's own rule (`SubmitReadiness.FILES_SCANNING`): `409 files-scanning` listing the files, audited with that reason (reviewer decision of 2026-10-18, so a settlement never lands in a frozen VA Submission); then the evidence file. On success the request is kept with the state and the Overdue flag's time it froze (`previous_state`, `previous_overdue_since`), the VA Submission moves to Exemption Requested through `moved` with `OVERDUE_AFTER_MOVE` (a frozen state waits on no window, so the flag clears), the caller is recorded at `SUBMIT`, and it is audited as `EXEMPTION_REQUESTED` with `state_from`, `state_to`, `exemption_id` and `basis`, never the evidence. Edits and the submit are refused while frozen because they accept only Draft and Returned for Rework.

2. **The fields** (`ExemptionFields`, IM8 as-1). `basis` is `PRIOR_VA` or `SCHEDULED_VA`. `vaDate` (yyyy-mm-dd) must fall, for a prior VA, from 3 calendar months before the Quarter's first day to the day before it, and not after today; for a scheduled VA, from the day after the Quarter's last day to 3 months after that day. For Q3 of VA Cycle 2027 (2 August to 31 October 2027) that is 2 May to 1 August 2027, and 1 November 2027 to 31 January 2028. `evidence` is long text cleaned by the one text rule (`ReportText.cleanLongText`), required and at most 4,000 characters (the table checks the same); every refusal names the field and never echoes what was sent. Each free-text field on screen carries the classification label (IM8 dp-8).

3. **The evidence file uses the upload pipeline as it is** (decided 2026-10-25). `evidenceFileId` names a supporting evidence file (kind `EVIDENCE`) of the same VA Submission that is `READY`, uploaded beforehand through `POST /api/submissions/{id}/files` to any of its Scan Reports, so it was quarantined, malware-scanned and type-checked like every file (ADR 0026), and the VA POC downloads it through the same attachment-only route. The check is a port the submissions declare (`ExemptionEvidence`) and the pipeline implements (`ReadyEvidence`), so `submission` does not reach up. A Not Started System has no VA Submission to upload to, so its request carries text evidence only; an SMO/Tech Lead who wants to attach a file starts the VA Submission first. The alternative, a multipart request whose file the pipeline checks after the request, would leave the request's own file scanning while the VA Submission is frozen and needs its own exception to item 1's rule.

4. **A request on a Not Started System, and its rejection** (decided 2026-10-25). The request creates the VA Submission (spec decision "an Exemption on a Not Started System creates the VA Submission"): a row inserted in a new state, `NOT_STARTED`, with the Quarter's windows and the requester as `started_by`, which the same transaction moves to Exemption Requested (`previous_state` `NOT_STARTED`, audited with `state_from` `NOT_STARTED`). A rejection puts the row back to `NOT_STARTED`. A System with no row is still Not Started as before; the dashboards show a `NOT_STARTED` row as Not Started with its id (`SystemState.of`), the SMO inbox offers Start for it, and a start that finds the System's row taken moves a `NOT_STARTED` one to Draft in a statement of its own (`TAKE_NOT_STARTED`, with `OVERDUE_AFTER_MOVE`), keeping the windows it has, while the insert stays `ON CONFLICT DO NOTHING`. The request-created row keeps the requester as `started_by`: the request started it, and only rows nobody started (the close's) have none. The Overdue sweep flags such a row by `window_passed('NOT_STARTED', ...)`, which V20 already answers, and the Cycle close makes it Not Endorsed like any unfinished state. This also gives ticket 42 a place for a lapse back to Not Started with new windows. The alternative, deleting the row on rejection, would lose the request's record and is blocked by the notifications and the participation that name the VA Submission.

5. **Decision.** `POST /api/exemptions/{id}/approve` and `/reject` (role `VA_POC`, body `{}`) are step-up actions with one intent, `exemption-decide` (spec: every Exemption decision), checked before anything is read. Then the request (`404` for an unknown id) and `atStep` with the `DECIDING` gate: step `ENDORSE` (ADR 0039 item 5, ADR 0042 item 2: deciding is the VA POC's endorsing step), from Exemption Requested only (`reason=state-not-decidable`), with segregation of duties (`403 sod-conflict` for a VA POC the Register names as the System's SMO/Tech Lead or Cyber Manager, or who acted at another step of it; the other VA POC decides). The decision is written once (`UPDATE ... WHERE decision IS NULL`), so a request already decided, or an older one when a newer request is pending, is `409 invalid-transition` with `reason=already-decided`. An approval moves to Exempted (final; the work, files and Findings are kept untouched for audit) and, for a scheduled VA, records `lapses_on`, the Quarter's last day plus 3 months, and answers `conditional: true` (ticket 42 records and confirms the VA, or lapses it). A rejection puts back `previous_state`. Both moves are one statement, `RESTORED`, which sets `overdue_since` to the time the request froze if the restored state's window has still passed (the same rule as `OVERDUE_AFTER_MOVE`, built from one function), so a VA Submission that was Overdue is Overdue again from the same moment and nobody is told twice; one whose window passed during the freeze is flagged by the next sweep; Exempted waits on no window, so an approval keeps no flag. Both are audited (`EXEMPTION_APPROVED`, `EXEMPTION_REJECTED`, with `state_from`, `state_to`, `exemption_id`; refusals with a `reason`) and published as a `SubmissionEvent` from Exemption Requested.

   Decided 2026-10-25 (docs/agents/reviewer-decisions.md): deciding is recorded at the VA POC's endorsing step (`ENDORSE`), as the run's conventions and ADR 0042 item 2 say, so a VA POC who rejected an Exemption may still endorse the same VA Submission. The glossary lists deciding an Exemption as a step of its own (CONTEXT.md, Segregation of duties). `DECIDE` stays allowed and unused in `submission_participation_step_check` so that a human can still choose a separate step; making it one is a new `SubmissionStep` with no Register assignment and the `DECIDING` gate's step.

6. **Notifications** (ADR 0043). `Awaits.EXEMPTION` and three `NoticeAction`s: `DECIDE_EXEMPTION` to both VA POCs as a pair on a request, linked to `/va-poc/exemptions`; `EXEMPTION_APPROVED` and `EXEMPTION_REJECTED` to the SMO/Tech Lead, linked to the VA Submission (their inbox when it is back to Not Started). Which pairs a move clears is one rule, `WorkflowNotices.handledBy(from, to)`, asked by the move's listener and by the Cycle close's: leaving Awaiting Endorsement clears the endorsement pair, except for an Exemption request (decided 2026-10-25: the pair stays open, since a rejection returns it there); leaving Exemption Requested clears the request's pair, and the endorsement pair too unless the move returns it to Awaiting Endorsement. The SMO/Tech Lead's link is `Links.forSmo(state, id)`: the inbox for Not Started, the rework queue for Returned for Rework, else the VA Submission. The three notices are in-app only, not mailed through the outbox (ADR 0046): the spec's required messages do not name them (decided 2026-10-25).

7. **The queue.** `GET /api/dashboards/exemption-queue?cycle=` (role `VA_POC`) lists the pending requests of one VA Cycle, oldest first: the Systems of the endorse scope read through `DashboardSystems` (and so `RegisterSystems.active(need, year)`) whose state is Exemption Requested, each with its request (pending means undecided with its VA Submission still Exemption Requested, written once in `ExemptionStore.PENDING`: a request a Cycle's close made moot stays undecided and is not pending), System, Quarter, basis, VA date, evidence, evidence file, the state a rejection restores and `sodConflict` (the decision's own rule, `Submissions.conflictedAt`). It carries what a person wrote, so every read is audited as `EXEMPTIONS_VIEWED` with the `count`, and it is never cached.

8. **Screens.** The SMO inbox offers Request Exemption on every row in a state that can take one, opening `/smo/systems/{id}/exemption` (basis, VA date, evidence, and a choice of the VA Submission's READY evidence files); the prepare screen shows a frozen notice while Exemption Requested and an Exempted notice after. The VA POC area gains an Exemption requests tab with Approve and Reject per row (or "the other VA POC decides" where segregation of duties refuses), the evidence as text and the file as a download; a `403 step-up-required` opens the app's step-up explanation and brings the VA POC back to press it again.

Migration numbering: V144_40 sorts after V141 (ticket 41), V141_35 (ticket 35) and V144 (ticket 44), whose CHECKs it rebuilds with the union of their values; V140 would run before them and be undone.

Not done here, on purpose:
- Recording, confirming or lapsing a conditional Exemption's VA, and Q4 Exemptions after the close (ticket 42).
- A read of a VA Submission's past requests for the SMO/Tech Lead; the notification says how it was decided.
- Any Playwright scenario (ticket 53).

Consequences:
- `SubmissionState` has ten constants. The one dashboard reader (`DashboardSystems`) answers no `submissionId` for a Not Started row, so every dashboard, board and inbox still reads "has an id" as "started"; a reader of `va_submission` itself must ask the state.
- A VA POC who rejected an Exemption may still endorse the same VA Submission, as both are the endorsing step (ADR 0042 item 2).
