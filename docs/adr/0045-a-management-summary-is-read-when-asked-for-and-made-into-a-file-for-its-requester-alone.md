# A management summary is read when it is asked for, made into a file in the background, and kept for its requester alone

Status: accepted (items 4 and 6 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 44 (stories 81, 84 and 86) lets a VA POC ask for the management summary in Excel. It adds one module, `export`, above `dashboard` (the only module that reads the dashboards), one migration (V32), a file-store zone and one screen. Tickets 45 (the PDF) and 49 (retention) build on it.

1. **The commands and their checks.** `POST /api/exports` (role `VA_POC`) with `type` `MGMT_SUMMARY`, `format` `XLSX`, and optionally `cycle`, `quarter` and `systems`. It checks, in order: the role (`403`); step-up (IM8 ac-2, story 77: `StepUp.require("export-mgmt-summary")`, so a stale session learns nothing and queues nothing); the fields (`400 invalid-field`, naming `type`, `format`, `quarter` or `systems`); the Cycle (`404` for one the app does not run, as for the matrix). It answers `202` with the export, `QUEUED`. `GET /api/exports` (the caller's of the last 48 hours), `GET /api/exports/{id}` and `GET /api/exports/{id}/download` are for the requester alone: anyone else, the other VA POC included, is told the export does not exist (`404`, ADR 0013's rule for things that belong to someone).

2. **What it holds is read when it is asked for, with the caller's access.** `ManagementSummaries` reads the Cycle matrix once (`CycleMatrix.matrix(cycle)`, ADR 0037), so the summary, the matrix and the boards cannot disagree about a state, Overdue or Endorsed Late, and asks the Findings for each VA Submission's open Deviations (`Findings.deviationCounts`). The matrix gains `Matrix.restrictedTo(systems)`, which keeps only those rows and recounts the strip over them by the matrix's own rule (`QuarterStrip.recount`, which the matrix itself now counts with), so a summary of one Quarter or of some Systems counts them alone without a copy of the rule; each row gains the System's `smoEmail`. The read is kept as one JSON document of the export module's own shape (`ManagementSummary` with its own `QuarterLine`, not a dashboard response) while the export is `QUEUED`, and removed once the file is made or the export fails. It is read in the request, not by the job, because the access guard answers from the request's own roles (ADR 0011) and the job acts for nobody: reading it later would need the job to act as the requester. Withdrawn VA Submissions and Quarters Handled outside the app are left out (glossary); a Quarter Handled outside the app cannot be asked for alone.

3. **The file.** Two sheets. `Summary`: the title, the business date it was read on, and per Quarter the app runs (or the one asked for) its dates, the count of each state but Withdrawn with Endorsed Late after Endorsed, and the total. `Systems`: System ID, name, Quarter, SMO/Tech Lead (the email the Register names), state, Overdue, Endorsed Late and open Deviations. Every text is a string cell, never a formula. Nothing from a Finding is read at all, so none can be written (a sentinel test checks the cells, headers and footers).

4. **Classification (story 86, assumption A-1).** `CONFIDENTIAL` when the export covers the complete set: every System of the Quarter or Cycle asked for (no `systems`, or a list naming every one that is not Withdrawn); otherwise `RESTRICTED`, written "Restricted / Sensitive-Normal". It is stored on the export and written in each sheet's header, footer and first row. *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* "open Deviations" counts the Findings whose current proposal is Risk Accepted or Remediation Planned, whatever the Cyber Manager's review of it (Disputed and awaiting review included), because a management reader asks how much is accounted for but still open, and before review nothing is confirmed.

5. **The export job and the 24 hours.** `ExportWorker.run()` (scheduled by `ExportWorkerJob`, ADR 0012; tests run a pass by hand) makes the file of each of the oldest queued exports, keeps it in a new file-store zone, `EXPORT` (the production store encrypts at rest, SSE-KMS, ticket 51), under the export's own id, and marks it `READY` with `expires_at` 24 hours later. It calls the store outside any transaction and moves each row only from the status it read, so two instances write the same bytes under the same key and change the row once (as the scan job does, ADR 0021). Each export is handled on its own and the two steps run whatever the other met: one whose stored content cannot be read back, or that cannot be made, or that the store refuses, is marked `FAILED` alone (the VA POC asks again), and any other failure is logged with the export id and the exception type only, never its message. A `READY` export reads as `EXPIRED` from `expires_at` on and its download is `410 export-expired`; the next pass removes its file and stores `EXPIRED` (a file the store cannot remove stays and is tried again, never served). Before it is made, or after it failed, the download is `409 export-not-ready`. The download is checked and audited in a short transaction that has ended before the file is read from the store (as for a Scan Report file), and a store that cannot be read is `503 storage-unavailable`. Retention of the rows themselves is ticket 49's.

6. **Audit.** Asking is `EXPORT_REQUESTED` (`export_id`, `export_type`, `format`, `classification`, `cycle`, `quarter` when one, and `count` of Systems); each download is `EXPORT_DOWNLOADED` (SUCCESS with the export's codes, or REFUSED with `reason` `export-not-ready` or `export-expired`). V32 adds the six new detail keys to the allow-list. Neither holds a System's name or an email; a step-up refusal is the `REQUEST_REFUSED` entry of every step-up. *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* downloading needs no step-up of its own. The step-up guards the asking (spec ac-2, "any bulk or detailed export"); the file is the requester's alone and kept for 24 hours, and asking for a fresh sign-in again a few seconds later, when it is ready, would add a round trip without a new decision.

7. **The screen.** `/va-poc/exports`, a tab of the VA POC area: the form (Cycle while two are open, Quarter or the whole Cycle, every System or those chosen from the Cycle matrix's rows), with the classification label beside each field (dp-8); a `403 step-up-required` opens the app's step-up explanation (and no second error on the screen) and brings the VA POC back with the form filled in again. The form's draft is read once as the page loads, as the Register's is, and `takeRestoredDraft` now leaves another action's draft where it is, so the Register screen no longer drops it. Times are shown in Singapore time. The list of their exports is read again every few seconds while one is being made, and a ready one downloads.

Not done here, on purpose:
- The PDF (ticket 45), which adds a `format` and a renderer beside `ManagementSummaryXlsx`.
- The Cyber Manager's detailed export and the auditor pack, which add their own `type`, roles and intents.
- Removing export rows after the retention period (ticket 49).

Consequences:
- The `export` module may read `dashboard`, `finding`, `cycle`, `access`, `audit`, `boundary` and `web`; nothing reads it (architecture test).
- A summary shows the states as they were when it was asked for, which is seconds before it is made.
- `RegisterSystems.ActiveSystem` carries the SMO/Tech Lead email, so any dashboard row can show it.

Amends ADR 0037 (the matrix can be restricted to some Systems, and its rows carry `smoEmail`).

Amended by ADR 0054: `format` may also be `PDF`, made by a second renderer from the same stored summary, with the classification on every page as a header, footer, first line and diagonal watermark.
