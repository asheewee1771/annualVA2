# The Register upload reads the file as untrusted data and keeps a one-hour preview that changes nothing

Status: accepted

`POST /api/system-register/uploads` (VA POC only, multipart field `file`) reads a filled-in template, works out what it would do to the System Register and answers `201` with a preview; `GET /api/system-register/previews/{id}` reads it back. Nothing in the Register changes until the apply (ticket 10), which is the step-up action the permissions matrix names. Six decisions follow.

1. **The file is decided from its bytes, capped, and never quoted.** The declared content type and file name are ignored. A file is accepted only if it starts with a zip signature, its archive holds `[Content_Types].xml` and `xl/workbook.xml` and no `xl/vbaProject.bin` (no macros), it is at most 2 MB, it has at most 200 archive parts and it unpacks to at most 20 MB. The archive is walked and counted before the spreadsheet library opens it, so a zip bomb never reaches POI. Formulas are never evaluated: a formula cell is read as its last saved result. Every refusal is a fixed problem type, a fixed sentence and a fixed audit code (`UploadRejection`); the only variable part is the column letter of a wrong header. Library exceptions are dropped, not logged, because their messages can quote the file. A cell can also hold what a JSON document or database column refuses (a NUL, a lone surrogate, a pair cut by a length limit), and the database quotes the document back in its error. So the validators judge the raw cell, which keeps the row Blocked, but only a display copy is stored and returned: cut on a code-point boundary at 254 code points, with every control, format, private-use, surrogate, unassigned or separator code point replaced by U+FFFD. Lengths are counted in code points. A database failure while storing a preview is rethrown without its cause (`PreviewNotStoredException`), so the driver's message never reaches the log. A refused file is a `REGISTER_UPLOAD_REJECTED` entry (outcome `REFUSED`, `reject_code` only) written independently, before any transaction opens, so it cannot be lost to a rollback and does not run inside a domain transaction (ADR 0014).
2. **The headers are the template's, as written.** The sheet is the one named `System Register`, or the only sheet; the first row must hold the five header texts of `RegisterTemplate.HEADERS` in columns A to E, and nothing after them (ADR 0016). A sheet with no System rows is refused, because the file would retire every System; more than 1000 rows is refused.
3. **The preview vocabulary: one outcome per row.** Rows are matched to Systems by System ID, trimmed and without regard to case. A row has exactly one `outcome` (`Outcome`): ADD, UPDATE or NO_CHANGE by System ID, RETIRE for a System the file leaves out (never deleted), or BLOCKED with fixed reason codes (`BlockReason`). A retired System that the file lists again is an UPDATE that reinstates it; one that is retired and left out stays unlisted. A row is BLOCKED for a missing or unusable System ID, a duplicate System ID (all rows sharing it), a System ID that starts `EXAMPLE-` (ADR 0016), a missing or oversized name, a missing or malformed SMO/Tech Lead email, a missing or malformed Cyber Manager email, a Cyber Manager who is the System's own SMO/Tech Lead, and a missing Quarter or one that is not exactly `Q1` to `Q4`. A BLOCKED row carries no ADD/UPDATE classification (the apply never reads one: it needs every row unblocked), still shows what was typed (sanitised, clipped) and the existing System it matches, and still stops the System it names from being retired. A System ID or name may hold no space other than U+0020, so look-alike IDs cannot differ. `canApply` is false while any row is BLOCKED. A reason names the problem and never repeats a cell. Every outcome is listed, including NO_CHANGE, so every Unlinked SMO flag the summary counts is visible.
4. **Unlinked SMO is read, not stored.** An SMO/Tech Lead email is Unlinked when no `app_user` with that email has a `sso_id` (a person pre-registered by email has not signed in). The preview records the answer at upload time; the Register table (ticket 10) asks again when it is read, so the flag clears as soon as the person signs in. The implementation plan's `va_system.smo_unlinked` column is therefore not created.
5. **Tables.** `va_system` (a surrogate `id` that `role_grant` and `audit_entry` use, the business System ID as `code`, citext and unique; a CHECK that the Cyber Manager is not the SMO/Tech Lead) is created here because the preview must read the Register; this ticket never writes it and ticket 10 adds the foreign key from `role_grant.system_id`. `register_upload` holds the preview, and the preview rows are one `jsonb` list on it (`rows`, a list of `PreviewRow`), not a table of rows: a preview is made once, read whole and applied whole, nothing queries one row, and a row table would need the outcome, the reasons and the before and after values to be kept consistent by CHECKs. The file itself is not kept. The audit log gains the detail key `preview_id` (migration V6) and the actions `REGISTER_PREVIEWED`, `REGISTER_PREVIEW_VIEWED` and `REGISTER_UPLOAD_REJECTED`.
6. **One hour, then gone.** A preview expires an hour after the upload by the `Clock` bean. Reading an expired preview answers `410 preview-expired`; an id that never existed answers `404`. Either VA POC may read a preview. Role gating is the control, twice: `hasRole('VA_POC')` on each controller method (ac-1) and the same rule on `/api/system-register/**` in the security chain, so a stranger's multipart body is refused before it is parsed. A preview names no one System the caller could be denied (a VA POC's scope is every System), so there is no `AccessGuard` check (ADR 0013).

**Malware scan: not yet, and owned by ticket 13.** IM8 as-12 and story 24 want every upload scanned before it is read, and that includes this workbook, but the `MalwareScanner` boundary does not exist yet: ticket 13 builds the quarantine and scan pipeline and ticket 51 the production adapter. Until then the workbook is parsed unscanned, with the mitigations in decision 1 and with only the two MFA-authenticated VA POCs able to upload. This is a tracked deferral under the "IM8 controls owned by a later ticket" decision; ticket 13 now names the Register upload as its to do (sync scan or a pending state is its design choice), and ticket 51 notes it.

Consequences: the apply must refuse a preview whose baseline has changed since it was made (two VA POCs may hold previews at once, and a preview is a snapshot, not a lock); expired previews and their rows are not purged yet (the retention ticket owns disposal, ADR 0014's trigger reasoning applies to the audit log only); the management summary and any other export that writes System names or IDs back into a spreadsheet must neutralise a leading `=`, `+`, `-` or `@` (ticket 44); a header or Quarter notation change is a change to ticket 07's template and to the reader together.
