# A Nessus compliance audit is parsed in the pipeline into Findings keyed by check, with an occurrence per host

Status: accepted

Ticket 16 adds the third parser behind the pipeline (ADR 0022 added Dependency-Check, ADR 0023 SCAP): a `.nessus` export (`NessusClientData_v2`) of a compliance audit, uploaded as the Secure Configuration Scan Report, is parsed in the settlement transaction into Findings, and the scan date and the hosts it names are kept for the SMO/Tech Lead to confirm. It is built on the shared pieces of ADR 0022 and 0023 (`FindingsBuilder`, `ParsedReport.Occurrence.merge`, `ReportDates`, `XmlCursor`, V10 and V11) and adds no table and no migration. Eleven decisions.

1. **One parser, streamed, reading only where the format puts a result.** `parser.nessus.NessusXmlParser` is behind `ReportParser` for `ReportFormat.NESSUS`; `ReportFormat` now has a null parser only for Burp (ticket 17). It walks the document through `XmlCursor` and goes only into `NessusClientData_v2/Report/ReportHost`, its `HostProperties` and its `ReportItem`s. Everything else is skipped without being looked at: the `Policy`, and, inside an item, everything except `compliance-check-id`, `compliance-check-name` and `compliance-result` (a `.nessus` file is mostly item descriptions and plugin output, which are never built). Nothing is held per item or per host: a result goes straight to `FindingsBuilder`, because the host is the `name` attribute of the `ReportHost` and is known before its first item. A result-like element in the `Policy`, directly under `Report`, nested inside an item or inside a nested `ReportHost` is never a result.
2. **The shape is checked by the parser, and a file that is not that shape is `REJECTED_SCHEMA`.** The type check decides `NESSUS` from the root element's name `NessusClientData_v2` alone, so any other root (`NessusClientData`, version 1, `Report`) is `REJECTED_TYPE` for a Secure Configuration upload. The parser then needs a `Report` under that root, and refuses (`REJECTED_SCHEMA`) a file with none, a failed, warned or errored check with neither a check id nor a check name or in a `ReportHost` with no `name`, a check id or name (the key) longer than 1,000 characters, a host name longer than 500, any value read longer than 4,000 characters (the check id and name), a `compliance-result`, a `HOST_END` or a `severity` attribute longer than 100, and a value that holds markup where text belongs. A file refused by the parser ends `SCAN_CLEAN`, `TYPE_OK`, `REJECTED_SCHEMA`, never `SCHEMA_OK`. A well-formed export of a scan with no compliance items at all, or of a vulnerability scan, is accepted with no Findings (`PARSED`); the pre-fill confirmation (ticket 23) is where a person sees that nothing was found.
3. **Which results are Findings.** A `ReportItem` is a compliance check only if it has a `compliance-result` (the `cm:` elements are the ones a compliance audit adds; every other item, a vulnerability, an information plugin or a compliance summary with no result of its own, is ignored whatever its severity). The result is compared after trimming and in upper case: `FAILED` and `WARNING` are Findings; `ERROR` is a Finding marked as a check that did not complete (CONTEXT.md), because it is neither a pass nor a fail; `PASSED`, and any other word Nessus may write or a hostile file may invent, is ignored, as for SCAP (a value this parser does not know is not a deviation to ask a person about). The elements are matched by local name and by their full path, not by the `cm` namespace: the prefix is only a convention, and what a real export binds it to is not verified until ticket 58 (a wrong guess about the namespace URI would make a real file silently yield nothing, which is worse than accepting a look-alike at the right path from a person who is uploading their own scan).
4. **Severity is the item's `severity` attribute; unrated is Medium.** `0` is Informational ("Info"), `1` Low, `2` Medium, `3` High, `4` Critical; the words Critical, High, Medium, Low, None and Info are read as well (as `Severity.ofLabel` reads them); a missing attribute, an empty one or any other value is Medium (implementation plan section 2.4: unrated SCAP and Nessus are Medium). A Finding's severity is the highest of its occurrences. The item's `risk_factor` element is not read. The ticket's rule is followed exactly: an item whose attribute is `0` is Informational even when its result is `FAILED`. Which level a real export gives a failed or warned check is not verified (ticket 58): if Nessus writes `0` on failed compliance items, every failure would read Informational, and the rule would need a second source of severity.
5. **The Finding key is `nessus|<check id>`, else `nessus|<check name>`, with one occurrence per host.** The id is preferred because it names one check and is short; two different checks can share a name and a check can be reworded between audit file revisions (neither is verified against a real export). A key is never cut, so a check name used as the key must fit in 1,000 characters or the file is refused. The identifier and the rule the list shows are the check name (what a person reads), else the id, cut to 1,000 characters because it only describes the Finding; so a long name beside an id is cut, not refused. A host is the `name` of its `ReportHost`, cleaned like every text from a report (ADR 0022 item 6). One check that fails on three hosts is one Finding with three occurrences, two files naming the same check are one Finding with an occurrence in each file, and a check read twice for one host (the same host scanned twice in a file) is merged by `Occurrence.merge` as `FindingsBuilder` already does (the worse severity; it did not complete only if neither reading did).
6. **Completion is the rule of ADR 0023 item 6, unchanged.** `finding_occurrence.did_not_complete` (V11) is true for a place whose results were all `ERROR`; the Finding-level `didNotComplete` is `bool_and` over its places, worked out when the list reads. A check that failed on one host and errored on another is a failed check.
7. **The scan date and the target are pre-filled, not trusted.** The scan date is the latest `HOST_END` of the file's hosts (the `tag` named `HOST_END` in a host's `HostProperties`; `HOST_START` is not used). Nessus writes it as `Tue Jul 20 10:03:44 2027`, with no zone and no ISO separators, so `ReportDates` now reads that form too (a day under ten is padded with a space, which it takes; the weekday must agree with the date, else it is no date); the time is taken as UTC, as for an ISO date with no offset, because the file does not say which zone the scanner was in, so it can be some hours out and is exactly what the SMO/Tech Lead is asked to confirm. The target is the hosts the file names (every `ReportHost@name`, including one with no compliance items), distinct, in order, at most 50, joined with a comma and cut to 200 characters. The hosts and the latest date are gathered by the new `parser.ScanFacts`, which the SCAP parser now uses too (its own copy of the same logic is gone and its behaviour is unchanged), and are stored and served by the audited metadata read of ADR 0022 item 5, unchanged.
8. **Limits.** The size limit is ADR 0021's, 50 MB, which is also the request ceiling, so a larger file is refused with 413 at the upload and nothing is kept. The caps inside a file are ADR 0022 item 9's and were accepted by a human on 2026-10-14 (`docs/agents/reviewer-decisions.md`); `FindingsBuilder` is the one place that counts them and the parser calls it without counting itself, so unlike SCAP it needs no per-host bound of its own. A report over a cap is `REJECTED_TOO_MANY_FINDINGS`. The web client's too-large hint for a Secure Configuration file now also names the 50 MB Nessus limit and advises exporting in parts, with fewer hosts each.
9. **Shared code, not a second copy.** New: `parser.ScanFacts` (item 7) and `ReportText.firstClean` (the first value that says something, cleaned; it replaces the private copy in the SCAP parser). Changed: `ReportDates` reads the Nessus form. The test helpers the parser tests share (a Findings total, the too-many-Findings assertion, the summary of Findings by key) moved up into `ParserSeam1` from the SCAP and Dependency-Check tests.
10. **Hardened XML, and nothing from a report is said back.** The reader is made in `SecureXml` (no DTD, no external entity; the architecture test keeps it so), and an entity declaration or an entity bomb is `REJECTED_UNREADABLE` by the schema check before the parser runs. No check id, check name or host reaches a log line, an audit entry or an error body; a rejection says the same fixed sentence whatever the file held (proved by Seam 1 tests with a sentinel, including for a file over a cap).
11. **Samples and build.** `backend/src/test/resources/samples/nessus/compliance-audit.nessus` is a hand-written reconstruction (two hosts, every result word, items that are not compliance checks) labelled so in the file and in a README, with invented names and documentation-range addresses; it is not the output of a real scan and **real Nessus exports are untested until ticket 58** (plan H6), which should be treated as a gate for this parser before release, particularly for items 3 to 5. One build-config change rides with this ticket because two tests now upload a 49 MB file (the ARF one of ticket 15 and a Nessus one) and each needs about 512 MB of heap, a standing review suggestion: the surefire `argLine` is `@{argLine} -Xmx1g` (keeping JaCoCo's agent), with an empty default `argLine` property so the late-bound reference resolves when JaCoCo does not set it.

Consequences: uploading the same export twice doubles every occurrence count until ticket 21's replace rule applies (as for the other parsers); a Nessus export of a vulnerability scan is accepted with no Findings; the severity a real export carries on a failed compliance item, the check id's stability and the `cm` namespace are assumptions to confirm at ticket 58; the date is taken as UTC.

Amends ADR 0023: item 1 and the consequences (`ReportFormat` has a null parser only for Burp now); the host and date gathering of item 7 lives in `ScanFacts`.
