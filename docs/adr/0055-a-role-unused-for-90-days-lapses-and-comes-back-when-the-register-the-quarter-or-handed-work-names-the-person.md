# A role unused for 90 days lapses and comes back when the Register, the Quarter or handed work names the person

Status: accepted (items 3, 4, 5 and 6 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 46 (story 80a, IM8 ac-3) builds the role lapse that V4 left room for (`last_used_at`, `lapsed_at`) and the automatic return the spec's *Release 1 decisions* added: with a standing Register no annual upload names people again, so a lapsed SMO/Tech Lead or Cyber Manager role also comes back when the Quarter of a System they are named on begins, or when work is handed to them; a VA POC's comes back only through configuration. It adds one migration (V149_46), one scheduled job, a configuration setting and no endpoint. The rule lives in `access` (`RoleLapse`, the only new writer of `role_grant`); `submission` tells it when each System's Quarter began and when work is handed over (`RoleLapses`), because `access` reads neither the Register nor the calendar.

1. **What is stored.** `role_grant` gains `returned_at` and `return_trigger` (`REGISTER`, `QUARTER_START`, `RETURN_FOR_REWORK`, `SUBMITTED_FOR_REVIEW`, `EXEMPTION_LAPSE` or `CONFIGURATION`), set together each time a lapsed grant comes back, so ticket 47's role-holder review can list the automatic returns since its last review. A CHECK holds that a VA POC grant returns only by `CONFIGURATION` and nothing else does. A lapse sets `lapsed_at`; a return clears it. The grant is the same row throughout: a lapse never revokes.

2. **The lapse.** `RoleLapses.run` (job `RoleLapseJob`, at startup and an hour after each pass, `annualva.roles.lapse-interval`, default `1h`, when `annualva.scheduling.enabled`; the ticket's daily job run hourly as the Overdue sweep is, ADR 0033 item 6) reads the clock once and calls `RoleLapse.pass`. A grant lapses when it still counts (not revoked, lapsed, suspended or expired) and the latest of its grant, last use and last return is more than 90 days before now: the one rule, `RoleGrantStore.UNUSED_SINCE`, read and then written with the same condition, so a request that used the grant in between wins and two passes lapse it once. Last use is what role resolution already records, at most once a day (ADR 0011). Every role lapses, the VA POCs' included. The person's sign-in is left alone (ac-3: annual SMOs are not locked out of the identity provider); their next request has no role, so the role-guarded endpoints answer `403` and are audited as every refusal is. Each lapse is a `ROLE_LAPSED` entry for nobody with the `role`, `source` and `grant_id`, about the System for a per-System role, never the email.

3. **The Quarter's start counts as a return moment** (decided 2026-10-25). For each System still in the Register, `RoleLapses` finds the latest of its Quarters that has begun among the open Quarters the Overdue sweep and the reminders read (`OpenQuarters`, ADR 0052: not Handled outside the app, in a VA Cycle that has not closed), and passes the instant it began (midnight, business time). A Quarter of a closed Cycle began more than 90 days before, so leaving it out changes nothing. A lapsed SMO/Tech Lead or Cyber Manager grant whose System's Quarter began after it lapsed comes back (`quarter-start`); and a grant whose System's Quarter began within the last 90 days does not lapse, even if unused. Without the second half, a grant last used 89 days before its Quarter begins would lapse on the Quarter's second day and nothing would return it until work was handed over, locking an annual SMO/Tech Lead out of the very Quarter they are named for. Because the Quarter start is compared with the lapse time, a pass missed while the application was down still returns the grant on the next pass. The alternative is the ticket's rule read literally (last use or grant only, and a return only for a grant lapsed before the Quarter began).

4. **A Register apply returns everyone it names** (decided 2026-10-25). The Register is one standing list (ADR 0018), so every apply names every active System's SMO/Tech Lead and Cyber Manager again. `RegisterRoles.follow` returns any lapsed `REGISTER` grant it would have kept standing (`register`), attributed to the VA POC who applied it; a suspended one stays suspended (ticket 47). The alternative is returning only the people on rows the preview classified as added or changed, which would mean an unchanged row never "names the person again".

5. **Work handed over** (decided 2026-10-25 in the submit). Heard synchronously inside the command's transaction (`@EventListener`, `MANDATORY`), so the return commits or rolls back with the move and is attributed to its actor:
   - a Return for Rework, by a Cyber Manager or a VA POC (`SubmissionEvent` to Returned for Rework), returns the System's SMO/Tech Lead (`return-for-rework`);
   - a submit (to In Review) returns the System's Cyber Manager (`submitted-for-review`). The ticket lists only the first; a submit hands the review to the Cyber Manager in the same way, and without it a VA Submission resubmitted after a Return for Rework or an Exemption lapse can wait on a Cyber Manager whose role lapsed with nothing to bring it back;
   - a conditional Exemption that lapses back with new windows (`ExemptionEvent` `LAPSED`, ADR 0051) returns the SMO/Tech Lead, who is told and must act in the new Submission Window, and also the Cyber Manager when it is back In Review (`exemption-lapse`), attributed to nobody. A lapse to Not Endorsed has no new windows and returns nobody; one back Awaiting Endorsement waits on the VA POCs, whom only configuration returns;
   - a rejected Exemption that puts a VA Submission back where the request froze it returns nobody: the SMO/Tech Lead asked for it shortly before.

   A transfer is a Register apply that names the new person, who gets a new grant (ADR 0049), so it needs nothing more here.

6. **A VA POC returns only through configuration** (decided 2026-10-25). `annualva.va-poc-role-returns` (environment variable `ANNUALVA_VA_POC_ROLE_RETURNS`, empty by default) may list only the configured VA POCs, or the application refuses to start; the startup sync returns a listed VA POC's lapsed grant (`configuration`, no actor). So a VA POC comes back by the same change request that sets them. A restart that lists nobody returns nobody, and neither does a Register apply or handed-over work, which return `REGISTER` grants only. The setting stays until the next change request empties it; a VA POC still listed when their role lapses again gets it back at the next restart. The alternative, every startup returning a configured VA POC, would make any restart, a crash recovery included, undo the lapse.

Migration numbering: V149_46 sorts after V149 and V149_42, merged before it; it changes only `role_grant`, which V4 created. No new table, no foreign key and no notification or audit-detail CHECK change (the trigger is audited under the existing `reason` key), so the disposal order (ADR 0050) is unchanged: a retired System's grants are already disposed of with it.

Not done here, on purpose:
- Telling the person that their role lapsed or came back: the spec names no such message, and the deadline reminders and Overdue notices still reach a lapsed SMO/Tech Lead by mail (ticket 37).
- Listing the automatic returns to the VA POCs: ticket 47's role-holder review reads `returned_at` and `return_trigger`.
- Immediate removal of anyone disabled at the identity provider (ac-3's second half): ticket 47.

Consequences:
- `RoleLapse` joins the classes `ArchitectureTest.onlyNamedClassesWriteRoleGrants` allows; `RoleLapses` reads the Systems through `OpenQuarters`, so the callers of `RegisterSystems.everyActive` are unchanged.
- `VaPocProperties` has a second component; `VaPocSync` and `RegisterRoles` take `RoleLapse`.
- The test reset clears the use, lapse and return of the organisation-wide grants, which outlive every test.

Amends ADR 0018 (an apply returns a lapsed grant it keeps) and ADR 0011 (a lapsed grant is now written by a job).
