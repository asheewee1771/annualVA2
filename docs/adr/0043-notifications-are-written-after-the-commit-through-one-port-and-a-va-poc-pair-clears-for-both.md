# Notifications are written after the commit through one port, and a VA POC pair clears for both

Status: accepted (items 6 and 7 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 36 (stories 92 and 69) gives every person an in-app list of their notifications and makes items for the VA POCs go to both and clear for both. It adds one module (`notification`), one migration (V27), two endpoints and one screen. Tickets 37 (mail), 38 (reminders), 39 (bounces), 40 (Exemptions) and 43 (withdrawals) send through what it builds.

1. **A module above the ones it listens to.** `sg.annualva.notification` depends on access, cycle, register, submission and web, and only `app` may depend on it (ArchUnit layer `notification`). The domain modules never call it: they publish events inside their own transaction and `WorkflowNotices` listens with `@TransactionalEventListener` (after the commit) in a `REQUIRES_NEW` transaction. So a refused or rolled-back command tells nobody, and a notification that cannot be written leaves the committed move as it is; Spring logs the failure (an event carries ids, codes and dates and no report content; the one email, a transfer's former SMO/Tech Lead, is left out of the event's `toString`). A Seam 1 test injects a failing write and sees the move committed and audited. Ticket 37's outbox adds the retry.
   - `SubmissionEvent` (ADR 0032) is the one event of the state machine. It gains `dueOn`, the last day of the window the new state waits on, read from the row by the one rule (V20 `current_window_due`) when the move publishes it, so no consumer recomputes a window. No new publishing path is added for submit, return, pass or endorse.
   - The Overdue sweep publishes an `OverdueEvent` per flag (VA Submission or Not Started System), with the state and the last day of the window that passed, which the flag statements now return (`SubmissionStore.windowDue` writes the function call once).
   - The Register apply publishes a `SystemChangeEvent` for each updated System whose Quarter changed (`MOVED`) or whose SMO/Tech Lead changed (`TRANSFERRED`, with the former SMO/Tech Lead's email, never logged or audited).

2. **The port.** `Notifications` is the one way anything tells a person something. A `Notice` holds the System, the state code, a `NoticeAction`, the due date, an app link (`Links`) and the instant, and has no field for free text, so no Finding, vulnerability or comment can reach a notification by construction (story 91). It is addressed with `toSmo` or `toCyberManager` (as the Register names them now, through `RegisterSystems.named`, which skips the access guard because the listener acts for nobody; an architecture test lets only this module call it), `to(email, ...)` for a named person, or `toVaPocs(notice, Awaits)` for the configured VA POCs. A recipient is an `app_user`: a person the Register names who has not signed in yet is pre-registered by email (`AppUserStore.known`), and their first sign-in links the same row, so the notification is waiting for them.

3. **What is sent.** Submitted: the Cyber Manager, `REVIEW`, linking the review screen. Returned for Rework (by the Cyber Manager now, a VA POC with ticket 35): the SMO/Tech Lead, `REWORK`, linking the rework queue. Passed to endorsement: both VA POCs, `ENDORSE`. Overdue: whoever's step it is, by the state flagged (Not Started, Draft and Returned for Rework the SMO/Tech Lead, `SUBMIT_OVERDUE`; In Review the Cyber Manager, `REVIEW_OVERDUE`; Awaiting Endorsement both VA POCs, `ENDORSE_OVERDUE`); the sweep flags once, so this is told once. Moved: the SMO/Tech Lead, `SYSTEM_MOVED`. Transferred: the new SMO/Tech Lead (`SYSTEM_TRANSFERRED_TO_YOU`) and the former one (`SYSTEM_TRANSFERRED_FROM_YOU`, with no due date and their inbox as the link). The state and due date of a Register change are the System's in the Cycle running today, read through `Submissions.inCycle` as the apply's caller, a VA POC. Endorsed is an FYI for the weekly digest (story 93, Release 2) and sends nothing yet.

4. **The VA POC pair** (story 69). `toVaPocs` writes one row per VA POC with a shared random `group_key` and the decision it `awaits` (`ENDORSEMENT`). A `SubmissionEvent` leaving Awaiting Endorsement (an endorsement now, a VA POC's return with ticket 35) clears every open pair of that VA Submission awaiting `ENDORSEMENT`, both rows, with `handled_by` (the actor) and `handled_at`. The list shows the handler's display name (their email when the identity provider gave none). Clearing is not reading: `read_at` stays as the reader left it. Ticket 40 adds `EXEMPTION` to `Awaits` and its CHECK, sends the request with `toVaPocs` and calls `handled` on the decision.

5. **Reading.** `GET /api/notifications` (any role) lists the caller's own rows, newest first, in pages of up to 200, joined to `va_system` for the System ID and name and to `app_user` for the handler's name; the message is the app's fixed sentence for the action. `POST /api/notifications/{id}/read` keeps the first read time; another person's row is `404`, the same as a missing one (ADR 0013). Neither is audited: they read and mark the caller's own messages, which carry no report content, as the inboxes are unaudited (ADR 0019). Writing a notification is not audited either; the move it reports is.

6. **Disputed is announced by the return** (decided 2026-10-25). The spec lists Disputed among the required messages. A Dispute is a review decision the SMO/Tech Lead cannot act on until the VA Submission is returned, and a return always attaches what is Disputed (ADR 0039), so the return's `REWORK` message ("Rework what is Disputed and submit the VA Submission again.") carries it and no notification is sent per Dispute. A separate `DISPUTED` notice at the return is a one-constant change.

7. **Only people who hold a role read the list** (decided 2026-10-25). The endpoints are open to the four roles, as the permission matrix opens every endpoint (ac-1). A former SMO/Tech Lead whom a transfer left with no System has no role, so they see `SYSTEM_TRANSFERRED_FROM_YOU` only once they hold a role again; the mail of ticket 37 reaches them meanwhile. Opening the list to any signed-in person is a one-line change to the guard.

Not done here, on purpose:
- Mail, the outbox and its retries (ticket 37); reminders before a window ends (ticket 38); bounces (ticket 39).
- Exemption requests and decisions (ticket 40) and withdrawals (ticket 43, which adds `WITHDRAWN` to `SystemChangeEvent.Change` and the SMO's notice); a Cyber Manager change, which no story asks to announce.
- An unread count in the header, and any Playwright scenario (ticket 53).

Consequences:
- A new kind of notification is a `NoticeAction` constant plus a migration widening `notification_action_check`, and a listener that runs after the commit; senders never write to the table.
- A notification names a System and a VA Submission by foreign key, so the test reset deletes notifications before them, and a later retention ticket (49) disposes of them with the Cycle.
- The listeners run in the request thread after the commit, so the response waits for them; a slow notification write slows the command's response but never undoes it.

Amends ADR 0032 item 3 and ADR 0033 (the events they publish now carry the due date; the sweep publishes one), and ADR 0018 (the apply publishes a change event for a move or a transfer).

Amended by ADR 0049: a withdrawal is heard as a `SubmissionEvent` to Withdrawn, not a `SystemChangeEvent`, and tells the SMO/Tech Lead (`WITHDRAWN`).

Amended by ADR 0052: a reminder carries the business day it is for and is written at most once per person, action, System, due date and day; `toEachVaPoc` sends a copy to each VA POC that no decision clears.
