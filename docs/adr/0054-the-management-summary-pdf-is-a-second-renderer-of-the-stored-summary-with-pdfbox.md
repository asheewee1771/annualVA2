# The management summary PDF is a second renderer of the stored summary, made with Apache PDFBox

Status: accepted (items 2 and 5 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 45 (stories 81 and 86) offers the management summary of ADR 0045 as a PDF, with its classification watermarked on every page. It adds a format, a renderer beside `ManagementSummaryXlsx`, one migration (`V35`) and one library, and no endpoint, job or table.

1. **One pipeline, a second format.** `POST /api/exports` takes `format` `PDF` as well as `XLSX`; everything else is ADR 0045 unchanged: the same role, step-up intent (`export-mgmt-summary`), checks, Classification rule, summary read with the caller's access at request time and stored as JSON, export job, 24 hours, requester-only status and download, and audit entries (whose `format` detail is now `PDF` or `XLSX`). The export job picks the renderer by the stored format (`ManagementSummaryPdf.render` or `ManagementSummaryXlsx.render`) from the same `ManagementSummary`. The download is `application/pdf`, named `management-summary-2027.pdf` (or `-q3.pdf`), with the same attachment, `nosniff`, sandbox and `no-store` headers. `V35` widens `export_request_format_check` to `('XLSX', 'PDF')`.

2. **The library: Apache PDFBox 3.0.8, pinned.** *Decided 2026-10-25 (docs/agents/reviewer-decisions.md).* The implementation plan named OpenPDF for a PDF ADR that was never written (ADR 0016 went to the Register template, so the ticket's "PDF library chosen in ADR 0016" points at nothing). PDFBox is chosen instead: it is an Apache Software Foundation project under the Apache License 2.0 (OpenPDF is LGPL 2.1 or MPL 2.0, which are not permissive), maintained since 2008, and the same library reads a PDF back, so the tests extract the text of the file the API serves without a second dependency. Its cost is that it has no table layout: `ClassifiedPdf` (about 330 lines) lays out lines of text and tables whose cells wrap. An architecture test keeps PDFBox (and FontBox) inside the `export` module, so a PDF someone uploads as supporting evidence is still never parsed (ADR 0026).

3. **The same content, in the same tables.** `SummaryText` turns the stored summary into its title, its date line and two `ExportTable`s, `Summary` and `Systems`: named columns in order (Endorsed Late after Endorsed, Withdrawn never counted), each with a width, and rows of cells that are either a text or a count. Each renderer walks a table with one loop: the workbook writes a count as a number and a text as a string cell, the PDF writes each as it reads, and shares the page's width out in the columns' proportions. So the two formats cannot disagree about a column, its place or its value. The PDF is A4 landscape: the title and the "As at" date, the Summary table of counts by Quarter, then the Systems table, one row per System. A table starts on a new page unless its name, header row and first row fit, and its header row is repeated on each page it runs onto. Every cell is text from the stored summary (counts, System IDs and names, SMO/Tech Lead emails, states and flags); nothing from a Finding is in it, so none can be written. The test extracts every page's text and checks for the Findings' texts as the workbook test does.

4. **Classification on every page (story 86, A-1).** Each page carries the label (`Confidential` or `Restricted / Sensitive-Normal`, as stored on the export) centred in its header, centred in its footer beside "Page n of N", as the first line of its content (as each sheet's first row does in the workbook), and once as a watermark: bold Helvetica in grey at 15 % opacity, corner to corner along the page's diagonal, sized to 70 % of it (at most 96 points). The watermark is drawn after the content, over it, so no table can cover it, and its opacity keeps the content legible. The tests check, page by page, the header and footer text, the first content line, a slanted run of text equal to the label, a graphics state with an opacity below 1, and that no upright character is drawn over another or into the side margins.

5. **Helvetica, not embedded; a character it cannot draw is `?`.** *Decided 2026-10-25 (docs/agents/reviewer-decisions.md).* The PDF names the standard Helvetica, which every reader has, and embeds no font, so the file is small and carries no font program. Helvetica draws Windows-1252 (Latin letters with their accents, and common punctuation). A System name may hold any letter (`RegisterText`), so a name in Chinese or Tamil script would show as `?` in the PDF, one per character; the Excel workbook keeps it as typed. Without this the export of a whole Cycle would fail for one such name. The other option is to embed a Unicode font (Noto Sans, SIL Open Font License, with its Chinese and Tamil companions: several megabytes in the jar, and subset into each file), which is the change to make if the Register holds such names.

Consequences:
- The export module may now depend on `org.apache.pdfbox`; no other module may (`ModuleConventionsArchTest`).
- A later export type (the Cyber Manager's detailed export, the auditor pack) that needs a PDF builds its own `ExportTable`s and hands them to `ClassifiedPdf` for its pages and classification; the same tables make its workbook.
- A single row taller than a page's content area (about 60 wrapped lines) would run into the footer; no row of the management summary comes near it (a System name is at most 200 characters).
- The screen asks for "Excel workbook" or "PDF, watermarked on every page" and lists each export with its format.

Amends ADR 0045 (item 1: `format` is `XLSX` or `PDF`; "Not done here": the PDF is done).
