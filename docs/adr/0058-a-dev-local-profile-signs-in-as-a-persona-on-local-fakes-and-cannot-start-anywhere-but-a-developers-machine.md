# A dev-local profile signs in as a persona on local fakes and cannot start anywhere but a developer's machine

Status: accepted (the profile and its guards decided 2026-10-27, docs/agents/reviewer-decisions.md; items 6 to 8 are provisional)

Ticket 63. The app cannot be signed in to or exercised in a browser without the private `mock-m-sso` stack (ADR 0003, ticket 01 is `ready-for-human`), and its file store, scanner, mail relay and account status are fail-closed stubs until ticket 51, so even with that stack an upload is refused. The `dev-local` profile lets one machine with only PostgreSQL run a whole VA Submission: a page lists the six dev personas and signs in as the one picked, and local fakes stand in for the four boundary adapters. It adds no migration and no table. A profile that lets anyone sign in as anyone is a hazard if it ever runs elsewhere, so most of this record is about making that impossible.

1. **Sign-in reaches the same code as a real sign-in.** `POST /api/dev/sign-in` with `{"persona": "<afcas.uuid>"}` builds the identity the single sign-on would have asserted (the persona's uuid, no email, an `auth_time` of now) and calls `SignInService.signIn`, so the sign-in rules (email from the dev identities, the linking of person to user, the account-status check) are the one copy. It runs as a filter in the one security filter chain, added when the chain is configured so that it takes the chain's own `SessionAuthenticationStrategy`: the session id rotates, the person's older session ends (one session per person), and `SignInSuccessHandler.establish` (now shared with the OIDC callback) writes the session, its limit stamps and the `SIGN_IN` audit entry. The anonymous-session cap, the idle and absolute limits, the CSRF rule and sign-out are the chain's, untouched. The way a sign-in starts became one seam, `SignInMethod`: `OidcLogin` (every profile but `dev-local`) and `DevLocalSignIn`.

2. **No identity-provider client exists under `dev-local`.** `MccClientConfig`, `MccHttp`, `MccIdentityProvider`, `JwksController`, `MccSsoProperties`, `OidcLogin`, `OidcSignInUserService`, `StepUpAuthenticationProvider` and the single sign-on `StepUpController` are `@Profile("!dev-local")`, so no client registration is built, nothing is discovered at startup, and the `annualva.mcc.*` settings are not needed. `StepUp` takes the authorization-request resolver through an `ObjectProvider`, since it is used only by the OIDC round trip. A test asserts there is no `ClientRegistrationRepository`.

3. **Roles are never granted by the page.** The sign-in body names a persona and nothing else (an extra `roles` or `email` field is ignored, and a test proves it). A persona's role is what the System Register says about its email, as for anyone: a persona the Register does not name sees empty screens. The VA POC personas hold `VA_POC` because `annualva.va-pocs` names them, as under `dev-mcc`. The SMO and Cyber Manager personas get theirs from a Register a VA POC persona uploads and applies; `scripts/dev-data/system-register.sample.xlsx` and `load-register.sh` do exactly that through the real endpoints, and a test (`DevDataSampleTest`) proves each persona then holds the role its label says. No class that writes `role_grant` was added (the architecture rule `onlyNamedClassesWriteRoleGrants` still holds), and no endpoint reaches it.

4. **Step-up keeps its meaning.** A sensitive command still calls `StepUp.require`, refused with `403 step-up-required` unless the session's `auth_time` is within the freshness window. The path the SPA follows, `GET /auth/step-up?intent=...&returnTo=...`, is the dev-local controller's: it remembers the intent, the person and the instant in the session and redirects to the front end's `/dev-step-up`. `POST /api/dev/step-up` with the intent completes it only for the same person, the same intent, once, and within the freshness window of starting it, and then does what the identity provider's fresh sign-in does through the same `StepUpSuccessHandler`: moves `auth_time` to now and nothing else (`absoluteExpiresAt` is unchanged). A confirmation that matches no started step-up changes nothing, answers `409 step-up-not-started` and is audited `STEP_UP_FAILED` with a fixed reason (`not-started`, `intent-mismatch`, `expired`); starting and completing are audited `STEP_UP_STARTED` and `STEP_UP_OK`, as for the single sign-on. The confirmation is a button, not a second factor: with no identity provider there is none to ask.

5. **Local fakes in `sg.annualva.adapters.local`** (the adapters layer, which nothing imports; no class name contains `Fake` or `InMemory`, which the architecture rule keeps off main). `LocalFileStore` keeps each zone in a sub-folder of `annualva.dev-local.file-store-dir` (default `.dev-local/files`, so `backend/.dev-local/`, git-ignored), so a restart keeps the files; it refuses a key that could name a place outside the zone. `LocalMalwareScanner` follows mock-SFS's keyword rule on the display name, case-insensitively (`quarantined` blocked, `sanitized` clean only after a change, which the application rejects, anything else unchanged) and finishes after `annualva.dev-local.scan-delay` (default 1 s); its ticket carries the decision and the instant it is ready, so it keeps no state and a scan under way at a restart still finishes. `LocalMailRelay` writes one `Event=email` log line per message with the template and the System, state, action, due date, link and change kind, never the address or any other value, and refuses an address whose local part ends in `.bounce` so SMO Unreachable can be shown. `LocalIdentityStatus` reports everyone enabled. The four `Unwired*` stubs are `@Profile("!dev-local")`, so each port has exactly one bean under `dev-local`; under `ci` the local fakes do not exist and the Seam 1 harness fakes stay the only ones.

6. **Guards, because it must be impossible outside a developer's machine.**
   - `DevLocalGuard` is a bean that fails the context unless: no other profile is active (an allow-list of one, not a deny-list of `sit` and `ci`, so a production profile with any name cannot be combined with it); `server.address` is set to a loopback address (an unset address listens on every interface, so it is refused, and a name other than `localhost` is refused unresolved); and the database is on this machine (a `JdbcConnectionDetails` host of `localhost` or a loopback address). The last is beyond the ticket's two guards: `application-dev-local.yml` supplies local defaults for every value the base file requires from the environment, so without it a stray `SPRING_PROFILES_ACTIVE=dev-local` next to a production database URL would start. It warns at startup that anyone who can reach the application can sign in as any persona.
   - `application-dev-local.yml` binds the server to `127.0.0.1`.
   - Every top-level class of the persona sign-in (`DevLocal*` in `access`) and of the local adapters is `@Profile("dev-local")`, and nothing outside them may depend on one: `DevLocalArchTest` fails the build otherwise.
   - Outside the profile the two public endpoints have no handler and answer `404`: `/api/dev/personas` and `/api/dev/sign-in` are on `SecurityConfig.PUBLIC_PATHS` for every profile, like `/login`, so the answer is the same for a signed-in and a signed-out caller and no session is made. `DevLocalAbsentTest` proves it under `ci`.
   - A guard cannot stop someone who edits the code, and a sidecar proxy on the same host reaches a loopback address; the profile is for a developer's laptop and is not a control against a hostile deployer.

7. **The calendar goes live earlier under `dev-local`** (provisional). The base `annualva.calendar.first-live-cycle` and `first-live-quarter` are 2027 and 3 (go-live in August 2027), so before then every Quarter is handled outside the app and no VA Submission can be started on a developer's machine. `dev-local` sets 2026 and 3, which keeps a VA Cycle running whatever day it is run. The alternative is a clock override (`annualva.dev-local.today`), which would let a developer walk the windows but changes how every module reads time; not built.

8. **The front end** (`/dev-sign-in`, `/dev-step-up`). The signed-out screen offers the picker only when `GET /api/dev/personas` answers 200. The picker shows each persona as a button (name, role label, email as text) under a banner that says this is local development sign-in and not the single sign-on; the classification banner stays. The confirmation page says the same and offers one button. No raw HTML is rendered.

Not done here, on purpose:
- A fake clock for dev-local (item 7), a persona created from the page, or a role picker: roles come only from the Register.
- Encryption of the local files: mock data on one machine.
- The real adapters (ticket 51) and the `mock-m-sso` path, which stay as they are under `dev-mcc`.
