# The VA POC's board is the Quarter board for the endorse scope, and the Cycle matrix reads the same rows

Status: accepted (items 3, 4 and 5 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 33 (story 64) gives the VA POC two tabs: a Quarter board of every System and a matrix of the whole VA Cycle (a strip of the four Quarters, then one row per System with its milestones against the day each is due). Both are read models in the `dashboard` module over the one dashboard reader, `DashboardSystems.in(cycle, need)` (ADR 0034 item 1), read for `Need.ENDORSE`, whose scope is every System. Neither is a copy of the Cyber Manager's reads, so the board, the matrix and the inboxes cannot disagree about a System's state, its due dates or its Overdue flag. Six decisions follow.

1. **One board, two scopes.** `GET /api/dashboards/quarter-board` is open to `CYBER_MANAGER` and `VA_POC`. `QuarterBoard` asks the access guard whether the caller has the endorse scope (`AccessGuard.scope(Need.ENDORSE).all()`, which only a VA POC has) and reads `Need.ENDORSE` if so, `Need.REVIEW` otherwise. Columns, the default Quarter and the Handled-outside list are unchanged (ADR 0034 item 5).
2. **The matrix is VA POC only.** `GET /api/dashboards/cycle-matrix?cycle=` is `hasRole('VA_POC')`: an SMO/Tech Lead, a Cyber Manager, an Auditor or a person with no role gets 403, no session 401, and a Cycle the app does not run 404 (`CycleCalendar.running`, as for the inboxes). It answers `cycle`, four `quarters`, `systems` and `handledOutsideApp`. Neither read is audited: states, dates and counts only (ADR 0019).
3. **The strip counts what the app runs, by state.** Each Quarter has its dates, a `phase` on today's business date (`HANDLED_OUTSIDE_APP` before the first live Quarter, else `CLOSED` once its last day has passed, `CURRENT` while today falls in it, `UPCOMING` before), `counts` for every state but Withdrawn (zeros included, Not Started counted), `total` and `endorsedLate` (Endorsed with the stored `endorsed_late` flag). Withdrawn VA Submissions and Quarters Handled outside the app are left out of the counts (spec, glossary "Withdrawn" and "First live Quarter"); the Systems of a Quarter Handled outside the app are listed under `handledOutsideApp`, as on every dashboard. *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* a Withdrawn VA Submission still has a row in `systems` (read-only, shown, not counted); today none appears, because the Register scope does not list retired Systems (ADR 0034, consequences) until ticket 43.
4. **Three milestones, each with its due day, the day it was reached and whether the state waits on it.** `submitted` is due on `submit_due`, `reviewed` on `review_due`, `endorsed` on `endorse_due` (the windows the VA Submission keeps, or its Quarter's for Not Started). `doneOn` is the business date (Asia/Singapore, `CycleCalendar.dateOf`) of `submitted_at` (written by submit, V19), `passed_to_endorsement_at` and `endorsed_at`. `current` is true for the milestone whose due day is the row's `dueOn`, the day the one window rule (`current_window_due`, ADR 0033 item 2) says the state waits on, so the matrix never writes the state-to-window mapping again (the three due days always differ, `va_submission_windows_check`, and a Quarter's do too): Not Started and Draft wait on submitted, In Review and Returned for Rework on reviewed, Awaiting Endorsement on endorsed, a final or frozen state on none. The row's `overdue` flag says whether that window has passed. *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* "reviewed" is the Cyber Manager passing the VA Submission to endorsement, the step that ends the review.
5. **Two new columns, written by the commands that reach them.** Migration `V133` adds `va_submission.passed_to_endorsement_at` and `endorsed_at` (`timestamptz`, null until reached), with `IF NOT EXISTS` so a ticket that adds the same column does not fail. The pass-to-endorsement command (ticket 30) and the endorse command (ticket 34) must write them, with the latter's `endorsed_late`; until then they stay null and the matrix shows those milestones as not reached. Each holds the last time the milestone was reached. *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* whether a VA POC return (ticket 35) clears `passed_to_endorsement_at` is that ticket's decision; this read shows what is stored. Ticket 35 keeps it (ADR 0047 item 4).
6. **A VA POC's board marks no segregation-of-duties conflict yet.** The board's `confirmed` and `awaitingReview` counts are the same for both roles. `sodConflict` is the review step's marker for a Cyber Manager (ADR 0035); for a VA POC it is false, because no endorsing step is recorded and `Submissions.conflictedAt` refuses a scope over every System until one is decided (ticket 30 or 34). `ReviewMarkers.of(rows, need)` takes the need the dashboard reads for, and `SubmissionStep.actingFor(need)` names the step it acts at: none for `ENDORSE` today, so the marker lights by itself once ticket 34 adds the endorsing step. A person who is both a VA POC and a Cyber Manager gets the VA POC's board, which holds their own Systems too.

Consequences: the strip, the board and the inboxes share one reader and one window rule; `Submissions.Summary` now carries `endorsedLate` and the milestone instants (`Submissions.Milestones`) for any dashboard; the board's component and its flags moved to the shared screens, used by both roles; the management summary (ticket 44) can count from the same reader.

Amends ADR 0034 (item 1: the board is open to `VA_POC` with the endorse scope).
