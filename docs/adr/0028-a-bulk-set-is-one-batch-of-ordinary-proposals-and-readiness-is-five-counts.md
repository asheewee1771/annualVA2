# A Bulk-set is one batch of ordinary proposals, and readiness is five counts

Status: accepted

Ticket 20 (stories 36, 37 and 38) lets the SMO/Tech Lead work through 100 to 200 Findings: filter chips, tick boxes with a select-all, a sticky bulk bar that applies one Finding Status to every ticked Finding, and a progress bar. It adds one migration (V15), two endpoints and no module; the code is in `finding`. The Cyber Manager's review of a batch is ticket 29; carry-over and Target Date Missed are Release 2.

1. **A Bulk-set is one batch and one ordinary proposal per Finding.** `POST /api/submissions/{id}/findings/bulk-proposals` takes `findingIds` and one status with its fields, in exactly the body of a single proposal (ADR 0027). It writes one `bulk_batch` row (the VA Submission, who and when) and, for each Finding, a `finding_status_proposal` row that carries `batch_id`; each becomes its Finding's current proposal with the review state back to `PENDING`, as a single proposal does. Both endpoints run the same steps in one package-private component, `Proposals`: `target` (ownership and state, with the refusal's own audit entry and the 409), `fields` (`ProposalFields.parse` and the memo check), `lock` and `write` (one `INSERT ... SELECT FROM unnest` with `batch_id` NULL for a single proposal, one `SET_CURRENT` keyed by the new proposals' ids, and the `STATUS_PROPOSED` entries). A proposal for one Finding is a batch of one with no batch row, so each rule, statement and audit entry exists once, and everything ticket 19 guarantees for a proposal (the fields of its status and no others, the cleaned and bounded texts, the history kept, a confirmed review reset) holds for every member by construction, and ticket 29 finds a batch's members by `batch_id` and the ones changed since by `current_proposal_id`. What was proposed is on the proposals and is not repeated on the batch. The answer is 201 with `batchId` and `count`; there is no batch resource to point a `Location` at until ticket 29. Each proposal now shows its `batchId` (null for a single one), and the row says "Bulk-set".
2. **A batch is history too.** `bulk_batch` has the same per-statement append-only trigger as the proposals (V14) and the audit log (V5). Ticket 49 replaces it with the proposals' trigger, deleting the proposals before the batches.
3. **The list of Findings is refused as a whole.** The checks run in the order ownership (a VA Submission of a System the caller is not SMO/Tech Lead of is 404, the same as one that does not exist, ADR 0013), the state (Draft or Returned for Rework, else 409 `invalid-transition`, audited as its own `BATCH_PROPOSED` REFUSED entry with `reason=state-not-editable`, ADR 0014), `findingIds`, the status and its fields (ADR 0027's order), the memo, and last that every Finding named belongs to this VA Submission. `findingIds` must be present, hold 1 to 1000 ids, each an id and none twice; any of those, and a list that names a Finding of another VA Submission or one that does not exist, is a 400 `invalid-field` naming `findingIds`. The sentence never says which id, and the same sentence covers a Finding that does not exist and one of another System, so nothing about another System is learned. Nothing is written for a 400, and a 400 is not audited. "Not editable" is the VA Submission's state: in Release 1 every Finding of an editable VA Submission may be proposed again, confirmed or not (ADR 0027 item 2).
4. **At most 1000 Findings in one batch.** The bound keeps the request and the lock set bounded (as-1); a screen holds 100 to 200 Findings. It is a constant (`BulkProposals.MAX_FINDINGS`, and `MAX_BATCH_SIZE` on the screen, which says so and disables Apply). The proposals are written with one statement over an array of ids, and the rows are locked in id order with one `SELECT ... FOR UPDATE` that a single proposal uses too, so two writes over the same Findings wait for each other instead of deadlocking and a single proposal lands before or after a batch, never in between. The lock is taken once the checks have passed, for a single proposal as for a batch; this replaces ADR 0027 item 2's "the Finding's row is locked first", with the same effect that the last proposal to commit is the current one.
5. **One audit entry for the batch and one per Finding.** `BATCH_PROPOSED` is about the System and the VA Submission, with `batch_id`, `count`, `finding_status` and the memo's `file_id` when there is one. Each Finding of the batch also gets the `STATUS_PROPOSED` entry a single proposal writes, about the System, the VA Submission and the Finding, with `finding_status`, `batch_id` and the memo's `file_id`, so the audit trail of a Finding shows a proposal made in a batch as well (reviewer decisions, 2026-10-17). Never any text. `batch_id` was already on the detail allow-list (V5, V14), so V15 changes no audit constraint.
6. **Readiness is five counts and two zeros.** `GET /api/submissions/{id}/readiness` answers `total` (every Finding), `proposed` (with a current proposal, whatever its review), `unproposed` (no proposal yet: what is still to do), `awaitingReview` (review state `PENDING`: awaiting the Cyber Manager), `disputed`, and `carriedOver` and `targetDateMissed`, which are 0 until Release 2 adds their columns. No field is called `pending`, because the word could mean either of the two (reviewer decisions, 2026-10-17); the screen shows the server's counts and computes none. Ticket 23 adds the file-age checks to the same read. It is for anyone who may see the System and, as counts with no content, follows the rule for reading the VA Submission itself (reviewer decisions, 2026-10-13): a Cyber Manager's or a VA POC's read is a `READINESS_VIEWED` entry with ids only, and the owner's reads, which the screen repeats after every proposal, are not recorded.
7. **The chips are the list's filters.** Needs attention is `needsAttention=true`, All is no filter, Disputed is `reviewState=DISPUTED` and Critical/High is `severity=CRITICAL,HIGH`, all from ADR 0027 item 9, so the total and the pages are of the narrowed list. The screen opens on Needs attention. Carried Over and Target Date Missed chips arrive with Release 2.
8. **The screen.** A tick box on every row and one in the header for the page; "Select all N Findings that match" reads the ids of the whole chip page by page (pages of 500) and stops past 1000. The selection is kept across pages of one chip and cleared when the chip changes or a batch is applied. A page past the end of a list that shrank (Needs attention shrinks with every proposal) moves to the last page there is, and the focus goes to the Findings heading after a batch is applied; the page's tick box shows a partly ticked page as indeterminate. The bulk bar sticks to the bottom of the view while anything is ticked: the count, one status, the fields that status requires (each with its classification label, through the same input as a row), Apply and Clear selection; it shows the server's problem and marks the field it names. The progress bar is a `<progress>` with its counts in words in a polite live region (`aria-live`), and both the list and the counts are read again after every proposal. Report content stays text (the no-raw-HTML gate).

Not done here, on purpose: the review of a batch (ticket 29), carry-over and Target Date Missed (Release 2), the submit rule "every Finding has a status" (ticket 25) and any Playwright scenario (ticket 53).

Amended by ADR 0029: the scan job's settlement of a parsed file also locks every existing Finding it will write with one `SELECT ... FOR UPDATE` in id order before it writes, so the settlement, a proposal and a Bulk-set all take their locks once and in the same order.

Amended by ADR 0029: `Proposals.write` takes an explicit proposer (the caller, or a rescan made for its uploader), so a rescan's Remediated proposals use the same write and the same audit builder, and every `STATUS_PROPOSED` entry carries `proposed_as`.

Amended by ADR 0031: the readiness read also names, by `fileId`, `name` and `reportType`, the report files more than 90 days old at today's business date (`tooOld`) and those with no scan date to judge (`undated`).

Amended by ADR 0032: the readiness read also lists `blockers`, every reason the VA Submission cannot be submitted apart from the Declaration, which the submit refuses with too.

Amended by ADR 0049: the batches' append-only trigger lets a DELETE through only inside the executor's transaction for an approved disposal list, after the proposals that name them.
