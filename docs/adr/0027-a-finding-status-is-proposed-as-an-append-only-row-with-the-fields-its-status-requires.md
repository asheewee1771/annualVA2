# A Finding Status is proposed as an append-only row with the fields its status requires

Status: accepted

Ticket 19 (stories 28 and 35) lets the SMO/Tech Lead of a System propose one of four Finding Statuses for each Finding and gives every reader the Findings with the filters the prepare screen needs. It adds one migration (V14), no module (the code is in `finding`, which now also reads the business date from `cycle`) and no new upload path. Confirming and Disputing (the review engine, tickets 28 and after), bulk proposals (ticket 20), carry-over and the Risk Accepted expiry are later tickets and are not built here.

1. **A proposal is a row that is never changed or removed.** `finding_status_proposal` holds one proposal: the status, the fields of that status, who proposed it (an id) and when (UTC). A database trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` for every connection, per statement, exactly as for `audit_entry` (V5); ticket 49's retention replaces it by a later migration. The history is what a Cyber Manager and an Auditor read later, so it must not depend on application code behaving. `GET /api/findings/{id}/proposals` returns the history, latest first, to anyone who may see the System; a read is audited for every role (`FINDING_PROPOSALS_VIEWED`, with the count), because the texts are what a person wrote. A test goes under the HTTP API to prove the trigger, as the audit test does.
2. **The Finding points at its latest proposal, and a new one resets the review.** `finding.current_proposal_id` is the latest row and `finding.review_state` is `PENDING`, `CONFIRMED` or `DISPUTED`. A check ties them: a Finding has both or neither, so one with no proposal has no review state (it is not "pending" a review of something that does not exist). A proposal sets the state to `PENDING` in the same transaction that writes it, so "confirmed holds only while the confirmed proposal is the current one" (plan, 2.4) is true by construction, whatever the review engine does later. The Finding's row is locked (`SELECT ... FOR UPDATE`) first, so two proposals for one Finding are written in turn and the last one to commit is the current one.
3. **Each status has its fields, and no row can hold another set.** Remediated: `evidence`. False Positive: `justification`. Risk Accepted: `reason`, `approverName` and `approverRole` (free text: the risk owner is usually outside the app) and an optional approval memo. Remediation Planned: `plan` and `targetDate`. `finding_status_proposal_fields_check` requires exactly those and nulls for the rest, and the text lengths are checked (1 to 4000 characters, names and roles 1 to 200), so a row that is wrong is refused by the table whatever wrote it. `ProposalFields` reads the request first and answers the person; the checks are the backstop.
4. **A wrong field is a 400 `invalid-field` that names it.** The body is read as text per field so one unreadable field is named instead of failing the whole body. The problem carries `field` (one of the source's own names: `status`, `evidence`, `justification`, `reason`, `approverName`, `approverRole`, `approvalMemoFileId`, `plan`, `targetDate`) and a sentence built from constants; nothing the person typed is echoed (as-13). The checks run in a fixed field order, so the first problem is always the same. A field the status does not use is refused too, rather than dropped silently, so a client that sends a plan with Remediated is told. An unknown status, a missing one or a malformed body is 400 as well.
5. **Free text is limited and cleaned by the one rule the report parsers use (IM8 as-1).** A long text is at most 4000 characters and an approver name or role 200, counted in code points. Before it is measured or kept, it goes through `parser.ReportText` (`cleanLongText` and `cleanOneLine`), the same character rule that cleans every text read from a report, so there is one list to tighten and not two. It removes every control character, every formatting character (the direction overrides and isolates, Unicode tag characters, the word joiner and invisible operators, the soft hyphen, the zero-width space, the byte order mark), the line and paragraph separators, every private-use and unassigned code point and any lone surrogate (the database could not store it), and trims the result. The only difference between the two entry points is a new line or a tab: a long text keeps them (the plan's "control chars stripped" does not mean a plan must be one line) and a name or role turns them into a space. A text that is empty after cleaning is a missing field. Every free-text input on the screen carries the classification label beside it (IM8 dp-8), through the same `ClassifiedField` the upload controls use, and the length limits are on the inputs. The front end does not mirror the character rule: it only sets `maxLength`, and the server decides what is kept.
6. **The target date is after today in Singapore, and no further than ten years ahead.** "A future target date" is judged against the business date (`Asia/Singapore`, ADR 0006) read through the `CycleCalendar` (so through the `Clock` bean): a date that is today in Singapore is not in the future, even where it is still yesterday in UTC. The ten-year bound is not a business rule: it keeps a date a real one (as-1) and the database's `date` type safe from `9999-12-31` and the like. It is a constant (`ProposalFields.MAX_YEARS_AHEAD`). `finding` may now depend on `cycle` (the architecture test says so).
7. **The approval memo is an ordinary evidence file, linked by id.** ADR 0026 said what the memo needs: a link from the proposal to a file of kind `EVIDENCE` in the same VA Submission, and no second upload, store or download. `approval_memo_file_id` is that link (a foreign key to `report_file`), and the proposal is refused with 400 naming `approvalMemoFileId` unless the file belongs to this VA Submission, is of kind `EVIDENCE` and is `READY` (it has passed the scan and the type check); a file still being scanned, a rejected one, a machine-readable report, another VA Submission's file and one that does not exist are all the same answer, so the check never says which. The memo is uploaded under any Scan Report with `POST /api/submissions/{id}/files`, `kind=EVIDENCE`, so it counts against that Scan Report's evidence cap of 20 files, and it has no `kind` of its own; it is downloaded through `GET .../files/{fileId}/content`, with every guarantee of ADR 0026 (attachment, never rendered, audited). Only a Risk Accepted proposal may carry one. One memo may be linked from several proposals (the approval may cover several Findings). The `finding` module reads `report_file` with one count query in its own store, as its list already joins it for the source files; it does not depend on `ingestion`.
8. **Who and when.** `POST /api/findings/{id}/proposals` is for the SMO/Tech Lead of the Finding's System: a Cyber Manager, a VA POC who is not its SMO and an Auditor are refused with 403 by the role rule, an SMO of another System and a Finding that does not exist are the same 404 (ADR 0013), and the VA Submission must be in Draft or Returned for Rework (the same states that take files; the check is `Submissions.fileTarget`'s), else 409 `invalid-transition`. The checks run in the order ownership, state, fields. The refusal for the state is audited in an entry of its own, written before the transaction rolls back (ADR 0014); a 400 for a field is not audited, as no other 400 is. A proposal is a `STATUS_PROPOSED` entry about the System, the VA Submission and the Finding, with `finding_status` (one of four fixed codes) and, when there is one, the memo's `file_id`: never the evidence, justification, reason, approver, plan or date (V14 adds `finding_status` to the detail allow-list). A proposal is answered 201 with the row; the Finding's own `proposals` address is its `Location`.
9. **The list gains filters and the proposal.** `GET /api/submissions/{id}/findings` takes `reportType`, `severity` (repeated or comma-separated, so a "Critical/High" chip later needs no new parameter), `reviewState` and `needsAttention`, alone or together; the total is the number that match, and a value that is not one of the choices is a 400. `needsAttention` is a Finding with no proposal yet or a Disputed one (what the SMO/Tech Lead still has to act on; Carried Over and Target Date Missed join it in Release 2). Each Finding now carries `reviewState` and `currentProposal` (the whole proposal, with its texts). The list was audited for every role already, with a count; a filtered read is one entry with the number returned, and the proposals' texts, like the Finding's, never reach a log, an audit entry or an error body (tests put a sentinel in every field and in every refusal and find it in none).
10. **The screen.** The prepare screen's Findings section is a spreadsheet-style table, the most severe first and 100 to a page: severity, the identifier (with Tentative and "check did not complete" flags), package or rule, Scan Report, places, the status proposed so far with its review state and what was proposed, and a select of the four statuses that opens the fields the chosen one requires beneath the row, each with its classification label, and the approval memo chosen among the READY evidence files. It is shown as text only (the no-raw-HTML gate), asked for again when a file has been read into Findings, and shows the server's problem, marking the field it names. The filter chips, tick boxes, the bulk bar and the progress bar are ticket 20's.

Not done here, on purpose: the review (confirm, Dispute), bulk-set, carry-over, Target Date Missed and the Risk Accepted expiry, a manual Finding, the submit rule "every Finding has a status", and any Playwright scenario (ticket 58). The `proposed_as` and `batch_id` columns of the plan's data model arrive with the tickets that write them.

Amended by ADR 0029: a proposal records who made it (`proposed_as`: `SMO`, or `RESCAN` for the Remediated proposal a rescan makes for a Finding it reports nowhere), and each proposal shows `proposedAs`.
