# A report file is deleted softly, and a Finding goes only if it never had a proposal

Status: accepted (ticket 60; the user's decisions of 2026-11-22 settle item 3, on the ticket's HITL 2 comment, item 4, docs/agents/reviewer-decisions.md "Ticket 60: a Manually Entered Finding that has had a proposal is not deleted", the hard delete of items 3 and 4, "Ticket 60: a Finding that never had a proposal is hard-deleted, an exception to the soft-delete rule", and items 1 and 5 on a rescan and the file it replaced, "Ticket 60: a parsed rescan and then the file it replaced can both be deleted")

Ticket 60 (stories 23 and 39, raised by the ticket 22 decision of 2026-10-18, "A Scan Report's mode is fixed once it holds anything") lets the SMO/Tech Lead undo a mistake on a Scan Report while the VA Submission is in Draft or Returned for Rework: delete a report file uploaded by mistake, or a Manually Entered Finding entered by mistake. It adds two endpoints, one migration (V47) and no module: the request for a file is `ingestion`'s, what it does to the Findings is `finding`'s.

1. **`DELETE /api/submissions/{id}/files/{fileId}`** (the SMO/Tech Lead of the System) answers 204. Checks run in the order the file (one that is not of this VA Submission, or is deleted already, is 404), ownership (another SMO's VA Submission is the same 404, ADR 0013), the state (Draft or Returned for Rework, else 409 `invalid-transition`, audited `REFUSED` with `reason` `state-not-editable`; the same row lock as every edit, ADR 0032), then, in the one statement that marks it, that it is a report file (`kind` MACHINE_READABLE) that no live rescan supersedes (409 `file-not-deletable`, audited with `reason` `not-deletable`; the reason is read from the row after the statement, so a deletion of the same file that committed first answers the same 404 as a later request). Any status is deleted: on its way through the checks, rejected, or parsed, a parsed rescan included. *Decided by the user on 2026-11-22 (docs/agents/reviewer-decisions.md, "Ticket 60: a parsed rescan and then the file it replaced can both be deleted"), in their words: "Allow deleting a parsed rescan, and then allow deleting the file it superseded too, so the Scan Report can be emptied."* So a parsed rescan is deleted by the ordinary rules (its places go, its Findings are re-rated, one that never had a proposal is removed, and otherwise it gets a Remediated `FILE_DELETED` proposal), and once it is gone the file it superseded can be deleted too. That file stays superseded (its Findings are not restored: undoing a rescan stays out of scope); it is a file a rescan replaced, which is not deletable, only while that rescan is not deleted. Supporting evidence is not a report file and is not deleted here (a later ticket can add it; an approval memo or an Exemption's evidence names it). A Cyber Manager, a VA POC who is not the System's SMO and an Auditor are 403 by the role rule.

2. **The file is a soft delete.** The spec allows only a soft delete before retention ends ("every other removal before retention ends is a soft-delete"; ADR 0050 item 8), so V47 adds `report_file.deleted_at` and `deleted_by`. The row, its hashes and its content stay until its VA Cycle is disposed of, which deletes them with the rest of the VA Submission's files (ADR 0050): that is "what a deleted record leaves behind", and the retention rules of ticket 49 cover it unchanged. Nothing lists, reads, downloads, counts (the 20 files, a mode change, the submit and age rules) or confirms a deleted file; the one statement that marks it (`ReportFileStore.DELETE`) also checks, with the row held, the kind and that no live rescan supersedes it, so a settlement that lands while the deletion waits is seen. The rescan it reads is another row: one whose deletion has not committed yet still counts as live, so a race between deleting a rescan and deleting the file it replaced ends in a refusal, never in a file superseded by a rescan that is still there. Lock order: the deletion holds the VA Submission shared, then the file's row, then the settlement lock and the Findings in id order; a settlement takes its file's row, then (a rescan) the replaced file's row, then the settlement lock and the Findings; a replace holds the VA Submission and the Scan Report shared, inserts the rescan (where a live rescan of the same file is refused by the one-live-rescan index, `replace-in-progress`), and only then takes the replaced file's row. No one waits for a file row while it holds the settlement lock, and the replace takes no file row before its insert, so it never holds the replaced file while waiting on another rescan's index entry (that rescan's settlement holds the rescan and waits for the replaced file); so they cannot deadlock, and the one that goes second re-reads the row the first wrote: a deletion that waited for a rescan superseding its file is refused, and a rescan whose file was deleted while it waited settles as an ordinary upload. A file deleted while it is still being checked is never sent to the scanner again and its verdict is never settled: every write of the scan job is guarded by `deleted_at IS NULL` as well as the status and attempts it read, and its unscanned bytes are swept like a settled file's (V47 lets a deleted file in quarantine forget its key). A deleted rescan is no longer live, so V47 recreates the one-live-rescan index without it and the file can be replaced again. A rescan whose replaced file was deleted while it was checked has nothing to replace: its settlement keeps it as an ordinary upload (no supersede, no `FILE_REPLACED`) and clears its `replaces_id`, so it no longer names a file it does not replace. A rescan is kept for a file only while that file is held and is still parsed, not superseded and not deleted (`ReportFiles.keep` re-checks it with the row held, `ReportFileStore.LOCK_REPLACEABLE`, right after the insert): otherwise, after a rescan of it superseded it and was deleted, which frees the one-live-rescan index, a second rescan could be kept for a superseded file and never settle; such a replace is refused 409 `file-not-replaceable` (audited `FILE_UPLOADED` `REFUSED` with `reason` `not-replaceable`), as a superseded file always was, the insert is rolled back and the quarantined bytes are discarded. Seam 1 shows both orders: the sequential one (a file whose rescan was deleted cannot be replaced again) and the interleaved one, where the fake file store's `beforeNextQuarantine` hook runs, between the replace's first checks and the transaction that keeps it, the settlement that supersedes the file and the deletion of that rescan. A file superseded by a live rescan is never deleted, so a rescan's settlement and a deletion of the same file wait for each other on its row, and whichever commits second sees the first.

3. **What deleting a file does to its Findings** (`Findings.fileDeleted`, in the deleting transaction). It takes the settlement lock of the VA Submission (ADR 0029 item 10), then locks every Finding with a place in the file in one id-ordered statement, removes the file's places and rates each of those Findings by the places it has left. A Finding still reported by another file keeps those places and its status. A Finding then reported by no file is, as the user decided on 2026-11-22:
   - **removed if it never had a proposal.** Nothing refers to it (a review and a return item are each about a proposal), so the row goes, with a `FINDING_DELETED` entry naming the file. This and the deletion of item 4 are the one hard delete of a Finding before its Cycle is disposed of; the file it was read from is kept (item 2), as a superseded file is kept after a rescan deleted its places (ADR 0029 item 7). The rule is written once, `FindingStore.REMOVE_UNPROPOSED`, which item 4 uses too. *Decided by the user on 2026-11-22 (docs/agents/reviewer-decisions.md, "Ticket 60: a Finding that never had a proposal is hard-deleted, an exception to the soft-delete rule"):* this hard delete, here and in item 4, is accepted as an exception to the spec's soft-delete rule (`.scratch/annual-va/spec.md` line 285, "Soft-delete is allowed only before retention ends", and line 470, "every other removal before retention ends is a soft-delete"), because nothing refers to such a Finding, its deletion is audited with its id, and a deleted file's content is kept.
   - **kept, with its history, if it has had one, and it follows the rescan rule (ADR 0029 item 5):** unless its current proposal is already Remediated, it gets a Remediated proposal through the one write path (`Proposals.write`), made as `FILE_DELETED` by the SMO/Tech Lead who deleted the file, with the evidence `Not reported by any file of this Scan Report since the file <name> (uploaded <date>) was deleted on <date>.` (business dates, Asia/Singapore) and `replaced_file_id` naming the deleted file, where it was last reported; its review goes back to PENDING. V47 lets `proposed_as` be `FILE_DELETED`, Remediated only and always with the file it names. The screen names the file but offers no download: a deleted file is not served.
   - A later file that reports such a Finding again takes the `FILE_DELETED` proposal away as current, exactly as it takes a rescan's (ADR 0029 item 10; reviewer decisions, "When to reuse: any automatic proposal whose basis a later fact contradicts"): the `PROPOSAL_WITHDRAWN` entry now carries the withdrawn proposal's own `proposed_as`.
   No proposal, review, batch or return row is ever updated or deleted, so the append-only triggers (V14 and later, the per-row checks of V44) are never reached.

4. **`DELETE /api/findings/{id}`** (the SMO/Tech Lead of the System) answers 204 for a Manually Entered Finding. Checks run in the order the Finding and ownership (404 for one that does not exist or another SMO's), the state (409 `invalid-transition`, audited), then, with the Finding's row locked as a proposal locks it, that it was entered by hand (409 `not-manually-entered`: a parsed Finding goes only with its file) and that it has never had a proposal (409 `finding-has-history`); both refusals are audited `FINDING_DELETED` `REFUSED` with that `reason`. A Finding entered by hand that has had a proposal is kept, since proposals and their history are never deleted; the SMO/Tech Lead proposes the status that fits it instead. *Decided by the user on 2026-11-22 (docs/agents/reviewer-decisions.md):* keep this refusal, rather than soft-deleting Findings (a flag every Finding read and count would have to filter) or another rule. `DeleteManualFindingTest` pins the 409, and the screen offers Delete only on a Finding entered by hand with no current proposal (one entered by hand never loses its current proposal, since only a rescan's or a deletion's proposal is withdrawn and those are made for parsed Findings only). A deleted Finding's identity key is free again, so the same Finding can be entered anew.

5. **The mode unlocks by itself.** A mode change counts a non-rejected report file that is not deleted (superseded or not), or any Finding (ADR 0030 item 4); the rule is unchanged, and deleted files simply leave it. Once the deletions leave the Scan Report with neither, the mode can change again; a Finding kept with its history keeps it fixed. A Scan Report that has had a parsed rescan is emptied by deleting the rescan and then the file it superseded (the user's decision of 2026-11-22, item 1): the superseded file counts until it is deleted itself.

6. **Audit.** `FILE_DELETED` (SUCCESS with `file_id`, `report_type` and the `count` of Findings removed; REFUSED with `file_id` and `reason`), one `FINDING_DELETED` per Finding removed (about the Finding; `file_id` when a file deletion removed it, `report_type` when it was entered by hand), and one `STATUS_PROPOSED` per proposal made, with `proposed_as` `FILE_DELETED` and `replaced_file_id` (whose meaning widens to "the file the Finding was last reported in"). All name the SMO/Tech Lead who deleted as the actor. Ids and fixed codes only: no file name, identifier, title or package reaches a log line, an audit entry or an error body (a test puts a sentinel in them). No new detail key is needed.

7. **The screen.** On the prepare screen, inside the `<Editable>` group (ADR 0032; disabled once submitted, ticket 65), each report file that no rescan still there has replaced offers Delete (a file whose rescan was deleted says "Replaced by a rescan that was deleted", and is listed with its Delete as long as the Scan Report is uploaded, which it stays while that file counts), and a Finding entered by hand with no status yet offers Delete in its row. Each asks once, saying what deleting does (the sentence describes the confirm button), before it sends; the files and the Findings are read again afterwards. After a deletion the focus goes to the heading of the files or of the Findings, since the row is gone; after Cancel or a refusal it goes back to the Delete button, and the server's problem shows beside it. A `FILE_DELETED` proposal is marked "File deleted" and names the file it was last reported in, without a download.

Not done here, on purpose: deleting supporting evidence (item 1), restoring the Findings of a file whose rescan was deleted (undoing a rescan), and restoring a deleted file.

Consequences: a Finding can now disappear from a VA Submission before its Cycle is disposed of, but only one nobody ever proposed a status for, and its removal is audited with its id; a deleted file's content is kept, unreadable, until the Cycle's disposal; the list of statuses a proposal can be made as has three values, and the Cyber Manager reviews a `FILE_DELETED` Remediated like any other.

Amends ADR 0021 (a report file can be deleted; a deleted file is not scanned, listed or served), ADR 0029 (items 2, 5 and 10: a deleted file is not superseded, and its Findings follow the rescan rule), ADR 0030 (item 4: deleting is how the mode unlocks) and ADR 0050 (item 8: the one hard delete of a Finding before disposal, of a Finding that never had a proposal).
