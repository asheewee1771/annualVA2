# A SCAP results file is parsed in the pipeline into Findings keyed by rule, with an occurrence per host

Status: accepted

Ticket 15 adds the second parser behind the pipeline (ADR 0022 added the first): a CIS-CAT Pro or OpenSCAP results file, an XCCDF `Benchmark` or `TestResult` (1.1 and 1.2) or an ARF `asset-report-collection`, uploaded as the Secure Configuration Scan Report, is parsed in the settlement transaction into Findings, and the scan date and the hosts it names are kept for the SMO/Tech Lead to confirm. Eleven decisions.

1. **One parser reads both formats.** `parser.scap.ScapXmlParser` is behind `ReportParser` for `ReportFormat.XCCDF_RESULTS` and `ReportFormat.ARF` (a `TestResult` is the same element in both; an ARF only wraps it and carries the whole benchmark besides). It streams the document through `XmlCursor` (decision 9) and reads results only where the formats put them: a root `TestResult`, `Benchmark/TestResult`, and `asset-report-collection/reports/report/content/TestResult`. Everything else is skipped without being looked at, an ARF's report requests (which repeat the whole benchmark and are why an ARF is so large) included, so a result-like element in a report request, a group or a nested `rule-result` is never a result. `ReportFormat` still has a null parser for Nessus and Burp until tickets 16 and 17.
2. **The shape is checked by the parser, and a file that is not that shape is `REJECTED_SCHEMA`.** The root must be an ARF in an `http://scap.nist.gov/schema/asset-reporting-format/` namespace, or a `Benchmark` or `TestResult` in an `http://checklists.nist.gov/xccdf/1.` namespace (1.1 and 1.2); a `TestResult` in any other namespace is not one; a file with no `TestResult` where one belongs (a Benchmark that is not a results file, an ARF with no reports) is refused; so is a failed, `error` or `unknown` rule result with no or an over-long rule id (more than 500 characters), a host name over 500 characters, a value that holds markup where text belongs, and any value read longer than 4,000 characters. A file refused by the parser never enters `SCHEMA_OK`; its stages end `SCAN_CLEAN`, `TYPE_OK`, `REJECTED_SCHEMA`.
3. **Which results are Findings.** `fail` is a Finding. `error` and `unknown` are a Finding too, marked as a check that did not complete (CONTEXT.md), because they are neither a pass nor a fail (spec, the 2026-09-29 grilling). `pass`, `notapplicable` and `notchecked` are ignored, and so are the other values XCCDF 1.2 defines (`notselected`, `informational`, `fixed`) and any word it does not: the ticket names three to ignore and two to keep, and a value this parser does not know is not a deviation to ask a person about. The result word is compared after trimming and in lower case.
4. **Severity is the one the rule result carries; an unrated check is Medium.** `rule-result@severity` `high`, `medium`, `low` or `info` (Informational); `unknown`, a missing attribute, an empty one or any other word is Medium (implementation plan section 2.4: unrated SCAP is Medium). XCCDF has no Critical level. The Benchmark's own `Rule@severity` is not read: CIS-CAT writes `unknown` there as well, OpenSCAP copies the rule's severity onto each result, and reading it would mean holding every rule of the benchmark (an ARF carries it several times over). A Finding's severity is the highest of its occurrences, as in ADR 0022.
5. **The Finding key is `scap|<rule idref>`, scoped to the System, with one occurrence per host.** The identifier and the rule the list shows are both the rule id (a report names no package; the list's "package or rule" column is the rule). A host is the first non-empty `target`, else the first `target-address`, else the `TestResult`'s own id, cleaned like every text from a report (ADR 0022 item 6); so one rule that fails on three hosts is one Finding with three occurrences, and two files naming the same rule are one Finding with an occurrence in each file, as for Dependency-Check. A rule that appears twice for one host in a `TestResult` is merged as it is read (the worse severity; it did not complete only if neither result did), so a rule repeated a hundred thousand times is one entry.
6. **A Finding is a check that did not complete only if it did not complete everywhere.** `finding_occurrence.did_not_complete` (V11) is true for a place whose results were all `error` or `unknown`; a rule that failed on one host and gave an error on another is a failed check, and a place that both failed and errored is a failure. The Finding-level answer (`didNotComplete` in `GET /api/submissions/{id}/findings`) is `bool_and` over its places and is worked out when the list reads, so there is no second stored copy that could disagree with the places (plan section 2.4: `not_completed` when all occurrences did not complete). It is false for every Finding of the other Scan Reports.
7. **The scan date and the target are pre-filled, not trusted.** The scan date is the latest `TestResult@end-time` of the file, read by `ReportDates` (the same reader as Dependency-Check: an ISO date and time with `Z`, `+08:00` or `+0800`, or none, taken as UTC; anything else, before 1990 or after 9999, is no date). The target is the hosts the file names (`target`, else `target-address`; not the result id, which is a place and not a target), distinct, in order, at most 50 of them, joined with a comma and cut to 200 characters. They are stored on the file as `scan_date_from_file` and `target_from_file` and served by the audited metadata read of ADR 0022 item 5, unchanged.
8. **Hard limits from the start, and an honest message.** The size limits are ADR 0021's (XCCDF results 25 MB, ARF 50 MB, decided from the bytes before the file is read in full); the web client says what to do when a Secure Configuration file is too large: an ARF over its limit can be exported again as XCCDF results only. Inside the file, one host's gathered verdicts (one per rule) are capped at 20,000, and the file's Findings and occurrences are capped at the same 20,000 and 50,000 as ticket 14 (`ParsedReport.MAX_FINDINGS`, `MAX_OCCURRENCES`). **These are the numbers of ADR 0022 item 9, reused as they stand, not new ones; a human accepted them on 2026-10-14** (`docs/agents/reviewer-decisions.md`; a scan of many hosts reaches the occurrence cap at about 250 hosts failing 200 rules each, but the byte limits usually bind first). A report over a cap is no longer `REJECTED_SCHEMA` ("not in the expected format", which was wrong for a well-formed file that is merely big): it is `REJECTED_TOO_MANY_FINDINGS`, a new code with its own status (V11 widens the status check; its sentence names the two numbers, also covers one item with far more entries than a real report has (a Dependency-Check dependency with over 1,000 packages or 20,000 vulnerabilities), and says to export the scan in parts; audit code `too-many-findings`). `REJECTED_TOO_LARGE` stays for a file over the size limit of its type. Ticket 14's two parsers use the same code.
9. **Shared code, not a second copy.** `parser.FindingsBuilder` is what every parser does with the Findings it reads (merge by key, one occurrence per place, worst severity of a Finding's places, and the two per-file caps, which it alone enforces and raises as `UnparseableReportException.overALimit()`; the exception carries a `Reason`, `SHAPE` or `OVER_A_LIMIT`, which `FileChecks` maps to `SCHEMA` or `TOO_MANY_FINDINGS`). The rule for one place read twice (the worse severity; it did not complete only if neither reading did) is written once, as `ParsedReport.Occurrence.merge`, and the SCAP parser uses it for a rule repeated on one host as `FindingsBuilder` does for a place repeated in a file. What a parser still counts itself are per-item bounds on what it holds while one item is read, in one named place each: a Dependency-Check dependency's packages and vulnerabilities (`DependencyCheckFindings`) and a SCAP TestResult's distinct rules (`ScapXmlParser.MAX_RULES_PER_HOST`). Dependency-Check's `DependencyCheckFindings` hands the builder its Findings instead of holding its own copy. `parser.ReportDates` is the date reader both use. `parser.xml.XmlCursor` is the one way the XML parsers walk a document: the element path from the root, text and attributes read only up to a length (refused as soon as longer than `ReportText.MAX_FIELD_CHARS`, 4,000, so a hostile value is never built whole), and a subtree skipped without a path built for any of it. A document nested deeper than `XmlCursor.MAX_DEPTH` (100, the same limit as ADR 0021's schema check, which now takes the number from it) is refused by the cursor itself, whether the walk enters the nesting or skips it, so a parser does not rely on its caller for that. The Dependency-Check XML parser now walks with it, which also closes ticket 14's open item that leaf text was read whole before any length check; its JSON parser sets the same 4,000-character limit on every string it reads (a string it skips is not read and has no limit). The severity order in the Finding list's SQL is written once, from `Severity.values()`, instead of as a literal array.
10. **Hardened XML, and nothing from a report is said back.** Every reader is made in `SecureXml` (no DTD, no external entity; the architecture test keeps it so): a DOCTYPE is skipped, an entity it would declare is an error, so an external entity or an entity bomb is `REJECTED_UNREADABLE` by the schema check before the parser runs. No rule id, host or target reaches a log line, an audit entry or an error body; a rejection says the same fixed sentence whatever the file held (ADR 0022 item 6, proved again by Seam 1 tests with a sentinel).
11. **Samples.** `backend/src/test/resources/samples/scap/` holds a CIS-CAT XCCDF 1.2 results file (one host, `cdf:`-prefixed) and an OpenSCAP ARF (two hosts, with the data stream collection in its report request). Both are hand-written reconstructions of the schemas, labelled so in the file and in a README, with invented names and documentation-range addresses; they are not output of a real scan and must be regenerated from one before release (ticket 58, plan H6).

Consequences: uploading the same export twice doubles every occurrence count until ticket 21's replace rule applies (as for Dependency-Check); a rule-result severity is the only source of a rating, so a Benchmark that rates a rule `high` while its result carries none reads as Medium; the assets an ARF describes (`arf:assets`) are not read, so a `TestResult` with no `target` is known by its id; the ARF and XCCDF files wait for ticket 23 for the pre-fill confirmation and for ticket 19 for statuses and filters; the host with the most failed rules and the cap on a host's distinct rules (20,000) are held in memory for the length of one `TestResult`.

Amended by ADR 0024: `ReportFormat` now has a null parser only for Burp (ticket 17), since the Nessus parser exists; the hosts and the latest scan date this parser gathers (item 7) are now kept by the shared `parser.ScanFacts`, which the Nessus parser uses too, with no change in behaviour.

Amended by ADR 0025: `ReportFormat` has no null parser now (Burp has one); the XML parse wrapper, reading holder and child loop, the severity scale and unrated policy, and the key prefixes are shared in `XmlCursor`, `ScanReading`, `Severity` and `FindingKeys`, with no change of behaviour.
