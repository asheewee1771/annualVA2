# The apply is one locked transaction against the baseline the preview saw, and the Register names the SMO and Cyber Manager roles

Status: accepted

`POST /api/system-register/previews/{id}/apply` (VA POC only, step-up intent `register-apply`) applies a confirmed preview (ADR 0017); `GET /api/systems` reads the Register. Seven decisions follow.

1. **The step-up is the first thing the apply asks.** `StepUp.require("register-apply")` runs before the preview is looked up, so a stale sign-in learns nothing about which previews exist, and a refusal changes nothing. The upload needs no step-up (ADR 0017); the front end names the preview in the apply's JSON body only so it can reopen it after the fresh sign-in (a file upload cannot be kept across that round trip, a preview id can). The server ignores the body.
2. **One transaction, one lock.** The Systems, the role grants, the preview's status and every audit entry commit or roll back together (ADR 0014: `AuditLog.record`, never `recordIndependently`, inside the command). The apply first takes a PostgreSQL transaction-level advisory lock, so two applies run one at a time: the second finds the Register the first left behind.
3. **A preview is a snapshot, not a lock, so the apply checks the baseline.** Each row was classified against the Register as it was. The apply refuses with `409 register-changed` unless every ADD names a System ID nobody holds now (checked by the column's citext rules), every UPDATE, RETIRE and NO_CHANGE row names a System that still reads exactly as the row's `before`, and no active System exists that the preview does not mention (it would have been retired or listed). The other 409s are `preview-applied` (a preview is applied at most once; `register_upload.status` becomes APPLIED with who and when), `preview-expired` (an hour, by the `Clock` bean) and `preview-blocked`. The problem sentences are fixed and never echo the file.
4. **System IDs are matched by the database.** The preview builder no longer lower-cases IDs in Java: it asks the database which of the file's IDs and the Register's codes are equal under the `citext` column (`RegisterStore.foldedIds`, a join on `a::citext = b::citext`), so an ID that Java would call distinct and the unique index would call equal can never reach an insert as a 500. Emails stay lower-cased in Java: they are ASCII by validation. An UPDATE keeps the System ID as first registered; only the name, emails and Quarter change, and listing a retired System again reinstates it as the same System (same id).
5. **The Register names the roles.** `RegisterRoles` (access module, the only writer of REGISTER grants and the apply's only collaborator that touches `RoleGrantStore`; the architecture test names it) makes the role store agree with the Register in the apply's transaction: every active System has one SMO and one Cyber Manager grant with source REGISTER scoped to it, by email where the person has not signed in (the first sign-in attaches it), and every other live REGISTER grant is revoked, including every grant of a retired System. Roles are read per request (ADR 0011), so a former SMO/Tech Lead's next request is refused. A grant that already stands is left alone, so applying the same Register again changes no grant; a lapsed or suspended grant that still stands is not revived here, those states belong to the role lifecycle (tickets 46 and 47). A configured VA POC named as an SMO/Tech Lead keeps VA_POC and gains the System role. `role_grant.system_id` now has its foreign key (migration V7); no endpoint writes a grant (story 76).
6. **What is audited.** One `REGISTER_APPLIED` entry (preview id and the counts added, updated, retired, unchanged, roles granted and roles revoked), one `REGISTER_SYSTEM_RETIRED` entry per retired System (about that System), and one `ROLE_GRANTED` or `ROLE_REVOKED` entry per grant (about the System, with role, source and grant id). Entries hold ids and numbers only: the allow-list gained the six count keys in V7, and no email, name or System ID is ever in an entry (lm-19). A refused or rolled-back apply writes none of these; the step-up refusal is the usual `REQUEST_REFUSED`.
7. **The Register table.** `GET /api/systems` (`VA_POC`, `SMO`, `CYBER_MANAGER`) filters by `AccessGuard.scope(VIEW)` (ADR 0013): a VA POC sees every System including retired ones, an SMO/Tech Lead or Cyber Manager only theirs. Each row has the System's id, System ID, name, both emails, Quarter (`Q1` to `Q4`), the retired flag and the Unlinked SMO flag, recomputed at read time (ADR 0017). The flag is shown to a VA POC only (`null` for anyone else): it is theirs to fix and tells a Cyber Manager whether a colleague has signed in. The list is not paged (a Register holds tens of Systems) and a read of it is not audited (it names no System's reports and changes nothing); revisit both if the Register grows or story 84's "every view" is read to cover it. An Auditor has no System scope yet and is refused.

Consequences: a System's `added_on` is the Singapore business date of its apply (`CycleCalendar.today()`), which the Window arithmetic of a mid-Quarter add will read; expired and applied previews are still not purged (ticket 49); the preview's effects on in-flight VA Submissions (Will withdraw, Will move, Will transfer) are ticket 43, and until it lands an apply does not touch VA Submissions because none exist yet; a person pre-registered by email is not created by the apply (a grant by email is enough, and the first sign-in links it).

Amended by ADR 0048: the apply reads the withdrawals the VA POC confirmed from its body, refuses a preview whose in-flight work has changed (`409 work-changed`) or whose withdrawals are not exactly confirmed (`400 withdrawal-unconfirmed`), and withdraws a retired System's in-flight VA Submissions.
