# A return attaches what is Disputed, and a pass to endorsement needs everything confirmed

Status: accepted (items 3 and 5 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 30 (stories 55 and 57) lets the Cyber Manager move a VA Submission out of In Review: back to its SMO/Tech Lead for rework, or on to the VA POCs for endorsement. It adds one migration (V130), three endpoints, one panel on the review screen and no module. The commands are in `submission`, which owns the state machine (ADR 0035); what is Disputed or unconfirmed is read through a port, `ReviewProgress`, which `finding` implements (`ReviewChecks`), as `SubmitReadiness` is for submit (ADR 0032).

1. **Two review-step commands, one set of checks.** `POST /api/submissions/{id}/return` and `POST /api/submissions/{id}/pass-to-endorsement` run a review's checks in its order (ADR 0035 item 2): the role rule (`403`), the access guard on `Need.REVIEW` (`404`), then, with the VA Submission's row held, segregation of duties (`403 sod-conflict`) and the state (`409 invalid-transition`, `reason=state-not-reviewable`). The checks are written once, in `Submissions.atReviewStep`, which `lockForReview` also uses; it records the caller at step `REVIEW`, kept only if the command commits. The two commands take the row exclusively (`FOR NO KEY UPDATE`, `SubmissionStore.lockForMove`, as submit does), so a review in progress, which holds it shared, finishes first, and a review that waited sees the new state (ADR 0035 item 3). The `ReviewTarget` remembers how the row is held, and the one method that moves the state refuses (an `IllegalStateException`) a target held only shared, so a later change that drops the exclusive hold fails every move test. A pass also sets `va_submission.passed_to_endorsement_at` (V133, ADR 0037) to the clock's instant in the same statement, which the VA POC's Cycle matrix shows as the reviewed milestone; a return leaves it as it was (ticket 35 decides what a VA POC return does to it). The move sets the state with `OVERDUE_AFTER_MOVE`: a return keeps the flag (Returned for Rework waits on the same Review Window), and a pass clears it unless the Endorsement Window has passed too (ADR 0033).

2. **A return attaches what is Disputed, and touches no review.** A return needs at least one Disputed Finding or not-applicable justification (`409 nothing-disputed` otherwise). It keeps a `submission_return` row (step, comment, who, when) and one `submission_return_item` per Disputed item, named by the review that Disputed it (`finding_review` or `report_review`), so the return still says what it was about after the SMO/Tech Lead proposes again or rewrites a justification. Both tables are append-only by the Declarations' trigger (V19); retention (ticket 49) replaces it, as for the reviews. The move changes no review state: a confirmed Finding stays confirmed until the SMO/Tech Lead proposes something else for it (ADR 0027 item 2), and Disputed and still-pending items stay as they are. Ticket 32 builds the re-review of only what changed on this.

   `GET /api/submissions/{id}/returns` lists them, the latest first, for anyone who may see the System. A return carries what a person wrote, so every read is audited as `SUBMISSION_RETURNS_VIEWED`, the owner's included (reviewer decision of 2026-10-14, "A 404 on a content-bearing read is not audited": a successful content-bearing read is audited for every role; the owner exemption of 2026-10-13 covers only reads with no content).

3. **The return comment is optional** (decided 2026-10-25). Each Dispute already carries its own required comment, so the return's comment is a summary for the SMO/Tech Lead: cleaned by `ReportText.cleanLongText` and bounded to 4000 code points (`ReportText.MAX_LONG_TEXT`, now the one constant for every long text a person types), with nothing left meaning none. The table checks the bound. The screen's box is labelled, carries the classification label (IM8 dp-8) and the server's `maxLength`, and is linked to the server's problem. The comment never reaches a log line, an audit entry or an error body; a test puts a sentinel in it. `submission` now reads `parser` for `ReportText` only, so the one text rule is not copied. Ticket 35's VA POC return requires its comment, because nothing else explains it.

4. **A pass to endorsement needs every Finding and justification confirmed, and says what is left.** Anything unconfirmed is one `409 not-confirmed` whose `reasons` are, in order: `findings-awaiting-review` (review state PENDING, or none), `findings-disputed`, then per Scan Report marked not applicable `justification-awaiting-review` or `justification-disputed`. Each is a `SubmitReadiness.Blocker` with a fixed sentence and a count, never a list of Finding ids, which can run to thousands; the review screen filters the Findings list by review state instead. `ReviewChecks.outcome` computes the list and `returnable` (something Disputed) as a pure function of the Findings' counts and the Scan Reports that the readiness read already loads, so it adds no query to a submit. `GET /api/submissions/{id}/readiness` gives the result as `review: {returnable, endorsementBlockers}`, and the return and the pass judge by the same function, so the panel and the commands never disagree. Only the items a return attaches are read separately (`ReviewProgress.disputed`), as a list of Findings and a list of justifications.

5. **How a VA POC counts for segregation of duties** (decided 2026-10-25; set here so that ticket 34 builds it). Holding the VA POC role does not assign a person to the endorsing step of any System: a VA POC counts at the endorsing step only once they act there (endorse, return or decide an Exemption on that VA Submission, `submission_participation`). The other direction is unchanged: a VA POC the Register names as a System's SMO/Tech Lead or Cyber Manager is assigned to that step and so refused the endorsing step of that System (ticket 34's acceptance line), and the other VA POC endorses. The opposite reading, that the role assigns a VA POC to the endorsing step of every System, would refuse a VA POC every submit and review, against the spec's chosen reading of story 76 (a VA POC's own Register upload may name them as an SMO/Tech Lead or Cyber Manager) and its "a VA POC who is conflicted leaves the item to the other one". So ticket 34 adds an `ENDORSE` step with no Register assignment, and `SegregationOfDuties.assignedAtAnotherStep` keeps refusing a scope over every System as a programming error, with a message that points here.

6. **Audit and events.** A return is `SUBMISSION_RETURNED` with `state_from`, `state_to` and the `count` attached; a pass is `SUBMISSION_PASSED` with the states. Refusals carry a fixed `reason`: `sod-conflict`, `state-not-reviewable`, `nothing-disputed`, or `not-confirmed` with the `count` of reasons. No detail key is new. Each move publishes a `SubmissionEvent` (In Review to Returned for Rework, or to Awaiting Endorsement) after the commit; the notifications (tickets 36 and 37) send the SMO/Tech Lead's required Return for Rework message and both VA POCs' item from it.

7. **The screen.** The review screen's "Finish the review" panel shows, only In Review, Pass to endorsement (disabled, with the server's list of what is left, until everything is confirmed) and Return for rework (disabled until something is Disputed) with the comment box; each says when it is possible. A refusal is the server's problem, and after a `409` the screen reads the VA Submission again.

Not done here, on purpose:
- The notifications themselves (tickets 36 and 37) and the SMO/Tech Lead's view of a return in the rework queue (ticket 31).
- Re-review of only what changed after a resubmission (ticket 32), the VA POC's return (ticket 35) and the endorsing step (ticket 34).

Consequences:
- A Cyber Manager cannot return a VA Submission they have only partly reviewed unless something is Disputed; what is still pending stays pending for the next review.
- `ReportType` gains a display title for fixed sentences.

Amends ADR 0035 (the reviewing step's checks are shared by the return and the pass, and the VA POC question is answered by item 5).
