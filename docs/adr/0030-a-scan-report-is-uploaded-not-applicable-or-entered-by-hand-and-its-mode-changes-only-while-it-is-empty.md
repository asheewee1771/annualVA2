# A Scan Report is uploaded, not applicable or entered by hand, and its mode changes only while it is empty

Status: accepted

Ticket 22 (story 23) lets the SMO/Tech Lead say how each Scan Report of a VA Submission is provided: its tool's machine-readable report is uploaded (as before), it does not apply to the System, or the tool cannot export a machine-readable report and its Findings are typed in. It adds one migration (V17), three endpoints and no module: the code is in `finding` (the plan puts "manual entries, N/A slots" there), and `ingestion` asks it whether a Scan Report takes report files. The Cyber Manager's confirm or Dispute of a not-applicable justification is the review engine's (ticket 28); the submit rule that every Scan Report is provided is ticket 25's.

1. **A Scan Report has a mode, and no row means uploaded.** `report_slot` (the VA Submission and the Scan Report as its key) holds `mode` (`UPLOAD`, `NOT_APPLICABLE` or `MANUAL`), `justification` and `review_state`. A VA Submission has no row for a Scan Report until the first write to it (a mode change, a report file or a Finding by hand), which adds it as `UPLOAD`; a read fills in `UPLOAD` for a missing one. Checks on the table, not only in code: Secure Configuration is never `NOT_APPLICABLE` (it is always required, uploaded or entered by hand); a justification is present exactly when the mode is not `UPLOAD`, 1 to 4000 characters; a review state is present exactly when the mode is `NOT_APPLICABLE`.
2. **`PUT /api/submissions/{id}/reports/{type}/mode`** (the SMO/Tech Lead of the System) takes `mode` and, for `NOT_APPLICABLE` and `MANUAL`, `justification`, and answers 200 with the Scan Report as it is now. Checks run in the order ownership (another SMO's VA Submission or one that does not exist is the same 404, ADR 0013), state (Draft or Returned for Rework, else 409 `invalid-transition`, audited `REFUSED` with `reason=state-not-editable`; the rule is `Proposals.editable`, the one proposals use, with its own sentence), `mode` (missing, unknown, or `NOT_APPLICABLE` for Secure Configuration: 400 `invalid-field` naming `mode`), `justification` (missing or empty once cleaned for `NOT_APPLICABLE` and `MANUAL`, longer than 4000 characters, or given with `UPLOAD`: 400 naming `justification`), and last, with the Scan Report locked, the content rule (item 4). The justification is cleaned by `ReportText.cleanLongText`, the rule every long text a person types goes through (ADR 0027 item 5). A Cyber Manager, a VA POC who is not the System's SMO and an Auditor are refused with 403 by the role rule. `GET /api/submissions/{id}/reports` gives the three Scan Reports in the order Dependency-Check, Secure Configuration, Burp Suite, with `mode`, `justification` and `reviewState`, to anyone who may see the System.
3. **A not-applicable justification is reviewed like a Finding.** Setting `NOT_APPLICABLE` puts `review_state` to `PENDING`. Setting it again with the same justification keeps the review (nothing new to review); a different justification, or marking it not applicable again after another mode, puts it back to `PENDING`, as a new proposal does for a Finding (ADR 0027 item 2). Any other mode has no review state: a Scan Report entered by hand is reviewed through its Findings. The justification is overwritten, not kept as history: the audit log records each change (item 7), and the review engine (ticket 28) decides whether the confirmed text must be kept beside the review.
4. **The mode changes only while the Scan Report holds nothing the new mode would deny.** A change to another mode is 409 `report-not-empty` (audited `REFUSED`, `reason=report-not-empty`) while the Scan Report has a report file that was not rejected (on its way through the checks, parsed, or superseded) or any Finding (parsed or entered by hand). A rejected file and supporting evidence do not count. Setting the mode it already has is always allowed, so a justification can be corrected. Without this rule a Scan Report marked not applicable could keep Findings that need statuses, and a file still being scanned could settle Findings into it later. There is no way yet to delete a report file or a Finding entered by hand, so once a Scan Report holds one its mode is fixed for that VA Submission.
5. **A Scan Report not uploaded takes no report file; supporting evidence goes anywhere.** `POST /api/submissions/{id}/files` with `kind=MACHINE_READABLE` for a Scan Report in `NOT_APPLICABLE` or `MANUAL` is 409 `wrong-report-mode`, audited as a refused `FILE_UPLOADED` with `reason=wrong-report-mode`; the quarantined bytes are discarded, as for every refusal after quarantine. Supporting evidence (`kind=EVIDENCE`) is accepted in every mode: a tool that cannot export a machine-readable report usually exports a PDF or HTML one, and an approval memo can sit under any Scan Report (ADR 0027 item 7). The check runs in the transaction that keeps the file, so the check and the insert see the same mode (item 6).
6. **Every write to a Scan Report locks its row first.** A mode change takes the row `FOR UPDATE` (after adding it if missing, `INSERT ... ON CONFLICT DO NOTHING`); an upload of a report file and a Finding entered by hand take it `FOR SHARE`. So a mode change and an upload or an entry wait for each other, and the one that goes second sees what the first committed: a mode change that waited counts the file or Finding that was just added, and an upload that waited sees the new mode. Locks on Findings are not involved (a Finding by hand is a new row), so the order of ADR 0029 item 10 is unchanged. Seam 1 runs one request at a time, so no test can show the lock; it is held by the statements and this ADR.
7. **`POST /api/submissions/{id}/findings/manual`** (the SMO/Tech Lead of the System) takes `reportType`, `title`, `identifier`, `packageOrRule` and `severity` and answers 201 with the Finding as the list shows it. Checks run in the order ownership (404), state (409 `invalid-transition`, audited), the fields in that order (400 `invalid-field` naming the first wrong one; not audited), then, with the Scan Report held, its mode (not `MANUAL`: 409 `wrong-report-mode`, audited), and last that the VA Submission has no such Finding yet (409 `duplicate-finding`, audited). Each text is cleaned to one line by `ReportText.cleanOneLine` and bounded: the title at most 200 characters, the identifier 200, the package or rule 500 (chosen format bounds for as-1, as constants in `ManualFindings`; the table checks them again for a Finding entered by hand). The severity is one of the five levels. A Finding entered by hand is an ordinary Finding: it has no place, needs a Finding Status, is counted by the readiness counts and is listed with `source` `MANUAL` and its `title`; every parsed Finding now says `source` `PARSED` and has no title. V17 adds `finding.source` (filled `PARSED` for existing rows by a default that is then dropped, so every write names it) and `finding.title`.
8. **The identity key of a Finding entered by hand.** It is `manual|<Scan Report>|<identifier>|<package or rule>`, with a `|` or `\` in a value escaped by `\` so two different Findings never share a key, hashed as every key is. So the same Finding is entered once per VA Submission (the unique key of V10 settles a race), a different package or rule is a different Finding, and a Finding entered by hand never matches a parsed one, which a mode change could not mix anyway (item 4). Carry-over (Release 2) matches on this key across Cycles.
9. **Audit.** A mode change is `REPORT_MODE_SET` with `report_type` and `mode`; a read of the Scan Reports is `SCAN_REPORTS_VIEWED` with the `count`, for every role, the owner included, because a justification is what a person wrote (as `FINDING_PROPOSALS_VIEWED`); a Finding entered by hand is `FINDING_ENTERED` about the new Finding with `report_type`. Refusals carry a fixed `reason`. Never a justification, title, identifier or package: V17 adds only `report_type` and `mode` to the detail allow-list, and tests put a sentinel in every field and every refusal and find it in no log line, audit entry or error body. A 400 and a 404 are not audited.
10. **The screen.** Each Scan Report card shows how it is provided, with its justification as text and the review of a not-applicable one, and a select of the modes it offers (Secure Configuration has no "not applicable") with a justification box beside it, each with its classification label (IM8 dp-8) and the server's length limit. Report files are offered only while it is uploaded; supporting evidence in every mode. A Scan Report entered by hand has a form for one Finding (title, identifier, package or rule, severity, each labelled), and the Findings and the progress are asked for again after each entry. A Finding entered by hand is marked "Manually Entered" in the list, with its title. The server's problem is shown beside the control and marks the field it names.

Not done here, on purpose: the Cyber Manager's confirm or Dispute of a not-applicable justification and its comment (ticket 28), the submit rule that every Scan Report is uploaded and read, not applicable or entered by hand (ticket 25; the plan's "Secure Config slot READY, other slots READY/N/A/MANUAL"), deleting a report file or a Finding entered by hand, and any Playwright scenario (ticket 53).

Consequences: a mode chosen by mistake can be undone only before anything is added to the Scan Report; the review of a not-applicable Scan Report lives on `report_slot`, so ticket 28 reviews two kinds of thing (Findings and not-applicable Scan Reports) and its counts and its "every Finding confirmed" rule must include the second; a Scan Report entered by hand has no file, so the scan-date and age rules of ticket 23 have nothing to check for it.

Amends ADR 0021 (an upload of a report file is refused when its Scan Report is not uploaded) and ADR 0027 (a Finding has a source and may have a title; the state rule of a proposal is shared with the mode change and the entry by hand).
