# Supporting evidence is scanned and type-checked like every file, and then never read

Status: accepted

Ticket 18 (story 22) lets an SMO/Tech Lead attach a PDF or HTML report to a Scan Report for people to read. It is the same upload (`POST /api/submissions/{id}/files` with `kind` EVIDENCE, under any of the three Scan Reports), the same quarantine, malware scan, hash rule and attempts as ADR 0021, and then it stops: nothing parses, schema-checks or reads it. HTML from a person's tool is active content from an untrusted source, so the decisions below are mostly about what is not done with it. It adds one migration (V13) and no new module.

1. **One resting status, `READY`, for a finished evidence file.** A machine-readable file rests in `PARSED` (ADR 0022). An evidence file skips the schema check and the parse, so `SCHEMA_OK` and `PARSED` would both be untrue of it. `TYPE_OK` is a stage a file passes through in the one write of the checks, not a place it rests. So it rests in `READY`, the last status of the implementation plan's pipeline, and its stages are exactly `QUARANTINED`, `SCAN_SUBMITTED`, `SCAN_CLEAN`, `TYPE_OK`, `READY`: a test proves that no `SCHEMA_OK` or `PARSED` is ever recorded. `READY` is viewable and downloadable like `SCHEMA_OK` and `PARSED`. V13 adds it to the status check and the clean-copy check, and a check that only evidence is `READY` and evidence is never `SCHEMA_OK` or `PARSED`. The file metadata read (ADR 0022) now answers for `PARSED` only, so it is 404 for evidence. (The plan's `READY` for a Scan Report slot, used by the submit rules in a later ticket, is a property of the slot, not a file status.)
2. **The type comes from the leading bytes alone.** The file name and the declared content type are never used. (a) `%PDF-` at **offset 0** is a PDF. Many readers accept the header anywhere in the first 1,024 bytes and `file(1)` does too, which is exactly why this does not: a file that starts with anything else, a byte order mark, a space or junk before the marker is not a PDF, because a looser rule lets a file that is something else (an HTML page, a script) hide a marker in its first kilobyte. (b) Otherwise it is HTML if, after an optional UTF-8 byte order mark, whitespace, one XML declaration and any number of comments, all within the first 4,096 bytes, the next token is `<!doctype html` (any case) followed by whitespace or `>`, or `<html` followed by whitespace, `>` or `/`. A comment that does not end inside the window, a doctype or tag cut by the end of the window, any other markup first (`<script>`, `<body>`, an `<svg>` root), UTF-16 and any other bytes are not HTML. (c) Anything else is `REJECTED_TYPE`. The two sniffs cannot both match (the PDF marker starts with `%`, which the HTML prefix never skips), so a file that looks like both resolves the same way every time: a marker at the very start makes a PDF, whatever HTML follows it, and an HTML page whose comment or body holds `%PDF-` is HTML. Tests pin each of these cases. The sniff is a few byte comparisons in `EvidenceFormat`, which an architecture test keeps free of any parser, XML or JSON reader and any file API.
3. **A machine-readable report is not evidence, and a PDF or HTML is not a report.** An XML report starts with an XML declaration and a root that is not `html` (or is a JSON object), so the HTML sniff refuses it as `REJECTED_TYPE` under `EVIDENCE`. A PDF, or an HTML document whose root is `html`, is `REJECTED_TYPE` under `MACHINE_READABLE` for every Scan Report (the existing sniff, unchanged: `TypeCheck.check` is now the machine-readable branch and `FileChecks` chooses the branch by kind). Evidence attaches to a Scan Report type but is not tied to a format: any evidence file is fine under any of the three.
4. **Limits are the ADR 0021 table's.** PDF 20 MB and HTML 10 MB (the 2026-10-13 size-limit decision in `reviewer-decisions.md` covers them), decided from the format the bytes show, before anything is read, so an over-limit file is `REJECTED_TOO_LARGE` and a 15 MB PDF is accepted where a 15 MB HTML file is not. The 50 MB request ceiling and the 20-live-files cap apply as before, counted for evidence apart from the Scan Report's machine-readable files.
5. **Nothing is read, so nothing can leak.** The checks never parse evidence and never take text from it: no parser, no schema check, no metadata, no Findings. A rejected evidence file keeps no bytes, as every rejected file (ADR 0021 decision 6). Its display name is cleaned by the same allowlist as every name. Logs, audit entries and error bodies carry the same ids and fixed codes as for reports, and tests put a sentinel in the names and bytes of evidence that is accepted and evidence that is rejected for each reason and find it nowhere.
6. **HTML is never rendered by the application.** One download path serves every file, evidence included: an attachment, `Content-Type: application/octet-stream` whatever the request's `Accept`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (set on the response itself, so the stricter policy replaces the application's own), `Cache-Control: no-store`, and the cleaned name. The API returns a file's name, size, status and format and never any of its content, and the screen offers only a download button: no preview, no iframe, no inline view, no object URL shown in a page. A file the person saves and opens on their own machine is theirs to trust or not; the card says so. Download access is unchanged and proven again for evidence: only when the file is `READY`, only for someone who may see the System, 404 otherwise and identical to a missing file (ADR 0013), audited as `FILE_DOWNLOADED` for every role including the owner (a 404 is not audited); a status or list read is `FILE_VIEWED` unless the owning SMO/Tech Lead reads it (`reviewer-decisions.md`, 2026-10-13).
7. **Real PDF and HTML files from the tools are not exercised until ticket 58.** The tests use small hand-made byte strings. The sniff is conservative on purpose, so a real export that does not start the way decision 2 requires (an HTML page with UTF-16 text, one that starts with a `<script>`, a PDF with a leading blank line) is refused with the plain type message and ticket 58 may widen it by a line.

8. **An encrypted PDF is refused, by a byte comparison.** A password-protected PDF is opaque to the malware scanner, so accepting it would hand reviewers a file nobody inspected. A PDF whose last 64 KB (`EvidenceFormat.ENCRYPT_WINDOW`: the trailer, or for a file with a cross-reference stream the dictionary that precedes the stream data) holds the name `/Encrypt` is `REJECTED_ENCRYPTED` (reject code `encrypted`, audit code `encrypted`) with the plain message to upload a copy without a password. The name must end at whitespace, a delimiter or the end of the file, so `/EncryptMetadata` and `/Encrypted` are other names. It is a check on a bounded tail of bytes in `EvidenceFormat`, applied after the size limit and to PDFs only (an HTML page that says `/Encrypt` is HTML), with no PDF library and nothing parsed; the architecture test above still holds. It is a heuristic and says so: an `/Encrypt` entry hidden in an object stream, spelled with a `#` escape, in the dictionary of a cross-reference stream whose data is longer than the window (a large PDF 1.5 file, up to the 20 MB cap), or in the first-page trailer of a linearised file that is more than 64 KB from the end is not caught, and ticket 51's production scanner (which must scan or reject an encrypted PDF) is what closes that gap. Do not add a parser for it. The human decision is in `docs/agents/reviewer-decisions.md` ("An encrypted PDF is refused as supporting evidence by a byte-level check"). V13 adds `REJECTED_ENCRYPTED` to the status check.
9. **A download of evidence takes its extension from the detected format.** The name a person gave is cleaned by the allowlist (ADR 0021) but keeps any extension, and the operating system, not the browser, decides how a saved file opens: HTML saved as `.hta`, `.svg` or `.wsf` would run, outside everything decision 6 does to the response. So the name offered in `Content-Disposition` for an evidence file is its cleaned name with the last extension replaced by `.pdf` for a PDF and `.html` for an HTML document (appended when there is none; `file` when nothing is left), whatever the upload was called. The stored name, the one the screen lists, stays what the person typed, as text. A machine-readable file keeps its name as before (its bytes were parsed as XML or JSON).

**A Risk Accepted approval memo (story 35, later) reuses this path.** It is a file of kind EVIDENCE (a memo is a PDF or an HTML page) uploaded to the same endpoint, quarantined, scanned, type-checked, kept in `READY` and downloaded through the same attachment endpoint, under the same audit. What it needs and this ticket does not build is the link from a Finding Status to the file (a nullable file id on the status, and the rule that the file belongs to the same VA Submission); it must not add another upload, store or download. Counting it against a Scan Report's evidence cap, or giving it a `kind` of its own, is that ticket's decision.

Consequences: `ReportFormat` stays the list of machine-readable formats; `report_file.detected_format` holds `PDF` or `HTML` for evidence; no `ScanPoller` change was needed because the settlement already carries a status, stages and a format name, and a null parse result writes no Findings; ADR 0021 decision 7 is amended by this ADR.
