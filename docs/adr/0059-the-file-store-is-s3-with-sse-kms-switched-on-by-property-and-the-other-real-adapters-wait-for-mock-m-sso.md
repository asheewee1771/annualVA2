# The file store is S3 with SSE-KMS, switched on by a property, and the other real adapters wait for mock-m-sso

Status: accepted for the scope (the user's decision of 2026-10-29, recorded on ticket 51: build only the file store now). Provisional, as built beyond that decision: items 2, 4 and 5, listed under "Human Decision Needed".

Ticket 51. `mock-m-sso` (ticket 01) is not on the developer machine, so the scanner, mail and MCC service-client adapters cannot be checked against the mocks. The file store needs only LocalStack, which compose already runs, so it is built alone: `adapters.pending.UnwiredFileStore` is replaced where the new store is switched on. The scanner, mail relay, MCC service client and `IdentityStatus` adapters stay `adapters.pending` stand-ins (`UnwiredIdentityStatus` goes only with its real adapter), and every ticket 51 box that is not the file store's stays open.

1. **S3 with SSE-KMS, in `sg.annualva.adapters.s3`.** `S3FileStore` implements `boundary.FileStore` on the AWS SDK for Java v2 (`software.amazon.awssdk:s3`, with `apache-client`, the netty client excluded: only the synchronous client is used). One bucket per zone (`quarantine`, `clean`, `export`); the key is the application's random id and a key that is not of that shape (`[A-Za-z0-9][A-Za-z0-9._-]{0,127}`, the local store's rule) is refused before any call. Every `put` sends `x-amz-server-side-encryption: aws:kms` with the configured key alias and bucket key enabled, then checks that the answer says `aws:kms` and names a key; if it does not, the object is deleted again and the write fails, so an S3 that ignores the request cannot leave plain bytes behind ("asserted on every write"). `get` of a missing key, and any SDK failure, is a `BoundaryFailureException` with a fixed sentence and no cause; `delete` of a missing key is not an error (S3 answers 204). Nothing is logged, so no key, bucket or content can reach a log, an audit entry or an error body. Timeouts are `annualva.aws.connect-timeout` (3 s), `read-timeout` (30 s: a file may be 50 MB) and `api-call-timeout` (60 s in all, retries included), with `max-attempts` (2), so a dead store cannot hold a request thread for longer than the last. The SDK's own request logging puts bucket and key names in DEBUG and TRACE lines, so `application.yml` pins `software.amazon.awssdk`, `org.apache.http` and `org.apache.hc` to WARN; DEBUG must not be enabled on them (it would write what the application keeps out of its logs). `AwsProperties.toString()` omits the access key and the secret, and the store closes the default credential chain it made when no fixed keys are set. The AWS SDK is used nowhere else (`ModuleConventionsArchTest.onlyTheS3AdapterUsesTheAwsSdk`).

2. **Switched on by `annualva.aws.enabled`, not by a profile name** (provisional). `S3FileStore` and its `AwsProperties` are `@NotDevLocal` and `@ConditionalOnProperty(annualva.aws.enabled=true)`; `UnwiredFileStore` is `@NotDevLocal` and `@ConditionalOnProperty(enabled=false, matchIfMissing=true)`. So there is exactly one `FileStore` bean per profile: `dev-mcc` (which sets `enabled: true`) has the S3 store; `dev-local` has the local folder store only (both stand-in and S3 are `@NotDevLocal`, whatever the property says); `ci` and the base profile have the stand-in, with the harness's `InMemoryFileStore` `@Primary` in Seam 1; `sit` has the stand-in until its environment sets `ANNUALVA_AWS_ENABLED=true` with a bucket for each zone and a key, and then the S3 store, which refuses to start without them (validated properties). `S3FileStoreWiringTest` proves each case without Docker, `S3FileStoreAbsentTest` proves the S3 store is absent under `ci`, and `DevLocalArchTest` fails the build when a bean of `adapters.s3` lacks `@NotDevLocal`. The alternative, `@Profile("dev-mcc")` on the S3 store, would have to name every deployed profile the day one is wired, and would need the stand-in to carry a second profile expression that `DevLocalArchTest` does not allow; the property keeps the profile's name out of the adapter and lets a deployment turn it on with no code change.

3. **Credentials.** `annualva.aws.access-key-id` and `secret-access-key` are set only under `dev-mcc` (LocalStack's mock `test`/`test`). Unset, the SDK's default credential chain applies (an instance or task role in a deployed environment). With an `endpoint` set (LocalStack) buckets are addressed by path, since `localhost` has no wildcard host name; without one the SDK uses AWS's own addressing.

4. **The export zone has a bucket of its own** (provisional, `annualva-export-dev`), and the config key `annualva.aws.export-bucket` is new. The existing dev config named only two buckets, but ADR 0045 keeps the exports in a third zone that must not share a bucket with files the scanner has passed. The alternative, a prefix in the clean bucket, would let one lifecycle rule or one access grant reach both.

5. **Lifecycle expiry is the second line, set by the bootstrap script, not by the application** (provisional). `scripts/localstack-init/02-buckets.sh` expires quarantine objects after one day (a scan takes minutes; ADR 0021 decision 6) and export objects after two (the application removes an export after 24 hours, ADR 0045; S3 expires in whole days, so two days cannot cut a download that is still inside its 24 hours). The clean bucket has none: the application's disposal executor removes those objects before their records (ADR 0050), and the retention is the VA Cycle plus three years. The application creates no bucket, key or rule, so its credentials need only `s3:PutObject`, `GetObject`, `DeleteObject` and `kms:GenerateDataKey`/`Decrypt` on the one key. The buckets must not be versioned, or a delete would leave the bytes behind; the script does not enable versioning, and a deployed bucket needs the same.

6. **Tested against a real S3 and KMS.** `S3FileStoreTest` runs inside every `./mvnw verify` and needs Docker (it is not an on-demand platform-tagged suite: LocalStack, unlike the mock stack, needs nothing outside this repository). It starts LocalStack (`localstack/localstack:3`, the image compose uses) in Testcontainers with the repository's own init scripts copied in, so the key, buckets, default encryption and lifecycle rules the run book relies on are exercised. A second SDK client reads back what the adapter stored. It checks put, get and delete, each zone in its own bucket, that SSE-KMS is requested into a bucket that has no default encryption (so the bucket default cannot be what encrypted it), the lifecycle rules, refused keys, an unreachable store, a missing bucket, and, through a small in-process HTTP server that answers 200 without an encryption header, that such a store is refused and the object deleted again. Seam 1 is unchanged: the harness fake stays the only store, and `S3FileStoreAbsentTest` asserts it.

7. **What LocalStack does not prove.** LocalStack echoes the alias it was asked for inside an ARN rather than resolving it to the key id, so the test accepts either; it does not enforce IAM or bucket policies; and its KMS does not check that the caller may use the key. A bucket policy that denies `PutObject` without `aws:kms` is the deployed environment's backstop and is not tested here.

Not done here, on purpose:
- The scanner, mail, MCC service-client and account-status adapters, and the platform-tagged suite against the mock stack (ticket 51's other boxes, blocked on ticket 01).
- Deleting the `adapters.pending` package.
- Wiring `sit` or production: setting `enabled` there with real buckets and a role.
- Server-side encryption checks on `get` (the bucket's own default encryption and the put check cover writes).
