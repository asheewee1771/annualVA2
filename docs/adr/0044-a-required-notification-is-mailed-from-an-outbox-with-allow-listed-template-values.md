# A required notification is mailed from an outbox, with allow-listed template values only

Status: accepted (item 2 provisional, awaiting a human decision)

Ticket 37 (stories 91 and 94, with the plumbing for 88 to 90) sends the required notifications by email through the organisation's mail relay (MCNS, assumption A-9). It adds one migration (V137), one boundary port (`MailRelay`), an outbox and its dispatcher in the `notification` module, and the capturing mail relay of the Seam 1 harness. Tickets 38 (reminders) and 39 (bounces) build on the outbox.

1. **One notification, two channels.** Mail goes out through the same port and listeners as the in-app list (ADR 0043): `Notifications` writes a notification and, when its action is a required message, queues one `mail_outbox` row for it in the same transaction. A mail therefore exists exactly when its notification does: a refused or rolled-back move queues nothing, and a notification that cannot be written queues no mail either. The outbox row holds no address and no value of the message; the recipient, the System, the state, the action, the due date and the link are read from the notification, the Register and `app_user` when the mail is sent. A reminder (ticket 38) is a notification like any other and is mailed the same way.

2. **Which messages are mailed** (provisional). The spec's required messages are deadline reminders, Overdue, Return for Rework, Disputed and Register changes, and story 93 makes Endorsed and Carried Over FYIs for the weekly digest. So `REWORK` (which carries what is Disputed, ADR 0043 item 6) is mailed with the `RETURNED_FOR_REWORK` template; `SUBMIT_OVERDUE`, `REVIEW_OVERDUE` and `ENDORSE_OVERDUE` with `OVERDUE`; `SYSTEM_MOVED`, `SYSTEM_TRANSFERRED_TO_YOU` and `SYSTEM_TRANSFERRED_FROM_YOU` with `REGISTER_CHANGE`. A submit (`REVIEW`, to the Cyber Manager) and a pass to endorsement (`ENDORSE`, to both VA POCs) are neither required nor FYI in the spec, and MCNS onboarding (ticket 57) lists no template for them, so they stay in-app only: the reminders of ticket 38 mail those people before their windows end. Mailing them is a template constant, a configured id and a CHECK widening. `MailTemplate.of` is the one exhaustive switch over `NoticeAction` that says how each is mailed (its template and, for a Register change, the `change_kind` wording), so a ticket that adds an action (Withdrawn in 43, mailed as `REGISTER_CHANGE` with "Withdrawn"; the Exemption decision in 40) must say which template it is mailed with, or none.

3. **The relay port and the allow-list.** `MailRelay.send(recipient, templateId, values)` takes only the relay's id of an onboarded template and the values it fills; the application never sends a subject or a body. It answers `Accepted(messageId)` or `AddressRejected`, and throws for anything that may pass. Before calling it, the application maps the logical template to the configured id (`annualva.mail.templates`, one per `MailTemplate`; the application refuses to start without one) and builds the values (`MailValues`): `system_id`, `system_name`, `state` (the state's name as the screens show it, now `SubmissionState.label`), `action` (the app's sentence), `due_date` (written `d MMMM yyyy`), `link` (the configured app address followed by the app path) and, for a Register change, `change_kind`. There is no other key, so nothing a person types into a VA Submission and nothing read from a report can reach a mail, and a forwarded email leaks no Finding (story 91). The action, the change and the due date come from typed fields in the app's own words. Of the values read from the database as text, the state and the link are held to the app's states and paths by V136's own CHECKs, written once there; the System ID and name are the Register's, checked only when a file is uploaded, so before every mail they must pass the Register's plain-text rule (`RegisterText`, moved out of the preview builder so both use it). One that breaks it settles the mail `REFUSED` (logged with the key) and the relay is never called. The System name is the Register's plain text, which may hold `<` or `://`: MCNS onboarding (ticket 57, noted there) confirms that every template escapes what it substitutes. A due date is left out when none applies (a transfer's former SMO/Tech Lead). The mapping and the check sit on the application side of the port rather than in the production adapter, so Seam 1 proves them; the adapter of ticket 51 only speaks to MCNS.

4. **The dispatcher.** `MailOutbox.dispatch` (every 30 seconds through `MailDispatchJob` when scheduling is on; by hand in tests) first settles `FAILED` every claim that was a last attempt and whose lease ran out (logged `mail-abandoned` with the count), then hands over up to 50 due mails one at a time: each is claimed with `FOR UPDATE SKIP LOCKED`, its attempt counted and leased for five minutes in one statement just before its hand-over, and the relay is called holding no lock (ADR 0012). Leasing each mail just before its own call keeps a slow relay from letting a lease run out on a mail still waiting its turn; the relay adapter's timeout must stay below the lease (`MailRelay`). A claim takes only templates and actions the running build knows, so during a rolling deploy an older instance leaves a newer kind of mail alone. Each outcome is written only while the row is still the claim it read (same attempt, still `PENDING`): `SENT` with the relay's message id and the time, `REJECTED` when the relay refuses the address (ticket 39 flags SMO Unreachable from it), `REFUSED` by the allow-list, or, after a failure, the next attempt 1, 2, 4 and 8 minutes later and `FAILED` after the fifth. An outcome that finds its claim gone is dropped and logged `mail-claim-lost` (proven by a hand-over that outlasts its lease while another pass sends the mail). The lease must exceed one relay call and the first retry wait a second, or the application refuses to start; ticket 51's adapter sets its timeout below the lease (noted there), since a last attempt that outlasts its lease is otherwise given up on although the relay took it. A row whose dispatcher stopped part-way is claimed again when its lease runs out, or set `FAILED` if that was its last attempt (both proven by stopping the dispatcher mid-call in Seam 1). Delivery is at least once: a dispatcher that stops after the relay took a mail but before recording it sends that mail again.

5. **Nothing personal in the logs.** Log lines name the outbox id, the attempt, a fixed `event.action` (`mail-send-failed`, `mail-abandoned`, `mail-address-rejected`, `mail-refused` with the refused key, `mail-claim-lost`, `mail-record-failed`) and the exception type; never a recipient address or a value of the mail. A claimed row's `toString` leaves the address out. Sending is not audited, as writing a notification is not (ADR 0043 item 5).

6. **Boundary and harness.** `MailRelay` is a boundary port implemented only under `sg.annualva.adapters` (architecture test); until ticket 51, `UnwiredMailRelay` fails every call, so a mail is tried five times and kept as `FAILED`. The Seam 1 harness replaces it with `CapturingMailRelay`, which records each accepted message with its template id, values and message id, and has a reject-address knob, a fail-the-next-calls knob, a hook that runs inside the next call before it answers, and a knob that stops the dispatcher mid-call (an `Error` nothing in the application catches, standing for an instance that died). A test-only endpoint shows the outbox until a delivery read exists (ticket 39).

Not done here, on purpose:
- Reminders (ticket 38), bounce handling and SMO Unreachable (ticket 39), the template onboarding and SIT ids (ticket 57), and the MCNS client with its rate limiter (ticket 51).
- A digest of FYI events (story 93, Release 2) and a cc: a copy to a Cyber Manager or VA POC is its own notification and mail (ticket 38).
- Skipping a VA POC pair's mail once the other VA POC has handled it before the mail went out.

Consequences:
- A new mailed kind is a `MailTemplate` constant, a migration widening `mail_outbox_template_check`, and a template id in every profile's `annualva.mail.templates` (and `ANNUALVA_MAIL_TEMPLATE_*` for the base profile).
- The outbox names notifications by foreign key, so the test reset deletes it before them, and a later retention ticket (49) disposes of it with them.
- Every deployed profile needs `ANNUALVA_APP_URL` and the three template ids; `sit` has placeholders until ticket 57 records the real ones.

Amends ADR 0043 item 1 (the outbox adds the retry it promised) and ADR 0016 (the Register's System ID and name rule is `RegisterText`, shared with the mail allow-list).
