# A VA POC return is the return at the endorsing step, with a required comment

Status: accepted (items 1, 2 and 4 decided 2026-10-25, and the migration ordering in item 6, docs/agents/reviewer-decisions.md)

Ticket 35 (stories 66 and 63) lets a VA POC return a VA Submission Awaiting Endorsement to its SMO/Tech Lead with a comment, to challenge something the Cyber Manager confirmed; the SMO/Tech Lead's resubmission then goes through the Cyber Manager again. It adds two migrations (V26, V31), no endpoint, no module and no new screen. The command is in `submission`, built from what tickets 30, 32, 34, 36 and 41 left: the return records of ADR 0039, the step gate of ADR 0042, the re-review rule of ADR 0040, the notifications of ADR 0043 and the closed-Cycle refusal of ADR 0044.

1. **One endpoint, the step the caller acts at** (decided 2026-10-25). The ticket names `POST /api/submissions/{id}/return`, the Cyber Manager's endpoint, so it now admits `CYBER_MANAGER` and `VA_POC`, and `Submissions.returnForRework` picks the step: a caller with only one of the two roles returns at that role's step; a caller with both returns as the System's Cyber Manager while it is not Awaiting Endorsement, and as a VA POC otherwise (or when they are not its Cyber Manager). So each meets the refusals of the step they act at: a VA POC returning a VA Submission In Review is `409 invalid-transition` (reason `state-not-endorsable`), a Cyber Manager returning one Awaiting Endorsement is `409 invalid-transition` (reason `state-not-reviewable`), as before. Only a caller with both roles has the VA Submission located before the step-up check; a VA POC's step-up still comes before any lookup (ADR 0042 item 1). The alternative is a separate endpoint (`/va-poc-return`), which needs no dispatch but departs from the ticket's path.

2. **The VA POC's return goes through the endorsing step's gate** (builds ADR 0039 item 5 and ADR 0042 item 2). It is a step-up action (intent `submission-return`, the spec's step-up list names "return"), then `Submissions.atStep` with the `ENDORSING` gate, whose refusal sentence now says "endorsed or returned by a VA POC": the access guard on `Need.ENDORSE`, then, with the row held exclusively, `SegregationOfDuties.require` at step `ENDORSE`, the closed-Cycle refusal (`cycle-closed`, ADR 0044) and the state. The caller is recorded at `ENDORSE`, so a VA POC who returned it may endorse the resubmission but never review it, and a VA POC who reviewed or submitted it, or whom the Register names its SMO/Tech Lead or Cyber Manager, leaves the return to the other VA POC. The move is the return's own statement (`MOVED`, with `OVERDUE_AFTER_MOVE`), so Returned for Rework after a VA POC return waits on the Review Window and is Overdue after `review_due` like any other (spec, decisions of 2026-09-29). Both returns now share one private `returned` path that keeps the return, moves the state, audits and publishes; only what each attaches differs.

   *Decided 2026-10-25 (docs/agents/reviewer-decisions.md):* the return attaches nothing. Awaiting Endorsement, everything is confirmed, so there is nothing Disputed to attach; the VA POC's comment says what is challenged, and no review changes, so the SMO/Tech Lead proposes again for what the comment names, which puts it back to `PENDING`. Letting the VA POC name the Findings or justifications they challenge would need a `submission_return_item` with no review behind it (V23 requires one) and a way to put a confirmed item back in the rework queue; it is a later change if the PO wants it.

3. **The comment is required.** Nothing else explains a VA POC's return (ADR 0039 item 3 said so), so a missing comment, or one with nothing left once cleaned by `ReportText.cleanLongText`, is `400 invalid-field` naming `comment`, and one over 4000 code points is the same; V26 widens the step check to `ENDORSE` and adds `submission_return_endorse_comment_check`, so the table holds the rule too. The one `returnComment` rule cleans, bounds and, for a VA POC, requires it. The comment is data: never logged, audited, put in an error body or in a notification (the tests check the audit entry and both notices). A field refusal writes no `SUBMISSION_RETURNED` entry, as for the Cyber Manager's return.

4. **The Cycle matrix keeps the last reviewed date** (decided 2026-10-25; ticket 33 left it here, ADR 0037 item 5). A VA POC return leaves `passed_to_endorsement_at` as it was, so the matrix shows when the review last ended, with the reviewed milestone current again while it is Returned for Rework and In Review; the next pass moves the date. Clearing it would hide that the review ended once and lose the date the VA POC's challenge was about. The other reading (clear it, so the matrix shows "not reviewed" until the next pass) is a one-column change to the return's statement.

5. **Re-review only what changed, unchanged.** The resubmit is the ordinary submit (ADR 0032) to In Review. No review changed at the return, so after the resubmission only a Finding proposed again since is `PENDING` and listed by `changedSinceLastReview=true` (ADR 0040, written for this case), and the pass needs only those confirmed. A Seam 1 test runs the whole round: VA POC return, a new proposal, resubmit, re-review of the one changed Finding, pass, and endorsement by the VA POC who returned it.

6. **Audit, events and notifications.** A VA POC's return is `SUBMISSION_RETURNED` with `state_from` `AWAITING_ENDORSEMENT`, `state_to` and `count` 0; refusals carry `sod-conflict`, `state-not-endorsable` or `cycle-closed`. No detail key is new. The `SubmissionEvent` (Awaiting Endorsement to Returned for Rework) clears both VA POCs' endorsement item, handled by the returner (ADR 0043 item 4, already wired). `WorkflowNotices` now tells, after the commit, the SMO/Tech Lead (`VA_POC_REWORK`: "A VA POC returned the VA Submission: read their comment, rework it and submit it again.", linked to the rework screen) instead of `REWORK`, whose sentence names a Dispute a VA POC's return does not carry, and the System's Cyber Manager as the Register names them now, whoever passed it (`VA_POC_RETURNED`, linked to the review screen), as the ticket asks. Both are required messages (a return), so both are also mailed through ticket 37's outbox (ADR 0046) with the `RETURNED_FOR_REWORK` template: `MailTemplate.of` maps `VA_POC_REWORK` and `VA_POC_RETURNED` there, and the mail carries the notice's own sentence, never the comment. V31 widens `notification_action_check`; it is numbered after V30, which rebuilt that CHECK last, because the notification table (V27) does not exist yet when V26 runs on a fresh database. As first built (V135 and V141_35), both versions were below V144, already on the integration branch, so a database migrated past it needed Flyway's out-of-order mode or a reset to take them, as the run's ticket-numbered migrations already did (V130 landed after V133). Decided 2026-10-25 (docs/agents/reviewer-decisions.md): no environment turns `outOfOrder` on; once every ticket is merged and before release, every migration on the integration branch is renumbered into one clean sequence. Done: the migrations run V1 to V41 in their old order, and the README's "Migration numbers" maps the old names to the new.

7. **The screens.** The VA POC's endorsement view (`/va-poc/submissions/{id}`) shows Return for rework beside Endorse while it is Awaiting Endorsement: a labelled comment box with its classification label (IM8 dp-8), `required` and the server's `maxLength` (IM8 as-1), linked to the server's problem, and a button disabled while the box is blank. A missing step-up opens the app's step-up explanation, and the comment typed is kept across the fresh sign-in: read once as the page loads, tied to the VA Submission the sign-in came back to, and forgotten once its Return panel has read it, so it never fills another VA Submission's box (`takeRestoredDraft` leaves a draft saved for another action in place, as ticket 44 also made it). The two moves share one hook held by the screen, so neither can start while the other is under way. The SMO/Tech Lead's rework screen says whether the Cyber Manager or a VA POC returned it, shows the comment as text and, after a VA POC's return, explains that the queue may be empty and links the prepare screen, where any Finding can be proposed again.

Not done here, on purpose:
- Naming the challenged Findings on the return (item 2).
- Any Playwright scenario (ticket 53).

Consequences:
- `POST /api/submissions/{id}/return` has two callers and two sets of rules; the role and the state decide which, and its tests cover both.
- A VA POC who returned a VA Submission counts at the endorsing step, so the other VA POC is not needed for its endorsement.

Amends ADR 0039 items 1 and 3 (the return is shared with the VA POC's, whose comment is required), ADR 0042 item 1 (the endorsing gate is also the VA POC's return's) and ADR 0043 item 3 (a VA POC's return sends its own two notices); extends ADR 0046 item 2 (both notices are mailed as Return for Rework).
