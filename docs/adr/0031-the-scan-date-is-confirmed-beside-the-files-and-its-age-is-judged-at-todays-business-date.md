# The scan date is confirmed beside the file's, and its age is judged at today's business date

Status: accepted

Ticket 23 (stories 25 and 26) lets the SMO/Tech Lead confirm or correct the scan date and target the parser pre-filled for each report file, rejects a report dated after today in the pipeline, and makes the readiness check name every report file too old to submit. It adds one migration (V18), one endpoint and no module; the age rule lives in `ingestion`, where the files are, and reaches the readiness check in `finding` through a port. Submitting itself (and refusing it) is ticket 25's.

1. **The age check is the pipeline's last stage.** After the parse has pre-filled the scan date, `FileChecks` compares its business date in `Asia/Singapore` with today's (both from the `Clock` bean, through `CycleCalendar`, which `ingestion` may now read: ArchitectureTest gains that edge). A report dated after today is `REJECTED_FUTURE_DATED` (reject code `FUTURE_DATED`, audit code `future-dated`, a fixed sentence asking for the scan machine's clock to be checked and the report exported again). Its stages are `SCAN_CLEAN`, `TYPE_OK`, `SCHEMA_OK`, `REJECTED_FUTURE_DATED`: `SCHEMA_OK` in a file's history already meant the parser accepted its structure (a file the parser refuses never has it), so it shows the parse and the pre-fill came first; a future-dated file the parser refuses is `REJECTED_SCHEMA`. No `PARSED` stage is recorded for it, because `PARSED` means its Findings are kept, and they are not. A report that names no date is not refused for it. A Burp export time after today is in the future too. A future-dated rescan is rejected like any file and changes nothing (ADR 0029). The test of the fixed order (`UploadPipelineTest`) now covers parse, pre-fill and age after the schema check.
2. **The confirmation is kept beside what the file says.** V18 adds `report_file.scan_date_confirmed` (a `date`: the business date the person says the scan was made) and `target_confirmed` (1 to 200 characters, the bound of `target_from_file`), both or neither, and only on a `PARSED` file; the file's own values stay as they were, so a reader always sees both. A target is **edited** when the confirmed one differs from the file's, compared exactly after cleaning, or the file named none: it is flagged (`targetEdited`), never refused (the spec's Upload rules). A changed scan date is flagged too, not blocked (`scanDateEdited`, reviewer decisions, "A changed scan date is flagged, not blocked, and the confirmed date is still judged"): the confirmed date differs from the business date of the file's own, which for a Burp export is its export day, so one rule covers every format, and a date given for a file that names none is edited. The confirmed date is still the one the age rule judges (item 5), so a wrong file date can be corrected, and the flag shows the reviewer that it was; the review screens (ticket 28 onwards) read the same flag.
3. **`PUT /api/submissions/{id}/files/{fileId}/metadata`** (the SMO/Tech Lead of the System) takes `scanDate` (yyyy-mm-dd) and `target` and answers 200 with the metadata as it is now. Checks run in the order ownership and the file (another SMO's VA Submission, a missing file, or one of this VA Submission that is not `PARSED` (still in the pipeline, rejected, or supporting evidence) is the same 404, as the read is), the state (Draft or Returned for Rework, else 409 `invalid-transition`, audited `REFUSED` with `reason=state-not-editable` and the `file_id`), the fields (400 `invalid-field` naming the first wrong one: `scanDate` missing, not a date written yyyy-mm-dd, after today, or more than ten years before today; `target` missing, empty once cleaned to one line by `ReportText.cleanOneLine`, or over 200 characters; not audited), and last, in the one `UPDATE` that writes it (`WHERE pipeline_status = 'PARSED' AND superseded_by IS NULL`), that no rescan has replaced the file: a superseded file is history and is 409 `file-superseded` (audited, `reason=superseded`). Confirming again replaces both values. The ten-year floor is a chosen format bound that keeps the date real (IM8 as-1), the mirror of the proposals' ten years ahead; a scan that old blocks submitting anyway. A Cyber Manager, a VA POC and an Auditor get 403 from the role rule.
4. **The metadata says what each date is.** `GET` and `PUT .../metadata` return `fileId`, `scanDate` (the file's instant), `scanDay` (its business date, which the screen offers, so the browser never works out a time zone), `scanDateIsExportTime` (ADR 0025), `target`, `confirmedScanDate`, `confirmedTarget`, `scanDateEdited` and `targetEdited`. The read stays audited for every role (`FILE_METADATA_VIEWED`); the confirmation is `FILE_METADATA_CONFIRMED` with the `file_id` and the yes/no details `date_changed` and `target_changed` (the audit detail allow-list, V18, and `AuditDetail` gain a boolean value for them), never the values. No date or target is ever logged, audited or echoed in an error body (a sentinel test).
5. **The age rule and which date it judges.** `FileAges` (in `ingestion`, behind `finding.ReportFileAges`) takes the VA Submission's live report files (`PARSED`, not superseded: a rejected file, a replaced one and supporting evidence never count) in upload order and judges each by its **confirmed scan date, else the business date of the file's own**, at today's business date. A file is **too old** when that date is more than 90 days before today (`MAX_AGE_DAYS`; exactly 90 days old still counts). A file is **undated** when there is no date to judge: the report names none and none was given, or **the only date is a Burp export time**, which is not a scan date (CONTEXT.md: it is offered "for the SMO/Tech Lead to correct"); judging the export time would understate the age of a scan exported later. Confirming a date takes a file out of `undated`. These facts of a file (its business date, whether that is only an export time, the date judged, whether the target was edited) are worked out once, in `ScanFacts`, which both the metadata and the age rule read. The rule reads only the controllable clock, so the tests move the clock rather than rewriting samples.
6. **The readiness check names the files.** `GET /api/submissions/{id}/readiness` (ADR 0028) gains `tooOld` and `undated`, each a list of `{fileId, name, reportType}` in upload order, so submitting (ticket 25) can refuse with a message naming each file. They carry the name the person gave the file and no scan date, because a scan date is report content and the owner's readiness reads are not audited (ADR 0028 item 6); the dates are on the metadata read, which is. The readiness is composed in `Findings.readiness` from the counts and `ReportFileAges.of`, which runs in its transaction; `finding` defines the port and `ingestion` implements it, so the modules keep their downward order.
7. **The screen.** Each Scan Report card lists, below its report files and outside their live region, "Scan dates and targets": for every parsed report file that no rescan replaced, what the file says (for a Burp export, that it is only the export time), what was confirmed with an edited scan date marked "Scan date edited" and an edited target "Target edited", and a form with a date input and a target input (each with its classification label, IM8 dp-8, and the server's 200-character limit) pre-filled with the confirmed values, else the file's. A rejected file shows "Rejected: dated in the future" with the server's sentence. The Findings section shows, under the progress bar, the files too old to submit and those with no scan date yet, by name and Scan Report, asked for again after each confirmation. The browser decides no date rule; the server's problem is shown beside the form and marks the field it names.

Not done here, on purpose: refusing to submit (ticket 25 reads `tooOld` and `undated`, and the plan's "none future-dated or still scanning"), and any Playwright scenario (ticket 53).

Consequences: a Burp Suite file always needs its scan date given before its VA Submission can be submitted (once ticket 25 enforces `undated`); a file's age can be changed by correcting its date, which is audited (by id, with `date_changed`), flagged (`scanDateEdited`) and visible to the reviewer beside the file's own date; the readiness read now touches `report_file` as well as `finding`.

Amends ADR 0021 (the age check is the last stage, and `REJECTED_FUTURE_DATED` a rejected status), ADR 0025 item 7 (the export time is offered and flagged, and is not judged by the age rule until a scan date is given) and ADR 0028 item 6 (readiness also names the files too old or undated).
