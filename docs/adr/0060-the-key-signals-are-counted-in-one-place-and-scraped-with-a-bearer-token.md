# The key signals are counted in one place and scraped with a bearer token, and health says only that the process is up

Status: accepted as provisional for the repository's part of ticket 52 (IM8 lm-16, pm-6), by the user's decision of 2026-11-22 that ticket 52 lands as provisional. Three choices stay provisional until ticket 55 (choose products and non-functional targets, with a person) decides them: the scraper's credential (item 2), the alert thresholds (item 6) and where the token is kept in each environment. See "Decided 2026-11-22" at the end and `docs/agents/reviewer-decisions.md`.

Ticket 52 builds what the repository can build: the meters, the endpoint that exposes them, the run book that says what to do about each, and the architecture document. It does not choose a monitoring product, an alert manager or any target (availability, response time, recovery): those are ticket 55 (H3 in `docs/implementation-plan.md`).

1. **One class names every signal: `monitoring.KeySignals`.** A new leaf module, `sg.annualva.monitoring`, depends on no other module (`ArchitectureTest`, `ModuleConventionsArchTest`), so the modules that act can record a signal without a new dependency between them. Every counter is registered when the application starts, so a scrape shows it at zero before the first event. A name is a constant; a tag is a value of a closed enum (`kind`), never text from a request, a report or a person, and no meter carries an id (lm-19, the same rule as the audit log and the logs). The signals:

   | Meter (Prometheus name) | Kind | Counted where |
   |---|---|---|
   | `annualva_submissions_overdue{kind="submission"}` | gauge | VA Submissions flagged Overdue and not finished (counted by `OverdueSweep` at each sweep, item 4) |
   | `annualva_submissions_overdue{kind="not_started"}` | gauge | Systems flagged Overdue with no VA Submission in that Cycle, not retired |
   | `annualva_scan_failures_total` | counter | a scanner or file-store call of the scan that threw, or an `ERROR` verdict: counted once, at the port call (`MalwareScan.quarantine`, `submit`, `check`, `fetchUnchanged`, and `CleanFiles.put`), for a Scan Report file and the Register workbook alike |
   | `annualva_scan_timeouts_total` | counter | a file or workbook given up on after its third scan attempt |
   | `annualva_mail_failures_total{kind=...}` | counter | `send_failed` (each failed hand-over), `abandoned` (given up on), `record_failed` (the relay answered and the answer could not be written: the mail may go twice), `refused` (a value broke the allow-list), `address_rejected` (the relay refused the address: SMO Unreachable) (`MailOutbox`) |
   | `annualva_stepup_refusals_total{kind=...}` | counter | `required` (a sensitive action with no fresh sign-in; `StepUp.require`, where it is decided), `failed` (a step-up round trip that did not prove one; `AccessAudit`) |
   | `annualva_audit_write_failures_total` | counter | an audit entry that could not be written (`AuditLog`): in the caller's transaction, an insert the database refused, and the exception still propagates, so the action that the entry described rolls back; in a transaction of its own (`recordIndependently`), anything that failed from beginning that transaction to its commit |

   The JVM, HTTP-server and datasource meters Spring Boot registers stay as they are.

2. **The scrape is a bearer token on its own security chain** (provisional until ticket 55). The ticket says "authenticated `/actuator/prometheus`". A person's MCC SSO session cannot authenticate a scraper, and anonymous access limited by the network is not "authenticated", so `app.MetricsScrapeSecurity` is a second `SecurityFilterChain`, ahead of the application's, matching that one path: stateless (no session, no cookie), one credential, `Authorization: Bearer <annualva.monitoring.scrape-token>`, compared as two SHA-256 digests with `MessageDigest.isEqual`. A wrong or missing token is a 401 audited like any refused request (lm-4). The token is a secret with no default (ADR 0005, like the database password): 32 to 200 visible characters, checked at start, set only from `ANNUALVA_MONITORING_SCRAPE_TOKEN` (a mock under `dev-mcc` and `dev-local`, a test value under `ci`, left empty in `.env.sit.example` so a copy that is not filled in does not start), and left out of `toString()`. An environment that does not set it does not start, so no deployment exposes the metrics open or forgets to scrape them. No session of a signed-in person opens it, and the path with a trailing slash is not served at all (a 401 without a session, a 404 with one; `MetricsEndpointTest`), and the token opens nothing else: `management.endpoints.web.exposure.include` is `health,info,prometheus`, and the application's chain keeps every other `/actuator` path behind a session. Alternatives: a role on the existing chain (no way for a scraper to sign in; rejected), HTTP Basic (a second secret shape for no gain), mutual TLS at the ingress (stronger, and the deployment's to add on top; the token is what the repository can prove).

3. **Health is liveness only.** `management.health.defaults.enabled=false` and `show-details`/`show-components` are `never`, so `GET /actuator/health` answers `{"status":"UP"}` for the process and nothing about the database, the disk or any boundary. A database or scanner outage is a signal for the run book, not a reason for the platform to restart a healthy instance, and an anonymous caller learns nothing about the dependencies. `/actuator/info` stays anonymous (it exposes nothing; no contributor is configured).

4. **The Overdue gauges hold what the last sweep counted.** At the end of each pass the sweep runs two `count(*)` statements (static SQL in `SubmissionStore`) over the flags it has just set, and hands the counts to `KeySignals` once its transaction has committed; a pass that rolls back changes nothing. A scrape reads only memory, never the database, so a slow or unreachable database cannot hold the scrape past the scraper's timeout and lose every series with it (a query timeout on the scrape thread was the alternative: it bounds the statement but not the wait for a connection). A rise shows at the sweep that flags it, since only the sweep sets the flag; a fall (a VA Submission finished, a System retired or moved) shows at the next sweep, up to an hour later (hourly, ADR 0033, and once at startup). Before the first sweep after a start each gauge is NaN, not zero: Prometheus stores NaN as a sample, so the run book alerts on the value, not on `absent()`. A sweep that fails leaves the last counts in place, so an Overdue alert does not resolve because the database is down. The alert is on how long the gauge stays above zero, not on a rate.

5. **What a counter sees and does not see** (so the run book does not claim more than the code does):
   - An audit entry written in the caller's transaction whose transaction then fails at commit (a deferred constraint, a lost connection) is not an insert that failed, so it is not counted; the action rolls back all the same.
   - An entry written in a transaction of its own (`AuditLog.recordIndependently`: refusals, sign-ins, step-ups) is counted for any failure of that transaction, a failure to begin it (the database is down, no connection is free) and a failed commit included (`AuditFailureSignalTest`). The sign-in machinery and the refusal listener then swallow it (`AccessAudit` logs `audit-write-failed`): the person is still refused, and the counter and that log line are the only traces.
   - A scan failure is counted at the port call, once per call, whatever the caller does next. A store that cannot quarantine an upload is one failure and no timeout on both paths, since no scan attempt was made: a Scan Report upload answers `503 storage-unavailable` and a Register workbook `503 scan-timeout`, and neither is kept (`ScanSignalTest`, `RegisterScanSignalTest`). A scanner that answers `ERROR` is a failure at each answer; one that never finishes is a timeout and no failure. The Register workbook's scan counts into the same two signals as a Scan Report file's, so a scanner outage shows whichever path met it first. A database failure while the scan job records an outcome is not a scan failure.
   - A step-up refusal is counted where it is decided: `REQUIRED` in `StepUp.require` before the 403 is thrown, `FAILED` where the round trip is refused.

6. **Thresholds are starting values** (provisional until ticket 55). The run book's thresholds in `README.md` (any audit write failure; mail send failures sustained over 15 minutes; an Overdue count above zero for a day; and so on) are chosen from how each meter behaves, not from an availability or response-time target, because none exists until ticket 55. They are the first values for the monitoring product to be loaded with, and they change by editing the run book.

7. **The architecture document is generated and checked.** `docs/tech-architecture.md` (and `.html`) follows the `/tech-arch-doc` layout and is a point-in-time document. Its tables and diagrams that can be read from the code (the modules and what they import, the endpoints and public types, the ADR index, the schema) sit in marked blocks that `python scripts/refresh-tech-arch-doc.py` rewrites, and its `--check` mode says whether any block is stale; the prose around them is written by hand and the script leaves it alone. `DocumentationCompletenessTest` (in the architecture test package, no HTTP) fails the build when the document does not name every module package, boundary port and adapter class, Spring profile, ADR and table in the repository, so a new one cannot be merged without the document being refreshed. It checks that names are present, not that the prose is right, and it does not notice a migration that only alters a table or an ADR whose title or status changed (the script's `--check` does): a person reads the prose at the doc review.

Not done here, on purpose:
- A monitoring product, dashboards, alert rules in a product's syntax, a pager or an on-call rota (ticket 55; the run book gives the content).
- Request-rate and latency alerts: the server's `http_server_requests` meters exist, but without a target there is nothing to alert on.
- A distributed trace or log shipping; lm-15's ECS logs are unchanged.
- Alerting on the sweep or a scheduled job not running at all (no heartbeat meter): the Overdue gauge staying flat after a window has passed is the only hint today.
