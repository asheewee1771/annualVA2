# Scan Report files are quarantined, scanned and checked in a fixed order before anything reads them

Status: accepted

`POST /api/submissions/{id}/files` (the SMO/Tech Lead of the System; multipart `reportType`, `kind` and `file`) takes a Scan Report file, quarantines it and answers `202` with the file in status `QUARANTINED`. A scan job then runs the stages after it. `GET /api/submissions/{id}/files`, `GET .../files/{fileId}` and `GET .../files/{fileId}/content` read the status, the list and the bytes. Ten decisions follow.

1. **The stage order is fixed and observable.** Quarantine, malware scan, type allowlist, schema check; the parser, pre-fill and age tickets append after them. A file's `stages` (table `report_file_stage`, one row each time it enters a status) lists the order it went through, and the tests prove it by files that would fail two stages: malware inside a disallowed type is `REJECTED_MALWARE`, a disallowed type that is also malformed is `REJECTED_TYPE`, and a file still with the scanner is never type-checked.
2. **Two new boundary ports, one `scan` module.** `FileStore` (zones `QUARANTINE` and `CLEAN`; keys are random ids, never file names) and `MalwareScanner` (`submit`, `check`, `fetchClean`; verdicts `PROCESSING`, `CLEAN_UNCHANGED`, `CLEAN_SANITIZED`, `BLOCKED`, `ERROR`). The module `scan` (below `register`, above `boundary`) is the only caller: it holds quarantine, the unchanged-must-match-the-upload-hash rule, the three-attempt limit and a synchronous scan for small files, so the Scan Report pipeline and the Register upload (decision 9) share them. Until ticket 51 the production beans are `adapters.pending.Unwired*`, which fail closed (nothing is stored or called clean, and no setting skips the scan) so that the application still starts.
3. **The scan is asynchronous, driven by a job, and makes no remote call inside a transaction.** `ScanPoller.poll()` is a plain bean; `ScanPollerJob` (`@Scheduled`, only when `annualva.scheduling.enabled`, every `annualva.scan.poll-interval`, 10 s by default) calls it, and Seam 1 tests call it through a test endpoint with the controllable clock (ADR 0012). A file is read, the scanner and the store are called with nothing held, and the outcome (status, stages, reject code, clean key, attempts and, for a rejection, its audit entry) is written in one short transaction guarded by the status and attempts that were read (`WHERE pipeline_status = ... AND scan_attempts = ...`), so a pass that lost a race, or two instances, never both apply an outcome. This replaces the `SKIP LOCKED` claim ADR 0012 sketched, which held a row lock across the scanner and store calls. At most `annualva.scan.max-in-flight` (10) files are with the scanner; the oldest quarantined files whose next attempt is due take the free slots. A failure writing one file's outcome is logged by id and leaves that file as it was; it never stops the others. What a lost race does to blobs: the clean copy is stored under the file's own id, so the pass that lost may have written the very bytes the winner's row points at. It removes its copy only when the write threw (nothing points at it) or when it re-reads the file and the file does not hold that clean key (the winner rejected it, or started another attempt); if the winner holds the key, the copy stays and downloads keep working. A delete that fails in that case is logged by file id and left to the quarantine bucket's lifecycle expiry (ticket 51), since no row keys it; the sweep also removes any clean copy of a rejected file while that file's quarantine key is still held. The sweep orders files by when they were last tried and moves a file whose delete failed to the back, so files that cannot be deleted never starve the others.
4. **Attempts.** An attempt times out after `annualva.scan.attempt-timeout` (10 minutes, by the `Clock` bean) and the file is submitted again; a scanner `ERROR` verdict counts as an attempt, and so does a submission that cannot be made, for any reason (a plain runtime exception from an adapter, not only a `BoundaryFailureException`). A failed submission is paced like a failed check: its attempt began when it failed, so the next one waits the attempt timeout and a scanner that is down is not tried three times in a minute. After the third attempt (the first and the two retries of the Upload rules) the file is `REJECTED_SCAN_TIMEOUT` with the message that the upload was rejected and should be uploaded again (story 27). A scanner that cannot be asked for a verdict, or a clean copy that cannot be fetched or kept, is treated as still working, so the attempt runs out its time and a file that keeps failing is rejected after the third. No file can hold a scan slot for ever.
5. **A scan result must match the upload, and a changed file is not accepted.** `CLEAN_UNCHANGED` with bytes whose SHA-256 differs from the upload's is `REJECTED_HASH_MISMATCH`. `CLEAN_SANITIZED` (the scanner had to modify the file) is `REJECTED_SANITIZED` with the message that the file was modified during scanning and the original should be uploaded again; the altered copy is neither fetched nor kept and nothing can be downloaded. This is the human decision in `docs/agents/reviewer-decisions.md` ("A Sanitized scan verdict is a rejection, not an accepted copy"), which supersedes the plan's "Sanitized accepted with clean hash". The Register workbook follows the same rule (decision 9), through the shared `scan` module. The `MalwareScanner` contract says so, and ticket 51's adapter must map the scanner's Sanitized verdict to `CLEAN_SANITIZED`.
6. **Rejected files keep no bytes; malware is never retained; bytes go only after the commit and the key stays until they are gone.** Every rejected file's quarantined bytes are deleted, and the unchanged copy is stored only for a file that passed every stage (under the file's own id, `clean_key`), never for one the checks refuse. Deletion is never inside the transaction that records the outcome: the job deletes after the commit and only then clears `quarantine_key`, so a rollback never leaves a row whose bytes are gone, and a failed delete (malware included) leaves its key and is retried on every pass until it succeeds. A clean copy stored by a pass whose write failed is removed at once, and if that removal fails too, the next attempt overwrites it (same key) and the sweep of a rejected file removes it. This is the decision to record beside the retention rules (ticket 49): retention never has a rejected file's bytes to dispose of. Ticket 51 also puts a lifecycle expiry on the quarantine bucket as a second line.
7. **Type allowlist and per-type size limits (IM8 as-1).** The format comes from the bytes only: the root element's local name for XML (read with `SecureXml`, DTDs and external entities off) or the top-level keys for JSON. The file name and declared content type are never used.

   | Scan Report | Format | Sniffed as | Limit |
   |---|---|---|---|
   | Dependency-Check | XML | root `analysis` | 25 MB |
   | Dependency-Check | JSON | top-level `reportSchema`, `scanInfo`, `dependencies` | 25 MB |
   | Secure Configuration | XCCDF results | root `Benchmark` or `TestResult` | 25 MB |
   | Secure Configuration | SCAP ARF | root `asset-report-collection` | 50 MB |
   | Secure Configuration | Nessus | root `NessusClientData_v2` | 50 MB |
   | Burp Suite | XML | root `issues` (its internal DOCTYPE is accepted only as Burp writes it, never obeyed: ADR 0025) | 50 MB |

   A file of any other type, or of a format that belongs to another Scan Report, is `REJECTED_TYPE`; one over its limit is `REJECTED_TOO_LARGE`; both are decided before the file is read in full. The container ceiling is 50 MB per upload; at most 20 files (not counting rejected ones) per Scan Report and kind (`too-many-files`, 409). Evidence (`kind` EVIDENCE: PDF 20 MB and HTML 10 MB) is typed, limited and kept as ADR 0026 says; it is not parsed. The limits are proposals from the implementation plan for the human to confirm (assumption list, H3).
8. **Schema check.** The whole document is read once and not kept: a truncated or malformed document is `REJECTED_UNREADABLE`; an XML document nested deeper than 100 levels, or Dependency-Check JSON whose `dependencies` is not an array, is `REJECTED_SCHEMA`; JSON nested deeper than the JSON reader allows (500 levels) is unreadable. An entity declared in a DOCTYPE is never expanded, so an entity bomb or an external entity makes the file unreadable and nothing is loaded. The parsers of tickets 14 to 17 tighten this per format. Only a file at `SCHEMA_OK` (and later statuses) can be viewed or downloaded.
9. **The Register workbook is scanned synchronously (as-12).** `RegisterUploads` calls `MalwareScan.scanNow` before `RegisterSheetReader` reads anything: quarantine, submit, poll for up to `annualva.scan.sync-wait` per attempt, three attempts, discard. `POST /api/system-register/uploads` still answers `201` with the preview for a clean file, so the front end and the preview contract are unchanged; the file is small and the VA POC waits for the preview, so no pending state was added. A blocked file is `422 file-rejected-malware`, a scan that times out `503 scan-timeout` (the upload-again message), a mismatched result `503 scan-mismatch`; each is a `REGISTER_UPLOAD_REJECTED` entry with the fixed code. The empty and over 2 MB checks stay before the scan, because nothing is stored for them. Only the scanner's clean copy is read. ADR 0017 is updated.
10. **Access and audit.** Uploads: `hasRole('SMO')` and the access guard with need `SUBMIT` (another SMO's VA Submission is `404`, a Cyber Manager or VA POC `403`); only in Draft or Returned for Rework (`409 invalid-transition` otherwise; the states are named as the table holds them because the enum has no constant for the second yet). Upload is also a URL-level rule (`POST /api/submissions/*/files` needs the SMO role), so a file of up to 50 MB is not spooled for anyone else. Reads and downloads: anyone who may see the System; a file that is not clean, was rejected, belongs to another VA Submission or is the caller's to be denied is the same `404`. Audit: `FILE_UPLOADED` (SUCCESS, or REFUSED with a fixed reason), `FILE_REJECTED` (written by the job, no actor, fixed `reject_code`), `FILE_DOWNLOADED` for every download (written in a short transaction that ends before the bytes, up to 50 MB, are read from the store, so a slow download holds no pooled connection), and `FILE_VIEWED` for a read of status or the list by anyone but the System's own SMO/Tech Lead, whose polling carries no report content (the same rule as reading a VA Submission, reviewer-decisions.md). Entries hold ids and fixed codes only. File names are cut to the part after any path and then allowlisted (letters, digits, `.`, `_`, `-`, parentheses and the ordinary space are kept, every other character becomes `_`, at most 100 code points), and are returned and offered for download as data; they, the keys and the scanner tickets never appear in a log line or an error body.

Consequences: a rejected file's row stays until the retention ticket disposes of it; the download name is the person's cleaned name, served with the generic content type and as an attachment; the in-flight cap is counted from the table at the start of a pass, so two instances could briefly exceed it by a file or two; the status endpoint is polled by the prepare screen every three seconds while a file is on its way.

Amended by ADR 0022: the parse stage follows the schema check for a format that has a parser (status `PARSED`), and a file is viewable and downloadable at `SCHEMA_OK` or `PARSED`.

Amended by ADR 0023: XCCDF results and ARF files have a parser too (status `PARSED`), and a report over the Findings caps is `REJECTED_TOO_MANY_FINDINGS`, not `REJECTED_SCHEMA`.

Amended by ADR 0026: a file of kind EVIDENCE (a PDF or HTML report) skips the schema check and the parse and rests in `READY`, which is viewable and downloadable like `SCHEMA_OK` and `PARSED`.

Amended by ADR 0029: a parsed report file can be replaced with a rescan (`POST .../files/{fileId}/replace`); once the rescan is parsed the old file is superseded (`superseded_by`), stays viewable and downloadable, and no longer counts against the 20 files.

Amended by ADR 0030: a report file (`kind=MACHINE_READABLE`) is refused with 409 `wrong-report-mode` when its Scan Report is marked not applicable or for Findings entered by hand, checked in the transaction that keeps the file with the Scan Report's row held; supporting evidence is accepted in every mode.
