# A Burp Suite issue export is parsed in the pipeline into Findings keyed by type, host and path, with a confidence

Status: accepted

Ticket 17 adds the fourth and last parser behind the pipeline (ADR 0022 added Dependency-Check, ADR 0023 SCAP, ADR 0024 Nessus): a Burp Suite XML issue export (an `issues` root), uploaded as the Burp Suite Scan Report, is parsed in the settlement transaction into Findings, and the export time and the hosts it names are kept for the SMO/Tech Lead to confirm. It adds one migration (V12, the confidence column) and, before the parser, a behaviour-preserving extraction of what the three XML parsers had each copied (item 10). Eleven decisions.

1. **One parser, streamed, reading only where the format puts an issue.** `parser.burp.BurpXmlParser` is behind `ReportParser` for `ReportFormat.BURP_XML`. It walks the document through `XmlCursor` and goes only into `issues/issue`; of an issue it reads `type`, `name`, `host`, `path`, `location`, `severity` and `confidence`, each with a bound (type, severity and confidence 100 characters, anything else 4,000, over which the file is refused). Everything else is skipped without being looked at: above all `requestresponse`, the requests and responses of the scan, which are nearly all of a real export (base64 or raw HTTP, and one can be tens of megabytes), plus the background, references and detail texts. Nothing from a request or response is built, kept, logged or said back; a test puts a sentinel in them and proves it appears nowhere. An issue-like element inside a wrapper, a request or another issue, or an `exportTime` on any element but the root, is never read.
2. **The DOCTYPE is allowed only as Burp writes it.** The reader never loads or obeys a DTD (`SecureXml`, unchanged: DTD support off, no external entity, no schema), so an entity declared in a DOCTYPE is never expanded and a reference to one is an unreadable file, found by the schema check before the parser runs. Burp's export carries an inline DOCTYPE of `ELEMENT` and `ATTLIST` declarations, so the parser checks the start of the file (the first 32 KB, as bytes) against one anchored pattern: an optional byte order mark and XML declaration, comments, an optional DOCTYPE named `issues` with no external id (`SYSTEM`, `PUBLIC`) and with no internal subset or one made only of `ELEMENT` and `ATTLIST` declarations (no `%` or `&` in them), more comments, and the start of the `issues` root. Anything else in the prolog (an `ENTITY` or `NOTATION` declaration, a processing instruction, a second DOCTYPE, a DOCTYPE hidden behind a comment, a root that starts after 32 KB, which is about ten times a real Burp prolog) is `REJECTED_SCHEMA`, even though the reader would have ignored it; none at all, an empty one, Burp's own and comments around it are accepted. The check is made on the bytes and not on the DOCTYPE text the StAX reader reports, because the JDK reader returns only the tail of a DOCTYPE longer than about 16 KB (measured), which would let an `ENTITY` declaration hide at the front of a long one; the pattern's loops are possessive so that no input makes the matcher recurse (a 20 KB comment and a 19 KB DOCTYPE are tested). Burp writes UTF-8, so the pattern is ASCII on purpose: an export in UTF-16 or UTF-32 is refused on purpose, with nothing echoed (tested, each encoding pinned): one with a byte order mark, UTF-32, and UTF-16 big-endian without one are `REJECTED_TYPE` (the type check, which needs an ASCII `<` first, cannot sniff them); UTF-16 little-endian without a byte order mark (the form a naive check would miss) gets past the type and schema checks, because the StAX reader detects the encoding, and is `REJECTED_SCHEMA` here. This is the ticket's "allowing only Burp's internal DTD subset with entity-expansion limits": nothing is ever expanded, so there is no expansion to limit. **The ticket's parenthesis "every other format forbids DOCTYPE" is not what ADRs 0021 to 0024 built**: the other formats' readers skip a DOCTYPE that declares nothing (tests for SCAP and Nessus say so) and refuse an entity reference to one that declares something. That is unchanged here; making the other three refuse every DOCTYPE is a one-line check per parser if the reviewer wants it.
3. **The shape is checked by the parser, and a file that is not that shape is `REJECTED_SCHEMA`.** The type check decides `BURP_XML` from the root element's local name `issues` alone (another root is `REJECTED_TYPE` for a Burp upload, and a Burp file is `REJECTED_TYPE` for another Scan Report). The parser then refuses an issue with no type id or no host, a type id or host containing `|` (which could make two keys read alike) or over its bound (type 100, host 500 characters), a normalised path over 1,000 characters, a value over its read bound, a value that holds markup where text belongs, an `exportTime` over 100 characters, and a DOCTYPE as item 2 says. A file refused by the parser ends `SCAN_CLEAN`, `TYPE_OK`, `REJECTED_SCHEMA`, never `SCHEMA_OK`; a truncated or malformed one is `REJECTED_UNREADABLE`. An export with no issues is accepted (`PARSED`, no Findings): it says a scan found nothing, and the pre-fill confirmation (ticket 23) is where a person sees that. The root's namespace is not checked (Burp writes none; unverified until ticket 58).
4. **The Finding key is `burp|<type id>|<host>|<normalised path>`, with an occurrence for each location.** The type id is Burp's `type` (a number), the host is Burp's `host` text (scheme and host, as Burp writes it) trimmed and **lower-cased**, and the path is Burp's `path` **normalised** so that the same page is the same Finding in the next scan: the query string and fragment are removed (a parameter's value changes between scans), path parameters (`;jsessionid=...`) are removed from every segment, repeated slashes become one, a trailing slash is dropped (the root stays `/`), a leading slash is added, the hex digits of percent escapes are upper-cased, and a missing or empty path is `/`; the case of the path is kept (a server may tell `/A` from `/a`). A key is never cut, so a part over its bound refuses the file. Two issues of one type on one page are one Finding, and each distinct `location` (Burp's `/search [q parameter]`, the parameter or header it was found in; the normalised path when Burp gave none) is an occurrence of it, merged by `Occurrence.merge` when the same location is read twice. The identifier the list shows is the issue name (cut to 1,000 characters because it only describes the Finding), else the type id; the subject (`packageOrRule`) is the host and path. The parameter or cookie a Finding was found in is therefore not part of its identity: a new parameter on a known page is another occurrence of a known Finding, not a new Finding (the cost is a Finding a person already dealt with absorbing it; the alternative, a key per parameter, would make every renamed parameter a new Finding and is not what the spec says: issue type plus host plus path).
5. **Severity is Burp's own; unrated is Medium.** `High`, `Medium` and `Low` are those levels, `Information` is Informational (ticket: "Information maps to INFORMATIONAL"), all in any case and trimmed; the words `Info`, `None` and `Critical` are read as `Severity.ofLabel` reads them (Burp writes none of them); a missing element, an empty one or any other word (including a digit) is **Medium**, as for SCAP and Nessus and unlike Dependency-Check's High (a plan choice: implementation plan section 2.4 names no Burp rule). A Finding's severity is the highest of its occurrences. The mapping is `Severity.ofBurp`, with the other tools' (`ofScap`, `ofNessus`) beside it, so the scale and the unrated policy live in `Severity` and in no parser.
6. **Confidence is stored on the occurrence and shown on the Finding.** Burp's `confidence` is `Certain`, `Firm` or `Tentative` (`Confidence`, most sure first), in any case and trimmed; a missing element, an empty one or any other word is **no confidence** (null), not Tentative and not Certain: a file that does not say is not assumed to be either, so ticket 30 never offers a shortcut on a guess. Migration V12 adds `finding_occurrence.confidence` (null, or one of the three, by a check constraint), kept on the occurrence for the reason `did_not_complete` is (ADR 0023 item 6): one Finding is read from several places and files with different words, and a stored copy on the Finding could disagree. **A Finding's confidence is the most sure of its places that have one**, worked out when the list reads it (`FindingStore`'s page query, an ordered sub-select) and returned as `confidence` on each Finding of `GET /api/submissions/{id}/findings` (null for every Finding of another Scan Report, and for a Burp one whose places say nothing). So a Finding is Tentative only if every place that says anything about it says Tentative, and a place that says nothing does not weaken one that does; the same place read twice takes the more sure of the two words (`Occurrence.merge`), as it takes the worse severity. **For ticket 30**: show `confidence` beside the severity; a Finding with `confidence = TENTATIVE` is the one the screen suggests marking False Positive (the Finding Status rules, which allow False Positive for any Finding with a justification, are ticket 30's); the per-place word is in `finding_occurrence.confidence` if it needs to show which place was Tentative (the Findings list does not return places yet). The Findings list UI that shows it is ticket 19's.
7. **The scan date is the export time, flagged; the target is the hosts.** The date offered is the `exportTime` attribute of the `issues` root (the only date Burp writes: `Tue Jul 20 10:00:00 SGT 2027`, Java's own date text with the abbreviated zone of the exporting machine), which is when the file was exported and not when the scan was made. `ReportDates` now reads that form too (the weekday must agree with the date, as for Nessus), as well as ISO forms and the zone-less form. A zone abbreviation is read by Java's own table, in which a few belong to more than one zone (`CST`, `IST`), so the instant can be hours out; an abbreviation Java does not know, or no date, is no date. The metadata read (`GET .../files/{fileId}/metadata`, audited as before) returns a new `scanDateIsExportTime`, true for a Burp file and false for every other format: it is derived from the file's detected format (`ReportFormat.scanDateIsExportTime`), so nothing is stored and no migration is needed. The target is the distinct hosts the issues name (lower-cased, in order, at most 50, joined with a comma and cut to 200 characters), gathered by `ScanFacts` as for SCAP and Nessus.
8. **Limits.** The size limit is ADR 0021's, 50 MB, which is also the request ceiling, so a larger file is refused with 413 at the upload and nothing is kept. The caps inside a file are ADR 0022 item 9's (accepted by a human on 2026-10-14): `FindingsBuilder` counts them and the parser calls it without counting itself, so a report over a cap is `REJECTED_TOO_MANY_FINDINGS` with the accurate message; the cap cases are proved once, for Nessus. The Burp-specific proofs are a 49 MB export (one request of 30 MB in a single base64 text, then issues with 100 KB requests, all skipped, under the surefire 1 GB heap), a value of 8 MB refused without being built whole, and the depth guard for the subtree a Burp parser skips. The web client's too-large hint for a Burp Suite file names the 50 MB limit and says to export the issues again without the request and response bodies.
9. **Every format now has a parser.** `ReportFormat.parser()` is no longer nullable, and the branch in `FileChecks` that left a file waiting at `SCHEMA_OK` for a parser that did not exist is gone. `SCHEMA_OK` stays in the status list and the stage history (every file still passes through it, and files and constraints written earlier name it) but no file rests there.
10. **Shared code extracted first, with no change of behaviour.** The three XML parsers each copied a leak-safe parse wrapper, a reading holder and the child-walk loop. Now: `XmlCursor.read(bytes, walk)` is the one wrapper (the cursor is closed, and a reader failure is an `UnparseableReportException` with none of the reader's message; a refusal the walk makes passes through); `XmlCursor.nextChild()` and `below(ancestor)` are the child loop (false at the element's end, an error if the document ends inside it); `parser.ScanReading` is the holder (the `FindingsBuilder`, the `ScanFacts` and a count of the sections the format requires, refusing a file with none). The severity scale and the unrated-is-Medium policy moved into `Severity` (`ofScap`, `ofNessus`, `ofBurp`), and the identity key of each tool is built in one place, `parser.FindingKeys` (`dc|`, `scap|`, `nessus|`, `burp|`), with `FindingsBuilder.found(key, shown, place)` for a Finding whose identifier and subject are one text. SCAP and Nessus use all of it, and Dependency-Check uses the parse wrapper and `FindingKeys` only (its private target and scan-date handling, `MAX_TARGET` in `DependencyCheckFindings`, was not moved onto `ScanFacts`); every test of theirs passes unchanged. The refactor stopped where Burp had what it needed: the 200-character target cut that still exists in both `ScanFacts` and `DependencyCheckFindings`, the `NessusLimitsTest` runtime and the hard-coded surefire `-Xmx1g` are still open (ticket 16's list).
11. **Hardened XML, nothing from a report is said back, the sample and its limits.** No issue name, host, path, location, request or response reaches a log line, an audit entry or an error body; a rejection says the same fixed sentence whatever the file held (proved by Seam 1 tests with a sentinel, for a rejected file and for an accepted one whose request and response carry it). `backend/src/test/resources/samples/burp/issues-export.xml` is a hand-written reconstruction (five issues of four Findings, with Burp's DOCTYPE, requests and responses) labelled so in the file and in a README; it is not the output of a real scan, and **real Burp exports are untested until ticket 58** (plan H6), which should be treated as a gate for this parser before release, particularly for items 2, 4, 6 and 7 (whether `path` carries the query, the form of `host`, the words for `confidence` and `severity`, the `exportTime` form and the root's namespace, and whether an export made without base64 can carry a character XML 1.0 forbids in a request or response, which the schema check would refuse as unreadable).

Consequences: uploading the same export twice doubles every occurrence count until ticket 21's replace rule applies (as for the other parsers); a Finding is keyed by page, not by parameter (item 4); the export time is not the scan date and a person must correct it (ticket 23's confirmation screen shows the flag); a zone abbreviation can put the suggested instant hours out; the confidence is returned on the Finding but not yet shown by any screen (ticket 19 lists Findings, ticket 30 uses the confidence).

Amends ADR 0021: the Burp row of decision 7's table is parsed, not left at `SCHEMA_OK` ("its internal DOCTYPE is skipped, never obeyed" is now "accepted only as Burp writes it, never obeyed", item 2 above). Amends ADRs 0022 to 0024: `ReportFormat` has no null parser now; the XML scaffolding, the severity mapping and the key prefixes they copied or built are in `XmlCursor`, `ScanReading`, `Severity` and `FindingKeys` (item 10).

Amended by ADR 0031: the SMO/Tech Lead confirms or corrects the scan date and target (`PUT .../files/{fileId}/metadata`); until a scan date is given, a Burp export time is not judged by the age rule and the file is listed as `undated` by the readiness check.
