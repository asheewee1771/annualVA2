# Overdue is a stored flag set by an idempotent sweep, and the windows stay soft

Status: accepted

Ticket 26 (stories 42 and 71) flags a VA Submission, or a Not Started System, Overdue once its window passes without the next step. Overdue is a flag, not a state (CONTEXT.md): nothing locks, and an Overdue VA Submission takes every command it took before. It adds one migration (V20), one scheduled job and no endpoint. Six decisions follow.

1. **The flag is stored, with when it was set, and only the sweep sets it.** `OverdueSweep` (in `submission`, which owns Overdue) runs one pass in one transaction: it reads today's business date in `Asia/Singapore` and the instant from the `Clock` bean (ADR 0006) and flags what is due and not flagged yet. Reads never compare dates (ADR 0019 item 4). `va_submission` gains `overdue_since` (UTC), and `overdue` becomes a column generated from it (`overdue_since IS NOT NULL`), so the two can never disagree and no statement writes the flag itself. `GET /api/submissions/{id}` answers `overdueSince` beside `overdue`; the SMO inbox gains `overdue` on every item.
2. **Which window each state waits on, written once.** V20 defines the one rule as two SQL functions: `current_window_due(state, submit_due, review_due, endorse_due)` gives the last day of the window the state waits on (null for a state that waits on none), and `window_passed(state, submit_due, review_due, endorse_due, today)` says whether it has passed. Not Started and Draft are Overdue after `submit_due`; In Review and Returned for Rework after `review_due` (Returned for Rework even after a VA POC return, spec *Release 1 decisions*); Awaiting Endorsement after `endorse_due`. A window's last day is inside it, so the flag is set from the next business day. Endorsed, Exempted, Withdrawn and Not Endorsed are final, and Exemption Requested is frozen: none is ever flagged. Nor is a VA Submission whose System is retired: nobody can see or act on it until the Register's withdraw (ticket 43), so the sweep flags only those of the active Systems it lists (item 3), and `submission` still never reads `va_system` (reviewer decisions, 2026-10-23, "The Overdue sweep skips VA Submissions of retired Systems"). The dates are the ones the VA Submission was started with (ADR 0020 item 4).
3. **A Not Started System is flagged on a row of its own.** Not Started has no `va_submission` row, so `not_started_overdue` holds one row per System and VA Cycle with `overdue_since`. For every VA Cycle the app runs (`CycleCalendar.cycles()`) that has not closed (its phase on today's business date is not `CLOSED`, ADR 0015 item 3), each Quarter not Handled outside the app whose Submission Window has passed (`window_passed('NOT_STARTED', …)` with the Quarter's dates) flags the active Systems of that Quarter with no VA Submission in that Cycle. A retired System and one in a Quarter Handled outside the app are never flagged; what a Not Started System becomes when its Cycle closes is the Cycle lifecycle ticket's (41). Before Release 2 gives an added System its own windows, a System added after its Quarter's Submission Window is flagged on the next pass, so its SMO is reminded at once; `va_system.added_on` is deliberately not used, since it would also hide a real non-start by a System added late in its Quarter (reviewer decisions, 2026-10-23, "Not Started Systems are swept in every Cycle the app runs that is not closed"; ticket 38 notes it). The sweep acts for nobody, so it lists the Systems with `RegisterSystems.everyActive()`, which skips the access guard; `ArchitectureTest.onlyTheOverdueSweepListsSystemsPastTheAccessGuard` lets only the sweep call it. Starting is the move from Not Started: a VA Submission started for a flagged System is created Overdue with the System's `overdue_since` when `window_passed` says Draft's window has passed (the start's insert reads the row), so the flag is not lost between the start and the next pass and is not audited twice; the row stays as the record.
4. **Every move keeps or clears the flag through the same rule.** The flag belongs to the current window and is not a permanent "was late" mark (reviewer decisions, 2026-10-23, "Overdue clears when a submit moves into a window that has not passed"). `SubmissionStore.OVERDUE_AFTER_MOVE` is the one SET fragment for it: `overdue_since` stays only if `window_passed` holds for the new state (`:state`) on `:today`, and is cleared otherwise; the sweep sets it again when that window passes. A submit moves the VA Submission into the Review Window, so it keeps the flag only if `review_due` has passed as well. The submit's own `SUBMISSION_SUBMITTED` entry is the record of the move; clearing is not audited separately. The tickets that add the other moves (return for rework, pass to endorsement, endorse, an Exemption decision) put `OVERDUE_AFTER_MOVE` in their UPDATE and pass the new state and today's business date; a new state that waits on a window is added to `current_window_due` by a migration, and nowhere else. No statement compares a due date with today by hand.
5. **Idempotent, and safe with two instances, without a lease.** The update claims its rows with `FOR NO KEY UPDATE SKIP LOCKED` in id order and only where `overdue_since IS NULL`, so it never waits: a row a submit, an edit or another pass holds is skipped and flagged on the next pass. The Not Started insert is `ON CONFLICT DO NOTHING` in id order; it can wait on another pass's uncommitted insert of the same key, and then inserts nothing once that pass commits. Both passes take the keys in the same order, so they cannot deadlock. Either way a second pass, or a second instance's pass at the same time, flags nothing more. Each flag is one `SUBMISSION_OVERDUE` entry (SUCCESS, no actor) about the System and, when there is one, the VA Submission, with the `state` it was in (`NOT_STARTED` for a System; V20 adds the key), written in the pass's transaction, so a flag and its entry commit together. This is the "idempotent flag setting" of ADR 0012; the `scheduler_lock` row it mentions is not needed for this job.
6. **When it runs.** A pass reads the clock once: the instant, and today's business date from that instant, as the submit does; the Cycles are listed for that date (`CycleCalendar.cyclesOn(today)`), not read again. A VA Submission is looked at whatever its Cycle's phase, since its windows all end before the Cycle closes and the close (ticket 41) moves what is left to a final state; a Not Started System only in a Cycle that has not closed. `OverdueSweepJob` runs the sweep at startup and then an hour after each pass ends (`annualva.overdue.sweep-interval`, default `1h`) when `annualva.scheduling.enabled` is true, as the implementation plan has it. The windows are whole business days, so a flag lands within the hour after midnight in Singapore. Seam 1 tests move the clock and run a pass through `/api/test/jobs/overdue`.

Not done here, on purpose: the reminders and the weekly Overdue message (ticket 38), the Cyber Manager inbox's Overdue-first order (ticket 27), the VA POC board's Overdue count (ticket 33), the meter for Overdue (ticket 52), and new windows for a System added or moved mid-Quarter (Release 2); until then such a System is flagged by its Quarter's dates, and a System a Register apply moves to another Quarter keeps a Not Started flag already set (ticket 43 decides the Register's effects).

Consequences: every VA Submission row carries its flag time; the Overdue flag is read, never computed, by every screen, export and reminder that follows; an Overdue Draft uploads, proposes and submits like any other (no command looks at the flag).

Amends ADR 0019 item 4 (the inbox now answers `overdue`, for Not Started Systems too), ADR 0020 item 4 (`overdue` is set by the sweep, and a start takes a Not Started System's flag) and ADR 0032 item 3 (a submit keeps the flag only if the Review Window has passed).

Amended by ADR 0034: the Cyber Manager inbox lists Overdue first, then by the day the current window ends, read through `current_window_due`.

Amended by ADR 0049: a Not Started System a Register apply moves to another Quarter has its flag cleared while the new Quarter's Submission Window has not passed.

Amended by ADR 0050: the weekly deadline reminder reads the flag, and goes every 7 days after the Overdue message while it stays set.
