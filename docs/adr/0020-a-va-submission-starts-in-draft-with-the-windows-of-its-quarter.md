# A VA Submission starts in Draft with the windows of its Quarter, and the start is the submitting step

Status: accepted

`POST /api/submissions` (SMO/Tech Lead) starts the VA Submission for a System (story 19), and `GET /api/submissions/{id}` reads it. Five decisions follow.

1. **A `submission` module above `register` and `cycle`.** It owns `va_submission` and `submission_participation` (migration V8) and will own the state machine and the segregation-of-duties guard as the transitions arrive. It asks `RegisterSystems.active(id, need)` for the System (the access guard runs first, so a System the caller may not submit for, one that does not exist and a retired one are all `404`, ADR 0013) and `CycleCalendar.running(year)` for the Cycle. The SMO inbox (`dashboard`) reads it, so a started System shows as Draft; nothing else does. The architecture test names the arrows.
2. **One per System and Cycle, enforced by the database.** `unique (system_id, cycle_year)` and `INSERT ... ON CONFLICT DO NOTHING RETURNING id`: a second start, even a concurrent one, inserts nothing and answers `409 invalid-transition`. A System whose Quarter is Handled outside the app also answers `409 invalid-transition`: the inbox offers no action for it, and a submission there would later be counted. The spec states only the first case; this is the reading that keeps such Quarters out of counts, reminders and the Cycle close.
3. **Which Cycle.** The body may name `cycle`; omitted, it is the Cycle running today, or before the first live Cycle starts that Cycle, which is what the inbox shows. The inbox passes the Cycle on screen, so Start in the older of two open Cycles starts in that Cycle. A year the app does not run is `404`. A Cycle that is closing accepts a start; whether a closed Cycle refuses one belongs to the Cycle lifecycle ticket (41), when closing exists.
4. **Windows are copied, not looked up.** `submit_due`, `review_due` and `endorse_due` are stored on the row when it starts, from the Quarter the System is in at that moment (a start before the Quarter begins takes that Quarter's dates). Later changes to the System's Quarter do not silently move them; the Release 2 mid-cycle changes (a System added mid-Quarter, a move) decide when they are reset. The `state` column accepts all nine states a row can be in from the start (with Not Started, which has no row, they are the spec's ten), and the Java enum holds only those that exist (`DRAFT`), so a later ticket adds a constant and not a migration. `overdue` and `endorsed_late` are stored false until the tickets that set them (26 and 34); the start does not compute them.
5. **Starting is the submitting step.** The caller gets a `submission_participation` row at step `SUBMIT` in the same transaction, which is the record segregation of duties rests on. `GET` returns it as `acted`: step, user id and first time, never a name or email (lm-19). The start is audited as `SUBMISSION_STARTED` (SUCCESS) in the command's transaction; a refused start (`already-started`, `quarter-handled-outside-app`) is the same action with outcome `REFUSED`, written in a transaction of its own because the command's rolls back (ADR 0014). A 403 is audited by the refusal listener as for any other endpoint, and a 404 is not. A read of one VA Submission by anyone but the System's own SMO/Tech Lead (a Cyber Manager or a VA POC) is audited as `SUBMISSION_VIEWED` in the read's own (read-write) transaction, with the System and VA Submission ids and no detail, because story 84 asks for every view and a single record is not a list; the owner's own reads write nothing, a 404 or 403 is not recorded by this path, and the inbox and lists stay unaudited (ADR 0019). A VA POC who is also the System's SMO is its owner. This is the decision recorded in `docs/agents/reviewer-decisions.md`; reads that carry report or Finding content will be audited for every role.

Consequences: the inbox gains `submissionId`, the state `DRAFT` and the next action `PREPARE_SUBMISSION` (due on the submission's own `submit_due`); a Draft is listed under Needs your action. The Register's reset in the Seam 1 harness also clears submissions. A Register apply that retires or moves a System with a started submission is not handled here: Withdrawn and the Release 2 move rules arrive with the Register change effects ticket (43), and until then the row stays and its System id keeps resolving (a System is never deleted).
