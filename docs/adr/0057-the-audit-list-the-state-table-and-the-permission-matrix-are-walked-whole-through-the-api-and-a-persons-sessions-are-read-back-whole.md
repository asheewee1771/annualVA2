# The audit list, the state table and the permission matrix are walked whole through the API, and a person's sessions are read back whole

Status: accepted

Ticket 50 closes the spec's Testing Decisions for story 84 (an audit entry for every action), the VA Submission state table (every row, rejected transitions included) and IM8 ac-1, ac-2 and lm-4 (every role against every endpoint, the step-up list, every refusal audited). It checks what tickets 02 to 49 built against the spec rather than adding behaviour, and it fixes the one defect the check found.

1. **The state table is a table in the test** (`StateTableTest`). Each state, `NONE` (a System with no VA Submission) included, is reached through the real commands on SYS-F1; then every command the spec's table does not allow from it (20 commands: start, submit, request, review a Finding or a justification, both returns, pass, endorse, approve, reject, record and confirm a conditional VA, and the seven writes to prepared content) must answer `409 invalid-transition`, leave the state as it was and add one `REFUSED` entry of its action with a reason. Then the Overdue sweep runs at the end of week 2, week 4 and the Quarter, and the flag must be set exactly on the states the spec names. A second parameterised test makes each of the table's 29 moves (including the conditional Exemption's lapse back, the Register's withdrawal and the Cycle's close) and checks where it lands and its audit entry's `state_from` and `state_to`. A Withdrawn VA Submission's System is retired, so its SMO/Tech Lead's and Cyber Manager's commands answer `404` (their roles for it were revoked, ADR 0049), and only the VA POCs' answer `409`.

2. **The audit list is one walk** (`AuditCompletenessTest`). One test factory drives a VA Cycle's life through the API (the Register, a VA Submission from start to endorsement through a Cyber Manager's and a VA POC's return, a malware rejection, Exemptions approved, rejected and confirmed, a withdrawal, a role-holder review, an export and its disposal, the Overdue sweep, the role lapse and return, the Cycle's open and close, sign-in, sign-out, a step-up and refusals), then produces one dynamic test per row: the entry's action and outcome, the actor and the role they held (none for a job), the System, VA Submission and Finding ids where it is about one, the fixed detail it must carry, and a correlation id. Every free text typed in the walk carries a sentinel that no entry may hold. Entries about a System are read by System; entries about none are told from the rest of the suite's by the ids that existed before the walk.

3. **The permission matrix is a table in the test** (`PermissionMatrixTest`): 63 endpoints, seven people (nobody signed in; the SMO/Tech Lead and Cyber Manager of SYS-F1 and of SYS-F2; a VA POC signed in 10 minutes ago; an Auditor), each cell `OK` (the access rules let it through, whatever the command answers), `401`, `403`, `404` or `STEP` (`403 step-up-required` with the row's intent). Every `401` and `403` must be in the audit log as `REQUEST_REFUSED`, found by the response's correlation id, with its status, reason, intent and actor. The step-up list (nine intents) is checked stale and fresh. In Release 1 an Auditor opens only what every role may read; the Auditor's scope, the Cyber Manager's detailed export and the auditor pack are Release 2.

4. **Guards against a later gap.** Each suite fails the build when the code grows past it: the state table must name every `SubmissionState` and move every non-final one on; every `AuditAction` must have a row of the walk or name the Seam 1 test class that asserts it (`SIGN_IN_FAILED`, `STEP_UP_FAILED`, `STEP_UP_FULL_SIGN_IN`, `FILE_REPLACED`, `PROPOSAL_WITHDRAWN`, `SMO_UNREACHABLE`, `SMO_UNREACHABLE_CLEARED`, `EXEMPTION_LAPSED`), and the class must exist; every `@RestController` mapping must have exactly one matrix row, read with ArchUnit's importer. `CompletenessSchemaTest` reads the CHECKs from PostgreSQL: `audit_entry_detail_check` must accept exactly the `DetailKey`s, and `va_submission_state_check` and `notification_state_check` exactly the `SubmissionState`s.

5. **What the check found.** Nothing the spec's state table, audit list or permission matrix asks for was missing or wrong in Release 1's scope; the suites pass on what tickets 02 to 49 built. The one defect was in the session store, below.

6. **A person's sessions are read back whole** (the 401 after a step-up of tickets 09, 13 and 46). Spring Session JDBC's query for a person's sessions has no `ORDER BY`, and its reader builds one session from each run of adjacent rows. Once the store holds many rows of one person (a long-running store, or the Seam 1 suite after a few minutes), PostgreSQL joins by hash, a session's attribute rows come back apart, and the reader keeps whichever part came last. The one-session rule (ADR 0008) then misses the "ended" mark on an older session, so that session stays live; at the person's next step-up the rule sees two live sessions and ends both, the current one included, and the next request answers `401`. In production that is a VA POC signed out at a step-up, and an older session that a newer sign-in should have ended still working. The fix is `SessionStoreConfig.SESSIONS_OF_A_PERSON`, the same query ordered by session id, set through a `SessionRepositoryCustomizer`. `OneSessionRuleTest` fills the store with 150 sign-ins of one person, analyses the tables as autovacuum would, and then signs in and steps up ten times: before the fix the first step-up ended its own session. The stopgap in the Seam 1 reset that deleted every signed-in session (ticket 13) is removed, so the full suite exercises the rule as production does; without the fix four step-up tests fail there every run.

Not done here, on purpose:
- Release 2: the Auditor's grant, scope and reads, the Cyber Manager's detailed export, the auditor pack, mid-cycle moves and transfers.
- Ticket 51: the production adapters (`adapters.pending`: identity status, file store, mail relay, malware scanner).
- Reads that are not audited stay as decided: the Register list, inboxes, boards, the role-holder review, the export and disposal lists and the audit log itself (reviewer decisions, ADRs 0014, 0019, 0056); a `404` and a `429` are not refusals the log records (ADR 0014).

Consequences:
- The three suites add about three minutes to the back-end gate; `OneSessionRuleTest` about 45 seconds.
- A ticket that adds an endpoint, an audited action, a detail key or a state adds its row to the matching suite, or the build fails and says which.
- `MailSeam1.returnedForRework` moved up to `ReturnSeam1`, which the new suites share.

Amends ADR 0008 (how the one-session rule reads the store).
