# A rescan replaces one file once it is parsed, and moves only that file's Findings

Status: accepted

Ticket 21 (story 39) lets the SMO/Tech Lead replace one report file of a Scan Report with a rescan, so that uploading a rescan never loses work. It adds one endpoint, one migration (V16) and no module: the request is `ingestion`'s, the comparison of the Findings is `finding`'s. Ten decisions; the human decisions of 2026-10-18 in `docs/agents/reviewer-decisions.md` (the seven rescan entries) are folded in.

1. **A rescan is an upload that names the file it replaces.** `POST /api/submissions/{id}/files/{fileId}/replace` takes multipart `file` only: the Scan Report and kind are the old file's. It is quarantined and answered 202 with the rescan's status, exactly as an upload (ADR 0021), and walks the whole pipeline. `report_file.replaces_id` records the file it replaces. The rescan is not counted against the Scan Report's 20 files when it is sent (it takes the old file's place); while it is on its way both count, and once the old file is superseded it no longer does (`superseded_by IS NULL` in the live count).
2. **Nothing changes until the rescan is parsed.** The old file, its Findings and their proposals stay exactly as they are while the rescan is scanned and checked. A rescan that is rejected (malware, type, schema, anything) changes nothing, and the file can be replaced again. Only in the scan job's settlement that records the rescan as `PARSED` (ADR 0022 item 7) are the Findings moved, the old file superseded (`superseded_by`, `superseded_at`) and the replacement audited, in one transaction: a failure rolls all of it back and the rescan is retried on the next pass, like any settlement.
3. **Only a parsed report file that no rescan has replaced, and one rescan of it at a time.** A file that is not `PARSED` (still being checked, rejected, or supporting evidence, which rests in `READY`) or is already superseded is 409 `file-not-replaceable`. A unique partial index (`replaces_id` where `reject_code IS NULL`) lets one rescan of a file be live, on its way or parsed, so a second one while the first is being checked is 409 `replace-in-progress`, and two requests that race are settled by the table, not by a read-then-write. Checks run in the order ownership (another SMO, or a file not of this VA Submission, is the same 404, ADR 0013), the file, the state (Draft or Returned for Rework, else 409 `invalid-transition`), replaceable, then the content (an empty file is 400 `file-empty`). A Cyber Manager or VA POC is 403 by the role rule, which is also a URL rule so a 50 MB body is not spooled for them.
4. **The comparison is against the old file's places only.** The rescan's Findings are kept as any parse keeps them (item 10 says how they are locked first) (an existing key keeps its Finding, a new key is a new Finding); then the old file's places are removed. A kept key therefore swaps the old file's places for the rescan's and keeps its proposals and its review untouched. A Finding that another file of the VA Submission still reports keeps those places and its status. Each Finding that had a place in the old file is rated again by the places it has now (a Finding's severity is the highest of its places, ADR 0022 item 4), so a rescan that rates it lower lowers it.
5. **A Finding reported nowhere any more is proposed Remediated by the rescan, unless it is already Remediated.** It is not removed: it keeps its history and gets a new proposal, Remediated, `proposed_as = RESCAN`, with the evidence `Not reported by the rescan <name> (scanned <date>, uploaded <date>), nor by any other file of this Scan Report.`, where the name is the cleaned name the person gave the rescan (ADR 0021 item 10), the scan date is the business date of the date the rescan's report names (left out, with its comma, when the report names none) and the upload date is the business date the rescan was uploaded (Asia/Singapore, through the `Clock` bean). The proposal also names the replaced file (`replaced_file_id`, shown as `replacedFile` with its id and name), where the Finding was last reported: the old file's places are deleted, and the Cyber Manager downloads that kept file instead. It is written through the one proposal write path and audit builder (`Proposals.write`, ADR 0028), the same as a single proposal and a Bulk-set, with an explicit proposer (`Proposals.Proposer.rescan`: the uploader, `RESCAN`, the rescan and the replaced file) instead of the caller, so it becomes the current proposal and the review goes back to `PENDING` for the Cyber Manager, whatever the earlier proposal (a Confirmed False Positive or Risk Accepted included). A Finding whose current proposal is already Remediated, by whoever, is left as it is: a second Remediated would only ask for a review of nothing new. The proposal is recorded as made by the SMO/Tech Lead who uploaded the rescan (`proposed_by`), and as `RESCAN` (`proposed_as`). It keeps its severity as last reported and shows no places.
6. **Who made a proposal is a column.** V16 adds `finding_status_proposal.proposed_as` (`SMO` or `RESCAN`; carry-over adds its own in Release 2), filled `SMO` for every existing row by a default that is then dropped, so every write names it, and `replaced_file_id`. A check lets a `RESCAN` proposal be Remediated only, and requires `replaced_file_id` on a `RESCAN` proposal and nowhere else. Adding the column changes no row, so the append-only trigger (V14) is not involved. Each proposal shows `proposedAs`, and the row says "Rescan".
7. **The superseded file is kept.** It can still be read and downloaded by whoever may see the System, its status stays `PARSED`, and it says `supersededBy`; the rescan says `replacesId`. A check allows `superseded_by` only on a parsed file, and a unique index lets a rescan supersede one file. Nothing here deletes a file or its bytes. The retention ticket (49) lists superseded files for disposal once the VA Submission is Endorsed, and that early disposal deletes only the superseded file's bytes from the file store: its `report_file` row (name, hashes, links) stays until the Cycle-plus-3-years disposal, because a rescan proposal (`finding_status_proposal.replaced_file_id`, append-only) and the rescan (`report_file.replaces_id`, and the old row's own `superseded_by`) reference it, and those foreign keys are kept. A download of a disposed file then answers with a plain "disposed" problem (reviewer decisions, 2026-10-18).
8. **Audit.** The rescan's upload is the SMO/Tech Lead's `FILE_UPLOADED` entry with `file_id` (the rescan) and `replaced_file_id`; a refusal is the same action, REFUSED, with `reason` `state-not-editable`, `not-replaceable` or `replace-in-progress` (a 404 is not audited). The replacement is a `FILE_REPLACED` entry written by the scan job with `file_id` and `replaced_file_id`, and each Remediated proposal a rescan makes is a `STATUS_PROPOSED` entry built in the one place every proposal's entry is built (`Proposals.write`): every `STATUS_PROPOSED` entry, an SMO's too, carries `finding_status` and `proposed_as` (`SMO` or `RESCAN`); a Bulk-set adds `batch_id`, an approval memo `file_id` (on a proposal, `file_id` is only ever the memo), and a rescan `rescan_file_id` (the rescan) and `replaced_file_id` (the file it replaced). A refused rescan's `FILE_UPLOADED` entry also names the file it was to replace (`replaced_file_id`). A rescan proposal taken away as current because a file reports its Finding again (item 10) is a `PROPOSAL_WITHDRAWN` entry (category database) about the System, the VA Submission and the Finding, with the re-reporting file's `file_id` and `proposed_as` RESCAN, one per Finding, as a batch writes one entry per Finding (reviewer decisions, 2026-10-17). All three name the SMO/Tech Lead who uploaded the file as the actor (role `SMO`), because the change follows from their action; `proposed_as` tells a reader it was made for them. V16 adds `replaced_file_id`, `proposed_as` and `rescan_file_id` to the detail allow-list. The attribution to the uploader is one helper, `AuditActor.onBehalfOf`, used by all three job-written entries. Ids and fixed codes only: the rescan's name and its content never reach a log line, an audit entry or an error body (a test puts a sentinel in both).
9. **The screen.** On the Scan Report card each report file whose findings were read, that no rescan has replaced and that has no rescan on its way offers Replace: a form below the file list (outside its live region) that takes the focus, with a file input with its classification label and the same early type and size feedback as an upload. A rescan proposal on the Findings list shows "Rescan" and "Last reported in <name>" with a download of the replaced file through the file endpoint. A rescan names the file it replaces, and a replaced file says "Replaced by a rescan" and can still be downloaded. The Findings and the progress are asked for again when the rescan is parsed, as for any parsed file.
10. **A rescan's proposal does not outlive a file that reports the Finding again, and every settlement locks once, in id order.** Any settlement, a rescan's or an ordinary upload's, that reports a key whose current proposal is a rescan's takes that proposal away as current: `current_proposal_id` and `review_state` are cleared (the check of V14 wants both or neither), the proposal stays in the history, the Finding is back under Needs attention, and the withdrawal is audited (item 8), since it can undo a Cyber Manager's Confirmed review. Settlements of one VA Submission run one at a time: the first statement of every settlement's Finding work takes a transaction-scoped advisory lock keyed from the VA Submission's id, in a namespace only settlements use (`FindingStore.serialiseSettlements`, `pg_advisory_xact_lock`), and holds it until the settlement commits. Without it two scan-job instances (ADR 0021 item 3) settling two files of one VA Submission that add the same new key could each count their locks before the other's insert, so one would write places to a key it neither locked nor rated (its severity would understate them), and its withdraw step could touch that row outside the id order. With it, every existing Finding a settlement writes was committed before its locks are counted. Then, before it writes, every settlement locks every existing Finding it will touch (those of the VA Submission with one of the file's identity keys and, for a rescan, those with a place in the replaced file) with one `SELECT ... FOR UPDATE` in id order, as a proposal and a Bulk-set lock theirs (ADR 0028 item 4). So every transaction that locks more than one Finding takes all its locks at once in the same order, and a settlement and a proposal over the same Findings wait for each other instead of deadlocking. New keys are new rows, which no proposal can hold; they are inserted in hash order, with the severity of their places in the file, so two settlements adding the same new keys wait on them in the same order. **Severity always comes from places.** Places can be removed now, so a running maximum kept on the Finding could go stale (a Finding a rescan empties keeps the severity it was last reported with, and a later file reporting it lower must not be rated by that). So the upsert no longer touches an existing Finding's severity, and every settlement, after its places are added (and, for a rescan, the replaced file's removed), rates every existing Finding it locked by the highest of its current places (ADR 0022 item 4); a Finding with no place left keeps its last severity until a file reports it again. The order of locks is: the settlement lock, then the Finding rows in one id-ordered statement. A proposal or a Bulk-set takes only the id-ordered row locks and never the settlement lock, so it cannot wait on a settlement while holding something the settlement needs before its row locks, and the two still wait for each other in id order. Seam 1 runs one request at a time and the scan job is driven one pass at a time, so no test can show either lock or their order (the tests show that settlements in sequence stay correct, and a mutant that drops either lock survives them); they are held by the statements and this ADR.

Decided by the human on 2026-10-18 (docs/agents/reviewer-decisions.md, "A VA Submission cannot leave Draft or Returned for Rework while any of its files is scanning"): a settlement applies no VA Submission state rule. A rescan uploaded in Draft or Returned for Rework settles whatever state its VA Submission is in by then (an Exemption Requested, Withdrawn or, after ticket 25, In Review one), and its Remediated proposals are written as in an editable one, as an ordinary upload's Findings already are (ADR 0021). The plan's submit rule ("none still scanning") covers the submit route only; whether a settlement in a state that takes no proposals should still propose, skip the proposals, or the file be refused, is settled the other way round: the settlement stays as described, and no route may move a VA Submission out of Draft or Returned for Rework while any of its files is still scanning (submit, ticket 25; exemption request, ticket 40; the Register's withdraw, ticket 43), so a settlement always lands in an editable submission.

Consequences: a key reported again leaves the Finding with no current proposal, not a new one, so the SMO/Tech Lead proposes again (the withdrawal is a `PROPOSAL_WITHDRAWN` entry and the history of the Finding still holds the rescan's proposal); supporting evidence cannot be replaced (an evidence file is attached again instead; reviewer decisions, 2026-10-18); the occurrences of a superseded file are removed, so where the old file placed a Finding is read from that kept file, which a rescan proposal names, until its bytes are disposed of after endorsement; the lock statement of a large report carries up to 20,000 identity hashes in one array; settlements of one VA Submission wait for each other (two scan-job instances settle files of different VA Submissions in parallel, never two of the same one), which a VA Submission of 20 files a kind can afford.

Amends ADR 0021 (a file can be superseded and the live count excludes it), ADR 0022 (a rescan's Findings replace another file's places in the same settlement) and ADR 0027 (a proposal records who made it).

Amended by ADR 0050 (item 7): once its VA Submission is Endorsed, a superseded file is listed for disposal and an approved disposal deletes its content only; the row stays until its Cycle is disposed of, `contentDisposedAt` says when, and a download answers `410 disposed`.

Amended by ADR 0061: deleting a report file removes its places like a rescan; a Finding it leaves reported nowhere is removed if it never had a proposal and otherwise gets a Remediated proposal made as `FILE_DELETED` (item 5), which a file reporting it again withdraws (item 10); a rescan of a file deleted while it was checked settles as an ordinary upload, and a parsed rescan can be deleted, after which the file it superseded stays superseded but can be deleted too.
