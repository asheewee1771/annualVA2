# A Register change names its effects on in-flight work, and withdraws only what a VA POC confirms

Status: accepted (item 6 decided 2026-10-25, docs/agents/reviewer-decisions.md)

Ticket 43 (stories 5, 6 and 7) makes the Register preview say what each row would do to in-flight work, a VA Submission of the System that is started and not in a final state (Endorsed, Exempted, Withdrawn and Not Endorsed are final; a Not Started row a rejected Exemption request left, ADR 0048, holds no work: `SubmissionState.inFlight`), and makes the apply withdraw a retired System's in-flight VA Submission once the VA POC has confirmed it. It adds one migration (V34), no endpoint, no module and no screen; the preview, the apply's body and the Register screen gain what follows.

1. **A port the submissions implement.** The VA Submissions sit above the Register, so the register module defines `InFlightWork` and the submission module implements it (`InFlightSubmissions`): the in-flight VA Submissions of some Systems, in any VA Cycle, each with its Cycle, its state, whether a file of it is still being checked (`SubmitReadiness.filesScanning`, the rule the submit's `files-scanning` refusal reads, so no second scanning rule is written) and the lower-case emails of who acted at each step (never logged, audited or answered). It also withdraws (item 4) and answers how many it withdrew. The callers are the preview and the apply, made by a VA POC, whose scope is every System (ADR 0013); Systems are still read only through `RegisterSystems`.

2. **The preview's vocabulary.** `WorkEffects` is the one place the rule is written; the upload classifies its rows with it and the apply classifies the stored rows again with the work it holds. A row keeps its outcome; what holds it back is its `reasons` (until now only a BLOCKED row had any), and a preview with any reason on any row cannot be applied (`preview-blocked`). Each row gains `effects` and `inFlight` (each VA Submission's id, Cycle and state), and the counts gain `willWithdraw`, `willMove`, `willTransfer` and `heldBack` (rows that are not BLOCKED but that their in-flight work holds back; `blocked` stays the rows the file itself breaks a rule on). Whether an UPDATE moves or transfers a System is asked of `SystemSnapshot` once, by the classification and by the apply's announcements alike:
   - a RETIRE of a System with in-flight work is `WILL_WITHDRAW`, applied once confirmed (item 3), unless a file of one of its VA Submissions is still being checked, a rescan included: then the row carries `FILES_SCANNING` until the file settles (decision 2026-10-18);
   - an UPDATE that changes the Quarter is `WILL_MOVE` when the System has in-flight work in a Cycle that follows the Register (an older Cycle keeps its Quarters once a newer one opens, ADR 0044, so a move changes nothing there); one that changes the SMO/Tech Lead or the Cyber Manager is `WILL_TRANSFER` when it has in-flight work in any Cycle (the access guard reads the Register as it is). Both are held back in Release 1 with `MOVE_IN_FLIGHT` or `TRANSFER_IN_FLIGHT`, until the mid-cycle tickets of Release 2 (the spec's decision);
   - a transfer is also held back with `SEGREGATION_OF_DUTIES` when it would give one person two steps of an in-flight VA Submission (story 58): the new SMO/Tech Lead reviewed or endorsed it or was its Cyber Manager, or the new Cyber Manager started, submitted or endorsed it or was its SMO/Tech Lead. "Was" is read from the row's `before`, so the spec's example, its Cyber Manager becoming its SMO, is blocked even before they review. Release 2 lifts the transfer block, not this one.
   A row Blocked by the file itself, an ADD and a NO_CHANGE have no effect, and a rename touches no work. Classifying the same rows again gives the same answer. The reasons are fixed codes; the screen gives each its sentence, lists every row by its outcome (a held-back one with what holds it back), and adds the effect groups across them.

3. **Each withdrawal is confirmed, and the apply checks the work it was shown.** The apply's JSON body gains `withdraw`, the ids of the VA Submissions the VA POC ticked one by one in the Will withdraw group (ADR 0018 item 1 kept the body for reopening the preview after a step-up; it now carries the ticks too, and the screen restores them). After the existing checks, the apply holds every VA Cycle the app runs against a start (`SubmissionStore.lockCycle`, the close's lock) and the in-flight VA Submissions of the rows' Systems as a move holds them, in id order, in the order Register apply lock, Cycle locks, VA Submission rows (ADR 0044 item 6), and classifies the rows again: if anything differs from the preview (a VA Submission started, finished or with a file uploaded since) it is `409 work-changed`; a state that only moved on (a Draft submitted) is not a difference. Then `withdraw` must name exactly the preview's withdrawals, else `400 withdrawal-unconfirmed` (the preview stays usable). Holding the rows also keeps any file from being added to them before the commit, since an upload takes the row shared.

4. **The withdraw is the submissions' move.** In the apply's transaction, after each System is retired, its confirmed VA Submissions become `WITHDRAWN` by one statement that sets `SubmissionStore.OVERDUE_AFTER_MOVE` (a final state waits on no window, so the flag clears); each is one `SUBMISSION_WITHDRAWN` entry (SUCCESS, attributed to the VA POC, about the System and the VA Submission, with `state_from`, `state_to` and the `preview_id`), and a `SubmissionEvent` to Withdrawn is published. The applied answer gains `withdrawn`. The notifications (ADR 0043) listen to that event, not to a `SystemChangeEvent.WITHDRAWN` as ADR 0043 foresaw, because the event of the state machine already carries the VA Submission and the state it left: the SMO/Tech Lead the Register last named gets `WITHDRAWN` (no due date, their inbox as the link, since the System is no longer theirs), mailed with the `REGISTER_CHANGE` template and the `change_kind` "Withdrawn" (ADR 0046); a withdrawal from Awaiting Endorsement clears the VA POC pair for both, as an endorsement would, and one from Exemption Requested clears the request's pair and the endorsement pair (the one rule `WorkflowNotices.handledBy`, ADR 0048) and is told as a withdrawal, not as a decision on the request. V34 widens `notification_action_check` with every action allowed before it.

   Withdrawn is read-only and out of every count and reminder by what is already there: every command refuses a final state; an upload, a proposal and a review need Draft, Returned for Rework or In Review; the Overdue sweep skips retired Systems and final states; every dashboard and export reads a Cycle's Systems through `RegisterSystems`, which leaves a retired System out. A VA POC still reads the VA Submission itself and its audit history.

5. **A Not Started System's flag follows its new Quarter.** A System with no VA Submission moved to another Quarter is an ordinary UPDATE (its SMO/Tech Lead is told, ADR 0043). The Overdue sweep hears the apply's `SystemChangeEvent` `MOVED` inside the apply's transaction (an `@EventListener`, so the change commits or rolls back with the move), and the System's Not Started Overdue flag in each Cycle that is not closed, by its Quarter in that Cycle, is cleared when the new Quarter's Submission Window has not passed (V20's `window_passed`), and set again by the sweep when it does: the flag follows the current window, not a permanent "was late" mark (reviewer decisions, 2026-10-23, "Overdue clears when a submit moves into a window that has not passed"). The `SUBMISSION_OVERDUE` entry stays as the record. This closes ADR 0033's note that a moved System keeps its flag.

6. **The Withdrawn column stays empty** (decided 2026-10-25). ADR 0034 left the Quarter board's Withdrawn column to this ticket. A Withdrawn VA Submission belongs to a retired System, and every dashboard reads Systems through `RegisterSystems.active`, which leaves retired Systems out, so the column stays empty and story 7's "excluded from counts" holds without a special case. The alternative is to list the Withdrawn VA Submissions of the Cycle and Quarter in that column for a VA POC, uncounted, through a new reader of retired Systems.

Consequences:
- Ticket 12's note: in Release 1 a Draft never sees a move (it is blocked), so its stored Quarter and dates stand and the SMO inbox cannot show another Quarter beside them; re-dating a moved Draft is Release 2's.
- A System already retired with an in-flight VA Submission before this ticket (none in production) is not withdrawn by it.
- A Not Started row a rejected Exemption request left (ADR 0048 item 4) holds no work: retiring its System leaves it Not Started on a retired System, which no reader lists; moving its System leaves the row's Quarter, windows and Overdue flag as they were (item 5 clears only the flag of a System with no row), and a later start keeps them (ADR 0048's `TAKE_NOT_STARTED`). Re-dating such a row on a move is Release 2's, with the windows of a System moved mid-Quarter.
- Tests that transfer a System with in-flight work stand its VA Submission aside in a final state while the apply runs, until Release 2.

Amends ADR 0018 (the apply reads `withdraw` from its body and withdraws), ADR 0033 (a moved Not Started System's flag), ADR 0034 item 5 (the Withdrawn column) and ADR 0043 item 1 (the withdrawal is heard as a `SubmissionEvent`).
